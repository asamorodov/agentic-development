
# Терминология и перевод английских слов

Этот файл — короткий словарь обычных английских слов и анти-калек для русского технического текста. Он нужен для случаев, где слово не имеет особой локальной концептуальной роли и его можно спокойно перевести обычным русским вариантом.

Если слово несёт специальное различение в агентской разработке, сначала смотри `protocols/rules/conceptual-translation-glossary.md`. Особенно это касается `evidence`, `transcript`, `trace`, `acceptance`, `handoff`, `state` и близких слов.

Примеры слов, которые в обычном объяснении нужно переводить:

tests → тесты;

failures → сбои / провалы / неудачные случаи;

wins → удачные случаи / успехи;

feature → фича / возможность / функция / изменение, по контексту;

setup → рабочая конфигурация / среда / настройка;

default → вариант по умолчанию;

later → позже;

input → входные данные;

output → результат / вывод;

tools → инструменты;

tooling → инструменты / инструментальная среда / инфраструктура;

context → контекст;

maintenance → сопровождение / поддержка / обслуживание;

patterns → паттерны / устойчивые приёмы;

useful → полезный;

when useful → когда это действительно полезно;

works → работает;

stronger model → более сильная модель;

hard thinking → сложное мышление / тяжёлое мышление;

background tasks → фоновые задачи;

issue tracker → трекер задач;

web agents → веб-агенты;

mobile app → мобильное приложение;

desktop app → desktop-приложение или настольное приложение, по контексту;

workflow → рабочий процесс / порядок работы / режим работы;

review → проверка / разбор / ревью, по контексту;

implementation → реализация;

dependency → зависимость;

prompt → запрос, если не имеется в виду точный фрагмент prompt;

summary → резюме / краткое изложение / выжимка;

source → источник;

evidence → см. `conceptual-translation-glossary.md`; не переводить автоматически как `свидетельство`, `наблюдение` или `доказательство`;

observation → наблюдение; но если слово фактически означает материал для принятия изменения, см. `conceptual-translation-glossary.md`;

transcript → переписка / лог чата / сырой журнал сессии, по контексту; подробнее см. `conceptual-translation-glossary.md`;

trace → след / трасса / журнал / трассировка, по контексту; подробнее см. `conceptual-translation-glossary.md`;

handoff → передача контекста / передача работы / handoff-документ, по контексту;

acceptance → принятие / критерии принятия / решение принять изменение, по контексту;

runtime → среда выполнения / работающее приложение, по контексту.

Примеры плохого результата:

Если задача tricky, он просит вынести всё в spec, отправляет spec в GPT-5-Pro for review через ChatGPT и later вставляет useful parts back.

Лучше:

Если задача сложная или неоднозначная, он просит вынести всё в спецификацию, отправляет её на проверку в GPT-5-Pro через ChatGPT, а затем возвращает полезные идеи обратно в основной контекст.

Плохо:

Людям нужно место, где можно обсуждать реальные failures and wins без marketing layer.

Лучше:

Людям нужно место, где можно честно обсуждать реальные сбои и удачные случаи без маркетингового слоя.

Плохо:

Tests after feature/fix in same context.

Лучше:

Тесты лучше просить сразу после фичи или исправления, пока у агента ещё свежий контекст задачи.

Плохо:

This matters for transfer.

Лучше:

Для переноса этой практики это важная оговорка.

## Дополнение для Атласа V2: стек агентского исполнения

Эти варианты обязательны для планов и статей о стеке агентского исполнения, если пользователь не утвердил другой вариант.

agent execution stack → **стек агентского исполнения**. Не писать `execution stack` латиницей как обычный связующий термин.

delivery form / delivery surface → **форма, в которой агент доступен пользователю**; в компактном аналитическом контексте допустимо **форма доставки агента**. Не смешивать с архитектурой исполнения.

execution architecture → **архитектура агентского исполнения** или **архитектура исполнения**, если контекст уже ясен.

agent core → **агентское ядро**. Использовать, когда нужно отделить планирование, вызовы инструментов и ведение задачи от терминала, IDE, web-интерфейса или другой пользовательской поверхности.

working surface / user-facing surface → **рабочая поверхность**; если важен именно интерфейс для человека, можно писать **пользовательская поверхность** или прямо: `терминал`, `IDE`, `облачная среда`, `редакторная панель`.

runtime / execution environment → **среда выполнения**. Если речь не о среде, а о фактическом запуске задачи, писать **выполнение** или **прогон**.

runtime state → **состояние выполнения**. Не смешивать с **рабочим состоянием проекта** или состоянием работы над изменением.

run / agent run → **прогон**, **выполнение**, **агентский прогон**, по контексту. Не писать `ран`.

agent-computer interface → **интерфейс между агентом и компьютером**. `ACI` можно оставить после первого объяснения, если источник использует это сокращение.

open harness → **открытая рабочая обвязка**. Английский вариант допустим рядом при первом употреблении, если речь идёт о принятом названии класса или исследовательской линии.

orchestration → **оркестрация**, если речь о техническом coordination/orchestration layer; в более обычной фразе лучше **координация**, **организация взаимодействия** или **управление ходом работы**.

multi-agent orchestration → **многоагентная оркестрация**.

observability → **наблюдаемость**, когда речь о техническом слое traces, logs, metrics, debugging и inspection. В менее техническом контексте лучше писать **видимость хода работы**.

tracing → **трассировка**, если речь об instrumentation / tracing layer. Для `trace` как материала сессии см. `conceptual-translation-glossary.md`.

evaluation / evals → **оценка**, **автоматическая оценка**, **оценочный прогон**, **набор оценок**, по контексту. `evals` можно оставить только как название конкретной практики, инструмента или API-раздела.

benchmark → **бенчмарк**. Если речь о конкретной проверке, можно писать **бенчмарк-задача**, **бенчмарк-набор**, **результат бенчмарка**.

human-in-the-loop → **участие человека в ходе выполнения**, **контрольная точка с участием человека**, **решение человека в ходе работы**, по контексту. Английский термин можно оставить рядом при первом объяснении, если это название паттерна в источнике.

issue-to-PR → **режим от задачи к PR** или **путь от задачи к PR**. Не писать `issue-to-PR` без объяснения.

cloud issue-to-PR agent → **облачный агент от задачи к PR**.

app-builder surface → **среда сборки приложения** или **app-builder форма**, если нужно сохранить узнаваемый английский ярлык.

spec-driven surface → **среда вокруг спецификации** или **spec-driven поверхность**, если нужно сохранить связь с устойчивым английским термином.

workflow engine → **движок рабочего процесса** или **среда выполнения рабочего процесса**, по контексту.

relationship map → **карта отношений**. Для `agent_execution_stack_relationship_map.md` использовать именно эту форму.


## Дополнение для Атласа V2: репозиторий как интерфейс для агента

Эти варианты использовать в планах и статьях о том, как проект сообщает агенту правила, контекст, процедуры и доступы. Если в конкретном источнике термин является названием функции или файла, название можно оставить на английском.

agent-facing repository interface → **репозиторий как интерфейс для агента**. В более обычной фразе можно писать **интерфейс проекта для агента**. Не писать `agent-facing interface` без объяснения.

repository-level context file → **файл проектного контекста на уровне репозитория**; если речь шире, можно писать **постоянная инструкция репозитория** или **проектная инструкция репозитория**.

tool-specific instruction → **инструкция конкретного инструмента**. Не смешивать с постоянной инструкцией репозитория.

scope / scoped rule → **область действия** / **правило с областью действия**.

nested instruction → **вложенная инструкция**. Если речь о правилах для подпапок, лучше писать **локальное правило** или **инструкция для отдельной области репозитория**.

steering → **steering** как название механики Kiro; при объяснении писать **проектные правила**, **устойчивый проектный контекст** или **правила, направляющие работу агента**, по контексту.

skill → **skill** как название механики; при объяснении писать **повторяемая процедура**. Не переводить автоматически как “навык”, если это делает текст менее точным.

hook → **hook** как название механики; при объяснении писать **точка автоматического вмешательства** или **автоматическое вмешательство в ход работы**.

subagent → **subagent** как название механики; при объяснении писать **отдельная роль**, **отдельный исполнитель** или **делегирование части работы**, по контексту.

MCP → **MCP**; при первом объяснении писать, что это структурированный доступ к ресурсам и инструментам. Не писать, что MCP сам по себе даёт право действовать.

instruction noise → **шум от лишних инструкций**. Форма **инструкционный шум** допустима как короткий технический ярлык, но обычный текст лучше писать естественнее.

instruction repair → **исправление и поддержка инструкций**. Если речь обо всём слое, писать **исправление и поддержка интерфейса проекта для агента**.

task-specific instruction → **временная инструкция для конкретной задачи** или **инструкция для конкретной задачи**. Не превращать частные форматы исполнительных архивов в публичный термин.

work interface for a task → **рабочая рамка конкретной задачи** или **материалы и порядок работы для конкретной задачи**, по контексту.


## Атлас V2 / A3 — от прогона к принятому изменению

Эти варианты использовать при планировании и написании статьи `От прогона к принятому изменению`.

- `agent run` — `агентский прогон` или `прогон агента`. Если речь о конкретной попытке выполнения задачи, лучше `прогон агента`.
- `run log` — `журнал выполнения`.
- `trace` — `трассировка`, когда речь о техническом trace инструмента; `след выполнения`, когда речь шире: переписка, команды, результаты инструментов, логи и изменения файлов.
- `tool output` — `результат вызова инструмента` или `вывод инструмента`.
- `evaluation` / `eval` — `оценочный прогон`, `оценка` или `автоматическая оценка`, по контексту. Не превращать всё в одно слово `eval` без необходимости.
- `benchmark` — `бенчмарк`, если речь о принятом классе задач или наборе тестовых задач.
- `verification material` — `проверочный материал`.
- `evidence` в этой зоне не переводить автоматически как `свидетельство` или `наблюдение`; чаще нужен `проверочный материал`, `основание проверки`, `материал для решения`.
- `acceptance record` — `запись о принятии результата` или `запись решения`.
- `agent-authored PR` — `PR, созданный агентом`.
- `rejected PR` — `отклонённый PR` или `непринятый PR`.
- `duplicate PR` — `дублирующий PR`.
- `stale context` — `устаревший контекст`.
- `review interaction` — `взаимодействие в ревью` или `ход ревью`.
- `decision rationale` — `основание решения` или `пояснение решения`, не `рациональ`.
- `post-merge learning` — `обучение процесса после merge` или `выводы после merge`, в зависимости от текста.

### Дополнение к A3: статус материала и переходы между статусами

Использовать в планах и статье `От прогона к принятому изменению`, если эти различения нужны для естественного русского текста.

- `status shift` — **смена статуса материала**. Не писать «статусный шифт».
- `transition threshold` / `status threshold` — **порог перехода** или **условие перехода**, по контексту. Если речь о более обычной фразе, писать «что должно измениться, чтобы материал стал основанием для следующего шага».
- `review material` — **материал для ревью**.
- `basis for decision` — **основание решения**. Если речь о принятии результата, можно писать **основание принятия**.
- `material for follow-up` / `learning material` — **материал для сопровождения**, **материал для дальнейшей работы**, **материал для улучшения процесса**, по контексту.
- `system evaluation` — **оценка системы**.
- `run inspection` — **разбор конкретного прогона** или **разбор хода выполнения**.
- `change verification` — **проверка конкретного изменения**.
- `acceptance decision` — **решение о принятии результата**.
- `what it does not prove` — **чего этот материал не доказывает**.
- `what strengthens the material` — **что делает этот материал сильнее как основание для следующего шага**.


### Дополнение к A3: проверки и материалы решения

- `status checks` — **проверки статуса** или **status checks**, если речь о конкретной механике GitHub. В обычном объяснении лучше писать **проверки CI** или **обязательные проверки PR**, если это точнее.
- `PR checks` — **проверки PR** или **обязательные проверки PR**.
- `API diff` — **API diff** как название класса инструментов; при объяснении можно писать **сравнение API** или **проверка изменений API**.
- `contract check` — **проверка контракта**.
- `CI signal` — **CI-сигнал** или **сигнал CI**; в обычном тексте чаще лучше писать **результат CI**.

### Дополнение к A2: стек агентского исполнения и прямые сравнения

Использовать в планах и статье `Стек агентского исполнения`, чтобы не превращать разные уровни стека в плоскую таблицу конкурентов.

- `false comparison` / `wrong comparison` — **ложное сравнение** или **непрямое сравнение**, по контексту. В обычном тексте лучше писать **с этим нельзя сравнивать напрямую**.
- `direct competitor` — **прямой конкурент**. Использовать только если инструменты действительно закрывают один и тот же участок работы и один и тот же уровень стека.
- `same layer` — **тот же слой стека** или **тот же уровень стека**.
- `different layers of the stack` — **разные слои стека**.
- `delivery surface` — **форма доставки агента** или **пользовательская поверхность**, если речь о том, где человек встречает инструмент.
- `execution architecture` — **архитектура исполнения**.
- `user-facing form` — **форма, обращённая к пользователю**, **пользовательская форма** или конкретнее: терминал, IDE, облачная среда.

- `app-builder surface` — **среда сборки приложения**.
- `spec-driven surface` — **среда вокруг спецификации** или **среда, где спецификация становится рабочей поверхностью**.

## 2026-06-17 — многоязычность и будущий английский перевод

Эта секция не заменяет двуязычный реестр `work/multilingual/BILINGUAL_TERM_REGISTRY.md`, а только фиксирует правила для русского текста.

- Не ухудшать русский текст ради будущего английского перевода. Русский корпус должен оставаться естественным и читаемым.
- Для будущего перевода сохранять не английский синтаксис в русском тексте, а стабильные ID, ссылки на источники, терминологические решения и translation notes.
- `Теория`, `Атлас`, `Рабочие сценарии`, `Каталог проблем и решений`, `Истории` должны иметь рабочие английские пары в bilingual registry.
- Английские источники при будущей английской версии нужно сверять с оригиналом, а не переводить обратно из русского пересказа.
- Технические имена, файлы, команды, API, протоколы и названия продуктов не переводить, если это собственные имена или устойчивые технические обозначения.
- Для крупных стабилизируемых материалов добавлять маленькую проверку `translation-readiness`: стабильный ID, рабочий английский title, ключевые термины в реестре, сохранённые source links, заметки для неочевидных русских формулировок.
