# IX. Среда исполнения: где работает агент, что ему разрешено и какой след остаётся

В агентской разработке легко рассуждать так, будто между намерением и результатом почти нет промежуточных слоёв. Есть задача, есть модель, есть контекст, есть кодовая база, и агент «делает работу». Пока агент только обсуждает задачу, пишет план или готовит черновик, такая короткая формула ещё терпима. Но когда он начинает менять файлы, запускать команды, открывать браузер, обращаться к API, читать логи, создавать ветку или готовить pull request, это уже не просто разговор о задаче. Агент выполняет действия в определённой среде, с конкретными правами и с реальными последствиями.

Возьмём обычный пример. В продукте есть страница оплаты: пользователь меняет тариф, проходит checkout, возвращается на `/billing`, а карточка тарифа всё ещё показывает старый план, пока страницу не обновить вручную. Агенту поручают найти причину, исправить устаревшее состояние billing UI, не сломать существующие subscription flows и вернуть pull request.

В формулировке задачи это небольшой bugfix. При выполнении это уже цепочка разных действий. Агент читает код фронтенда и бэкенда, ищет путь возврата из checkout, правит отдельный worktree, запускает тесты, поднимает локальное приложение, открывает браузер, смотрит консоль и сетевые запросы, пытается проверить тестовый платёжный сценарий, упирается в секреты и сетевую границу, может попросить approval, вызвать MCP/tool для трекера задач или billing provider и оставить после себя журнал команд, трассу браузера, diff и резюме PR.

Если среда устроена небрежно, вся эта цепочка превращается в расплывчатую фразу: «агенту дали доступ» или «агент сделал задачу». Но доступ к чему именно? К чтению кода? К записи в рабочее дерево? К запуску тестов? К браузеру, где пользователь уже вошёл в реальные сервисы? К test API key? К внешнему MCP server? К созданию PR? К merge?

Это разные границы, и проблемы начинаются там, где одна граница начинает подменять другую.

Есть ещё одна особенность агентского запуска: разные действия выглядят похожими, потому что все они приходят из одного чата или одного agent thread. В интерфейсе видно, что агент «что-то делает». Но инженерно это разные переходы. Когда агент читает `billing_controller.ts`, он получает информацию. Когда он правит frontend hook в worktree, он создаёт diff. Когда он запускает `npm test -- billing`, он исполняет код проекта. Когда он открывает локальную страницу в браузере, он получает наблюдение о поведении продукта. Когда он вызывает MCP tool для staging logs, он выходит за пределы локального проекта. Когда он создаёт test customer во внешней billing-системе, он уже производит внешнее действие. В одном интерфейсе всё это может выглядеть как продолжение одного диалога, но последствия у этих шагов разные.

Поэтому в этой главе нужно удержать простое различение. Техническая возможность выполнить действие ещё не означает, что действие допустимо, безопасно или уже принято проектом. Агент может запустить команду. Среда может разрешать определённый класс команд. Пользователь может подтвердить конкретный выход за границу. Тест или браузер может дать полезный проверочный сигнал. И всё равно проекту нужен тот, кто имеет право сказать: это изменение можно считать частью работы проекта.

Эта глава не является обзором Codex, Claude Code, MCP, Kiro, Roast, Temporal, LangGraph или Sandvault. Все эти источники важны здесь только как материал для одного аргумента: агентское действие становится инженерной работой не из-за силы модели и не из-за удачного промпта, а из-за среды, которая задаёт место работы, права, инструменты, наблюдения, возможность продолжения и след, который останется после запуска.

## 1. Сначала нужно понять, где агент работает

Одной формулировки задачи недостаточно. Из фразы «почини billing UI» не видно, в какой среде агент будет работать: в обычном checkout разработчика, в отдельном Git worktree, в контейнере, в облачном devbox, под отдельным пользователем macOS, в CLI внутри sandbox или в корпоративной платформе, которая сама готовит окружение и возвращает PR. У этих вариантов разный радиус последствий.

Первое, что нужно назвать, — область, где агент может читать и писать. Агент работает не в абстрактной «кодовой базе», а в конкретных местах: корень проекта, отдельный worktree, области с правом записи, временные и кэшированные пути, сгенерированные файлы, защищённые директории. В современных агентских инструментах это уже отдельный слой. В документации Codex sandbox описан как техническая граница, а approval policy — как правило остановки перед выходом за неё: sandbox определяет, какие файлы можно менять и можно ли использовать сеть, а approval policy определяет, когда Codex должен остановиться и спросить разрешение [OpenAI Codex sandboxing](https://developers.openai.com/codex/concepts/sandboxing). В Claude Code исходная позиция тоже строится вокруг прав на чтение по умолчанию: редактирование файлов, запуск тестов и выполнение команд требуют явного разрешения, а запись ограничена рабочей папкой и её подпапками, если не выдано дополнительное право [Claude Code Security](https://code.claude.com/docs/en/security).

Для billing-задачи это означает следующее. Агенту нужна отдельная рабочая область, где его diff не смешивается с обычной работой человека. Он может читать `docs/billing.md`, код маршрутов и контроллеров, frontend billing hook, существующие тесты. Он может писать в пределах worktree. Но из этого не следует, что ему можно читать реальные значения из `.env`, трогать production database, открывать залогиненный billing dashboard или вызывать внешний payment API.

Git worktree — простой способ такого отделения. Агент работает в отдельной директории, похожей на checkout, и его изменения не смешиваются с текущей веткой разработчика. Документация Codex app про worktrees описывает запуск нескольких независимых задач в фоновых worktree, передачу результата обратно в локальную среду и отношение к каждой задаче как к отдельной рабочей области [OpenAI Codex worktrees](https://developers.openai.com/codex/app/worktrees). У Mike McQuaid Sandvault/Superset доводит эту логику дальше: агент работает от имени изолированного пользователя, а worktree и общая папка нужны для контролируемой передачи файлов, а не для полного доступа к домашнему каталогу мейнтейнера [Mike McQuaid, “Sandboxed Agent Worktrees”](https://mikemcquaid.com/sandboxed-agent-worktrees-my-coding-and-ai-setup-in-2026/), [Sandvault repository](https://github.com/webcoyote/sandvault).

В нашем примере агент создаёт diff в worktree `billing-ui-fix`. Он не трогает текущую ветку разработчика. Тесты запускаются внутри этого дерева. На выходе человек получает патч или PR. Если направление оказалось неверным, worktree можно удалить. Если diff полезен, его можно рассмотреть и влить.

Но worktree не означает, что результат можно принимать. Он отделяет изменения, но не доказывает их правильность. Он помогает вести несколько задач параллельно, но не решает смысловые конфликты между ними. Он защищает основное рабочее дерево от случайных правок, но сам по себе не обязательно защищает секреты, сеть, браузер и внешние инструменты. Worktree может быть частью хорошей среды, но он не заменяет sandbox, permission, тесты, ревью и состояние проекта.

Инструкции вроде `AGENTS.md`, `CLAUDE.md`, steering files или project rules тоже важны, но они не являются границей исполнения. Они могут сказать агенту: используй только test data, не трогай production, запускай `npm test -- billing`. Но если среда одновременно показывает production secrets, открывает реальную browser session и разрешает широкий network access, текстовая инструкция остаётся просьбой. Хорошая среда делает опасный шаг невозможным или хотя бы требует отдельного подтверждения в тот момент, когда агент подходит к границе.

Поэтому нельзя смешивать контекст и среду. Контекст помогает агенту понять проект. Среда определяет, что агент сможет сделать даже тогда, когда он ошибается, спешит, неправильно понял задачу или пытается обойти ограничение.

## 2. Sandbox, permission, approval и принятие результата — разные вещи

В обычном разговоре можно сказать: «агенту разрешили запускать команды». Для инженерной среды этого мало. Нужно уточнить: какие команды, где, с какими правами, с какой сетью, с какими файлами, с какими исключениями и кто рассматривает шаги за предел текущей границы.

Sandbox — это техническое ограничение. Команды агента выполняются в среде, где часть файлов недоступна для записи, сеть может быть выключена, локальные сервисы закрыты, private network заблокирована, а protected paths нельзя менять. Codex в текущей документации говорит, что локально агент по умолчанию работает с отключённым network access и OS-enforced sandbox, который обычно ограничивает действия текущим workspace. Это ограничение распространяется на запущенные команды, включая `git`, package managers и test runners [OpenAI Codex Agent approvals & security](https://developers.openai.com/codex/agent-approvals-security), [OpenAI Codex sandboxing](https://developers.openai.com/codex/concepts/sandboxing).

Permission — это выбранный режим допуска. Codex, например, описывает встроенные режимы `:read-only`, `:workspace`, `:danger-full-access` и пользовательские настройки. Но та же документация подчёркивает: эти permission-настройки задают границы локального sandboxed command execution, а app connectors, MCP servers, browser/computer-use surfaces, cloud environments и approved escalations имеют отдельные controls [OpenAI Codex permissions](https://developers.openai.com/codex/permissions). Это важное различение. Если локальное выполнение команд переведено в read-only, это не значит, что весь агентский запуск безопасен: browser, MCP server, облачная среда или уже одобренный выход за границу могут иметь другую поверхность прав.

Отсюда следует ещё одна практическая деталь. Даже network allowlist не является решением о доверии. Если агенту разрешили обращаться к определённому домену, это означает только то, что трафик может пройти к этому домену. Это не означает, что ответ домена полезен, безопасен, свободен от misleading content, не содержит prompt-injection-like instructions и не подтолкнёт агента к лишним действиям. Документация Codex прямо разводит outbound destinations и trust: domain rules ограничивают трафик, но не решают, заслуживает ли allowed destination доверия [OpenAI Codex permissions](https://developers.openai.com/codex/permissions).

Approval — это подтверждение конкретного перехода. Агент пытается сделать что-то за пределами текущего режима: записать файл outside writable roots, открыть network, вызвать tool with side effect, зайти на новый сайт в browser, использовать test key. Система спрашивает: разрешить один раз, на сессию, для класса действий или не разрешать вовсе. Такая пауза нужна не потому, что человек должен благословлять каждую команду. Она нужна потому, что выход за границу должен быть видимым.

Claude Code показывает ту же проблему через свои режимы. `acceptEdits` позволяет автоматически принимать file edits и некоторые common filesystem commands inside scope. `plan` даёт исследовать задачу и писать план без правки исходников. `auto` уменьшает количество prompts через отдельный classifier, но документация называет его research preview и не replacement for review on sensitive operations. `bypassPermissions` прямо описан как режим, отключающий обычные permission prompts, и документация рекомендует использовать его только в sandboxed контейнере без internet [Claude Code Security](https://code.claude.com/docs/en/security).

В billing-примере агент может иметь permission писать в workspace и запускать tests. Но когда он просит доступ к Stripe-like test API, это уже другой шаг: сеть, секрет, внешний сервис, создание внешнего объекта. Approval должен быть узким: например, один раз разрешить создать test Checkout Session с test key для этого воспроизведения. Такое подтверждение не должно превращаться в общее право пользоваться внешним биллингом.

Auto-review в Codex полезен как признак направления, в котором будут развиваться такие среды. Auto-review может поставить другого reviewer agent на границу sandbox: основной агент остаётся в той же sandbox и approval policy, а reviewer решает, можно ли выполнить eligible escalation. Документация подчёркивает, что Auto-review заменяет ревьюера на этом шаге, но не выдаёт новых прав; он не расширяет writable roots, не включает network и не ослабляет protected paths [OpenAI Codex Auto-review](https://developers.openai.com/codex/concepts/sandboxing/auto-review). Это удобная форма для будущих систем, но она не отменяет человеческого принятия результата. Reviewer agent может сказать, что конкретный вызов выглядит допустимым; владельцем продукта он от этого не становится.

Важно и то, что отказ не должен превращаться в игру «найди обход». В документации Codex Auto-review отказ возвращает причину и прямо инструктирует основного агента не добиваться того же результата обходным путём, косвенным исполнением или нарушением политики; он должен найти материально более безопасный маршрут или остановиться [OpenAI Codex Auto-review](https://developers.openai.com/codex/concepts/sandboxing/auto-review). Именно такая дисциплина нужна агентской среде: отказ должен менять маршрут работы, а не запускать рационализацию обхода.

Так появляются четыре разных слоя. Permission говорит, что действие лежит внутри текущей политики. Approval разрешает конкретный выход за предел. Sandbox технически ограничивает среду. Принятие результата решает, может ли итог войти в проект. Если агент получил approval на test API call, он не получил право merge. Если reviewer agent одобрил escalation, он не стал product owner. Если sandbox позволил команду, это ещё не означает, что команда безопасна по смыслу.

Эту тему легко свести к морали «не включайте опасные режимы». Лучше сформулировать иначе: чем больше автономности получает агент, тем точнее должна быть устроена внешняя среда. Это не вопрос недоверия к модели как к «характеру». Это признание того, что у действия должны быть место, радиус последствий и граница.

## 3. Команда, tool и browser — разные поверхности работы

После того как мы назвали место работы и базовые границы, важно не смешать разные поверхности действия. Shell command, MCP tool и browser action могут быть доступны из одного интерфейса, но это не одно и то же.

Shell command исполняет код в локальной или удалённой среде. Простая команда вроде `npm test -- billing` может быть безопасной, если она работает в disposable environment, без сети и без секретов. Та же команда может стать опасной, если test setup читает реальные `.env`, пишет в shared database или запускает destructive fixture. Поэтому хорошая среда не ограничивается фразой «можно запускать команды». Она задаёт command policy, working directory, writable roots, environment variables, network rules, timeout, output capture и audit log.

Codex Rules формализуют это через `prefix_rule`: decision может быть `allow`, `prompt` или `forbid`; побеждает самое ограничительное совпадение; `match` и `not_match` задают условия; правило применяется к argv, а для shell-команд учитывается разбор простых цепочек [OpenAI Codex rules](https://developers.openai.com/codex/rules). Это хорошая инженерная поверхность: команда не просто «кажется опасной» или «кажется нормальной», она попадает в правило.

Но у такой механики есть предел. Команда — это строка, а риск часто находится не в самой строке, а в окружении. `npm test` почти всегда выглядит безопасно. Но если test script скачивает arbitrary code, трогает shared database или пишет generated files outside workspace, строка уже плохо описывает действие. `migrate:fresh` в одноразовой test DB и `migrate:fresh` в базе, которую разработчик вручную собирал неделю, — разные действия, хотя строка похожа.

Arvid Kahl показывает этот слой на бытовом уровне. В его настройках Claude Code появляются правила `allow` и `deny`: разрешить полезные команды, запретить опасные, например действия, похожие на database wipe или рискованную migration. Но он же описывает проблему обхода: если запрет построен слишком поверхностно, агент может попытаться выполнить запрещённую команду через shell script [Arvid Kahl, “How to actually use Claude Code to write code with agents”](https://thebootstrappedfounder.com/how-to-actually-use-claude-code-to-write-code-with-agents/).

В billing-задаче policy не должна сводиться к списку «разрешённых» команд. Нужны protected paths, disposable local database, отдельные test credentials, сетевые ограничения, hooks и logs. Если агенту нельзя менять billing schema без review, ограничение должно ловить не только прямую migration command, но и попытку создать скрипт, который делает то же самое. Если агенту можно запускать tests, среда должна сохранять test command, output и commit/branch, к которому эти результаты относятся.

MCP/tool — другая поверхность. Спецификация MCP описывает resources, prompts и tools; tools — это возможности для взаимодействия с внешними системами, которыми управляет модель [MCP tools specification](https://modelcontextprotocol.io/specification/draft/server/tools). Если tool только читает документацию, он похож на расширение контекста. Но если tool читает private issues, получает логи, создаёт test objects, закрывает ticket или меняет project config, это уже действие вне локальной кодовой базы.

В billing-примере MCP/tool может вернуть публичную документацию billing provider, прочитать внутренний issue с шагами воспроизведения, достать последние logs from staging, создать test customer или test Checkout Session, закрыть support ticket, обновить subscription config. Называть всё это одним словом «доступ к инструментам» слишком грубо.

Правильнее говорить о capabilities и их радиусе последствий. MCP спецификация прямо вводит authorization поверх HTTP-based transport: server может требовать OAuth, scopes, consent и token audience; security best practices требуют user consent and control, защищать token passthrough и учитывать confused deputy problem [MCP authorization](https://modelcontextprotocol.io/specification/draft/basic/authorization). Codex MCP документация добавляет практическую грань: MCP tools могут читать, писать и выполнять действия во внешних системах; для этого нужны доверие к server, careful scoping, подтверждение destructive actions и понимание, что OAuth может вводить человека в заблуждение, если непонятно, какой именно server получает права [OpenAI Codex MCP](https://developers.openai.com/codex/mcp).

HumanLayer хорошо формулирует проблему через harness engineering: опасный `rm` легко запретить, а вот «увеличить quota customer tenant до $1000/месяц» — это не похоже на shell-команду, но может быть настоящим product operation [HumanLayer, “Skill issue: harness engineering for coding agents”](https://www.humanlayer.dev/blog/skill-issue-harness-engineering-for-coding-agents). Для главы IX это ключевой пример. Внешнее действие может быть оформлено как аккуратный tool call, но его нельзя оценивать только по названию tool.

Browser — третья поверхность. Claude Code Chrome extension показывает, почему browser нельзя считать просто ещё одним viewer. Агент может подключиться к конкретной вкладке, видеть страницу, console и network requests, делать screenshots и выполнять click/type. Документация прямо предупреждает, что extension даёт агенту доступ к содержимому browser session, включая сайты, где пользователь вошёл в систему, а значит пользователь должен работать с тестовыми данными, отдельной тестовой сессией браузера и осторожно относиться к credentials [Claude Code Chrome extension](https://code.claude.com/docs/en/chrome).

Для billing UI браузер очень полезен. Он показывает, что видно пользователю после возврата из checkout. Он позволяет увидеть console error, stale network response, missing refetch. Но если агент открывает залогиненный production billing dashboard, browser становится не просто наблюдением, а каналом к реальному аккаунту. Без отдельной тестовой сессии браузера и тестовых данных такой шаг легко пересекает границу, которую текст задачи вообще не называл.

Вывод здесь простой: хорошая среда не говорит агенту обобщённо «у тебя есть tools». Она перечисляет поверхности работы и их границы. Команда исполняет код. Tool может перейти во внешнюю систему. Browser показывает поведение продукта и может нести чужие учётные данные. У каждой поверхности должны быть свои правила, approvals, logs и ограничения.

## 4. Среда должна возвращать агенту полезную обратную связь

Среда исполнения — это не только запреты. Если среда умеет только останавливать агента, он будет чаще просить широкий доступ или уходить в догадки. Хорошая среда помогает безопасному пути быть самым удобным: запускает локальное приложение, даёт тестовые данные, возвращает понятные ошибки, показывает нужные логи, сохраняет вывод команд и связывает результаты с конкретным diff.

Hooks — один из способов встроить такую обратную связь в жизненный цикл. Claude Code Hooks привязываются к событиям вроде `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop` и `SessionStart`; они могут блокировать, добавлять контекст, запускать команды и возвращать структурированный JSON с `decision`, `reason` и дополнительными данными [Claude Code Hooks](https://code.claude.com/docs/en/hooks). Kiro Hooks работают с file events и manual triggers, могут запускать agent hooks, читать project context и проверять изменения [Kiro Hooks](https://kiro.dev/docs/hooks/). Для этой главы важно не сравнивать реализации, а увидеть форму: среда может вмешиваться до действия, после действия и в момент остановки.

В billing-задаче `PreToolUse` может запретить запись в billing schema без review. `PostToolUse` после изменения frontend hook может автоматически запустить targeted tests. `Stop` hook может проверить, есть ли diff, были ли запущены нужные tests и не остались ли failing commands. `SessionStart` может загрузить `docs/billing.md` и напомнить, что внешние payment calls требуют test key и отдельного approval.

Но hook тоже не является доказательством. Если hook говорит, что целевые тесты не прошли, это один вид обратной связи. Если Stop hook спрашивает другого агента, выглядит ли работа завершённой, это другой вид обратной связи. Оба сигнала могут быть полезны, но их нельзя одинаково называть доказательством.

Язык harness engineering у Martin Fowler помогает назвать более широкую форму: guides/feedforward направляют агента до действия; sensors/feedback сообщают, что произошло после действия; harness должен подавать feedback в форме, удобной для LLM, а не только как человеческий log [Fowler, “Harness engineering for coding agents”](https://martinfowler.com/articles/harness-engineering.html). Это важное дополнение к permission. Permission отвечает на вопрос, можно ли сделать шаг. Sensor показывает, что получилось после шага. Review решает, можно ли засчитать результат.

Рядом с hooks находится более прозаический, но не менее важный локальный harness: `make dev`, `make test`, `make tail-log`, seed scripts, local fixtures, debug email stdout, browser helpers, local API wrappers. Armin Ronacher в заметках про agentic coding и Pi постоянно возвращает модель к обычному исполнению программы. У проекта должны быть скрипты, которые запускают dev environment, читают logs, дают browser access, выводят тестовое письмо в stdout, создают local state и позволяют агенту увидеть то, что действительно важно [Armin Ronacher, “Agentic Coding”](https://lucumr.pocoo.org/2025/6/12/agentic-coding/), [Armin Ronacher, “Code MCPs”](https://lucumr.pocoo.org/2025/8/18/code-mcps/), [Pi repository](https://github.com/earendil-works/pi). Он также осторожно относится к превращению всего в MCP: иногда обычный code/CLI — лучшая поверхность инструмента.

Для billing bug хороший локальный harness может быть простым. `make dev` поднимает фронтенд и бэкенд. `make seed-billing-user` создаёт пользователя с basic plan. `make simulate-checkout-return` или local webhook replay создаёт тестовое событие. `make test-billing-refresh` запускает targeted regression. `make tail-log billing` показывает последние relevant lines. Browser helper открывает локальный `/billing` как seeded user. Ни один из этих инструментов не выглядит эффектно. Но именно они делают безопасный маршрут дешёвым.

Хороший локальный harness заметен не по одному большому инструменту, а по отсутствию мелких препятствий. `make dev` можно вызвать дважды, и он не поднимет две копии сервера на одном порту. Если порт занят, команда скажет, какой процесс уже работает. Логи не потеряются в прокрученной terminal history, а будут лежать в известном файле. `make tail-log` покажет последние строки без бесконечного потока. Тестовое письмо появится в dev log, а не в реальном inbox разработчика. Webhook replay будет иметь test fixture. Seed data создаст billing user в известном состоянии. Есть targeted test command, и агенту не нужно угадывать всю раскладку тестов.

Когда этих деталей нет, агент начинает чинить не продукт, а окружение. Он перезапускает сервисы, угадывает порт, читает огромный output, создаёт новую фикстуру вместо использования существующей, просит реальные credentials или сдаётся. Поэтому harness относится к правам исполнения не косвенно, а очень практически: он не только показывает, что можно делать, но и делает безопасный путь самым простым.

Чем хуже локальный harness, тем чаще агент просит широкий доступ: к сети, production-like dashboard, реальным данным, arbitrary shell commands. Чем лучше harness, тем меньше таких просьб. Хорошая среда не просто запрещает опасное. Она предлагает рабочий безопасный маршрут и даёт полезную обратную связь, когда этот маршрут ломается.

## 5. Запуск можно возобновить, но это ещё не восстанавливает смысл работы

Некоторые агентские задачи укладываются в одну interactive session. Многие — нет. Даже billing/UI fix может стать длинной цепочкой: подготовить worktree, прочитать issue, воспроизвести поведение локально, внести patch, запустить тесты, открыть браузер, остановиться до получения тестового API key, вызвать внешний сервис, продолжить работу, собрать артефакты и подготовить PR. Если session падает после создания внешнего тестового объекта, наивный повтор может создать этот объект ещё раз. Если человек через несколько часов разрешает network call, запуск должен продолжиться без потери состояния.

Здесь появляется workflow runtime. Shopify Roast полезен потому, что делает AI step частью исполняемого workflow, а не превращает всю работу в свободный разговор с агентом. В примере Shopify Boba процесс добавления Sorbet annotations не начинается с просьбы к агенту «типизируй проект». Сначала идут детерминированные изменения, затем Sorbet autocorrect, затем разбор оставшихся ошибок, затем `CodingAgent` получает конкретную остаточную задачу, и после этого запускаются tests/type checks [Shopify Engineering, “Introducing Roast”](https://shopify.engineering/introducing-roast).

Названия `cmd`, `ruby`, `chat`, `agent`, `map`, `repeat`, `call` важны меньше, чем сама форма работы. `cmd` запускает обычную команду. `ruby` выполняет обычный код. `chat` спрашивает модель, не выдавая ей полного права редактировать код. `agent` передаёт ограниченный coding step. `map` раскладывает шаблон по коллекции. `repeat` создаёт явный цикл с условиями выхода. Session resume/forking позволяет продолжить или разветвить дорогой контекст без старта с нуля. Workflow становится не разговором о процессе, а средой, где часть действий выполняется обычной программой, а часть остаётся задачей модели.

Внешний walkthrough Daniel Doubrovkine добавляет полезную бытовую деталь: запуск Roast зависит от обычных runtime-фактов — API key, выбранной модели и правки workflow file. Он сначала проверяет OpenAI key через `curl`, затем меняет settings модели в workflow, потому что исходная смесь моделей недоступна или слишком дорога для его запуска [Doubrovkine, “Executing Structured A.I. Workflows with Shopify Roast”](https://code.dblock.org/2025/05/10/executing-structured-ai-workflows-with-shopify-roast.html). Для главы IX это важно: даже структурированный AI workflow не живёт в чистой логике процесса. Он зависит от ключей, моделей, бюджета, локального окружения и доступных команд.

Quix’s Klaus Kode показывает ту же логику с другой стороны. Команда пыталась приручить Claude Code для построения data pipelines и пришла к workflow engine, где обычные API calls и cloud sandbox берут на себя устойчивую orchestration, а Claude Code используется для bounded coding step [Quix, “Claude Code wouldn’t behave, so I built a workflow engine to tame it”](https://quix.io/blog/claude-code-wouldnt-behave-so-i-built-a-workflow-engine-to-tame-it), [Klaus Kode repository](https://github.com/quixio/klaus-kode). Смысл не в том, что каждой команде нужен такой engine. Смысл в границе: устойчивость исполнения часто лучше держать в обычной программе, а не просить модель помнить весь порядок работы.

Durable execution frameworks обобщают сторону продолжения. LangGraph поддерживает persistence, interrupts и human-in-the-loop decisions вокруг tool calls [LangGraph durable execution](https://langchain-ai.github.io/langgraph/concepts/durable_execution/). Temporal даёт durable workflows, event history, signals, timers и replay [Temporal documentation](https://docs.temporal.io/workflows). Restate ведёт журнал steps и side effects, чтобы replay мог пропустить уже завершённую работу [Restate documentation](https://docs.restate.dev/). DBOS workflows могут продолжаться с последнего завершённого шага и использовать workflow IDs для idempotency [DBOS documentation](https://docs.dbos.dev/python/tutorials/workflow-tutorial). Эти системы не нужно сравнивать здесь как продукты. Для главы достаточно общего пункта: они позволяют останавливать запуск, повторять шаги, возобновлять выполнение и хранить историю исполнения.

В billing/UI примере долговечный workflow может остановиться, когда агенту нужны тестовые платёжные ключи, продолжиться после точечного approval, записать ID созданной test Checkout Session и не создать её повторно после неудачной попытки. Это важная инженерия. Но из неё не следует, что работа принята. Workflow может знать, что step 7 resumed, а step 8 passed. Но он не обязательно знает, соответствует ли test coverage продуктовому обещанию, принял ли domain owner риск внешнего сервиса и следует ли merge PR.

Здесь важно не смешать две памяти. Durable runtime может помнить, что step 6 failed, step 7 ждал approval, approval arrived, а step 8 resumed. Он может replay event history или пропустить completed journaled steps. Но если reviewer спросит: «что именно мы доказываем?», runtime может не иметь ответа за пределами собственных шагов. Он знает порядок исполнения, но не обязательно хранит смысл работы. Для этого нужен другой объект: work item с promise, owner, blocker, gate, required checking material, accepted/rejected state и safe next action.

Так проходит граница между состоянием исполнения и состоянием работы. Runtime может продолжить запуск. Но он не обязан сам понимать, что именно осталось доказать, кто должен принять решение и какой следующий шаг безопасен.

## 6. Платформа готовит вариант изменения, но не принимает его

В большом масштабе те же механизмы становятся платформой. Разработчик или продуктовый человек просит изменение из Slack, issue tracker или IDE. Система готовит environment, загружает blueprint или workflow, выдаёт агенту tools, запускает checks, создаёт PR и возвращает вариант изменения. Здесь важны Stripe’s Minions, но использовать их нужно аккуратно. Публичные материалы и вторичные пересказы говорят о больших объёмах PR, однако эти числа относятся к разным вещам: Minion-produced PR, AI-assisted PR, merged PR, one-shot merge и human-reviewed PR могут означать разные контуры работы. Для этой главы важнее не точное число, а структура: массовое агентское производство кода переносит нагрузку с написания на выбор задач, подготовку среды, проверочный материал, review и policy.

Интеграционный benchmark Stripe для этой главы полезнее, чем громкие числа PR. Stripe построила реалистичные test environments для агентов, пытающихся собрать Stripe integrations: code, databases, scripts, test Stripe API keys и deterministic graders, которые проверяют API behavior, UI behavior или Stripe artifacts вроде test-mode Checkout Sessions [Stripe, “Can AI agents build real Stripe integrations?”](https://stripe.com/blog/can-ai-agents-build-real-stripe-integrations). Именно такая форма нужна примеру с биллингом. В платежах “almost right” недостаточно. Среда должна позволить агенту взаимодействовать с реалистичной системой и затем проверить конкретные артефакты.

Поздние эксперименты Stripe со steering добавляют ещё один полезный пункт: не прятать важную инструкцию там, где агент может её никогда не прочитать. Если инструкция важна, она должна лежать на пути исполнения — как loaded context, explicit error, skill, tool intervention или deterministic check [Stripe, “You can’t whisper at an AI agent”](https://stripe.dev/blog/ai-steering-experiments). Это тот же принцип, что у hooks и harnesses: если правило действительно важно, агент должен встретить его в момент действия.

Но платформа не решает вопрос полномочий. Система в духе Minions или Roast может произвести PR, даже много PR. PR — это вариант изменения. CI и checks дают обратную связь. Generated summary помогает читателю. Проекту всё равно нужны правила: кто может merge, какие домены требуют owner review, как раскрывать AI-generated contributions, какие изменения слишком широки и что делать, когда reviewers становятся bottleneck.

Правила Homebrew для AI-assisted PR полезны здесь потому, что удерживают ответственность на contributor: disclosure, готовность отвечать на review, splitting large PRs и limits on low-quality AI contributions остаются социальными и процессными gates вокруг технического runtime [Homebrew CONTRIBUTING](https://github.com/Homebrew/brew/blob/main/CONTRIBUTING.md). Это не антиагентская позиция. Это всё то же различение: среда может быстро производить candidate changes; право принять их остаётся у проекта.

## 7. След исполнения ещё не является проверкой

В конце здорового billing/UI run агент может вернуть много полезного материала:

```text
diff в worktree
список изменённых файлов
журнал команд
вывод test/typecheck/lint
маршрут в browser и screenshot
наблюдения из console/network
ID внешних тестовых объектов
записи approval
журнал MCP/tool calls
workflow event history
резюме PR
известные ограничения
```

Это след исполнения. Он ценен, но сам по себе ещё не является проверкой.

Чтобы этот след стал проверочным материалом, его нужно связать с обещанием изменения. Исходное обещание было не «агент запустил тесты». Оно было таким: после успешного возврата из checkout страница billing должна показать обновлённый план без ручного refresh, а существующие subscription flows не должны сломаться. Поэтому важен не весь log, а та его часть, которая отвечает на этот claim: test route, test account, endpoint refetch, frontend state update, отсутствие console error, targeted regression и то, что именно было проверено вручную через browser.

Здесь глава IX передаёт вопрос будущей главе о проверке. Runtime может создать сырой материал. Он может даже частично его структурировать. Но проверочный материал — это не просто output; это output, истолкованный относительно обещания изменения. Browser screenshot без route, action и state может быть декоративным. Test pass без связи с bug может вводить в заблуждение. Long transcript может скрыть отсутствие единственной проверки, которая действительно нужна.

То же относится к approval. Approval на запуск `npm test` не является approval на вызов внешнего billing API. Approval на вызов test API не является approval на использование production credentials. Approval на создание PR не является approval на merge. Green CI не равен product acceptance. Успешный hook не равен maintainer review. Workflow completion не равен project authority.

Именно поэтому механизмы уровня PWG относятся к следующему слою, а не растворяются внутри execution runtime. Gate может ждать human review, CI, GitHub run, PR state, timer или другой work item. Prime/rehydration artifact может помочь следующему агенту восстановить task context. Но эти механизмы не заменяют run log; они объясняют, для чего этот run log нужен. Runtime говорит: вот что произошло. Состояние работы говорит: почему это важно, кто должен принять решение, что всё ещё заблокировано и какого материала не хватает.

Если глава IX размоет эту границу, следующие главы потеряют своё основание. Trace становится полезной только тогда, когда привязана к claim, который должна поддержать. Durable run history без work item — это дневник исполнения. Work item без run trace — обещание без заземлённого материала. Жизненному циклу изменения нужны оба слоя, но они не совпадают.

Итоговое различение такое: среда исполнения показывает, что агент сделал, где он это сделал, какие границы переходил и какие следы остались. Следующий слой связывает эти следы с обещанным изменением. Слой полномочий решает, может ли результат войти в проект.

## 8. Зачем эта глава нужна всей теории

В разговорах об агентской разработке часто перескакивают от способности модели к организационному результату. Модель умеет писать код — значит, кажется, что она может решить задачу. Агент умеет запускать tools — значит, кажется, что он может довести работу до ship. Тесты прошли — значит, кажется, что всё правильно. PR существует — значит, кажется, что работа завершена.

Между этими пунктами находится среда исполнения. Это не самая эффектная часть агентской разработки, но именно здесь автономность становится пригодной к использованию. Среда определяет, сколько рутинной работы можно отдать агенту без постоянного вмешательства человека, насколько узким будет радиус последствий при ошибке, что агент может наблюдать, что может менять, где он должен остановиться, как продолжит работу после паузы и какой материал получит reviewer.

Зрелый вопрос звучит не как «как дать агенту больше доступа?». Лучше спрашивать иначе: какой доступ должен быть открыт по умолчанию, какой требует узкого подтверждения, какой должен быть невозможен, какие наблюдения должны быть простыми, какие внешние последствия обязательно логируются, какие шаги требуют продолжимого запуска и где человеческое право решения остаётся явным.

Хорошая среда не только ограничивает агента. Она делает безопасный путь дешёвым, а опасный переход заметным. Она даёт небольшие надёжные tools, читаемые logs, тестовые аккаунты, изолированные worktrees, scoped network, явные approvals и recoverable run state. Она позволяет агенту разбираться с обычными ошибками выполнения без того, чтобы человек подтверждал каждый безвредный шаг. И она останавливает агента там, где граница уже не техническая: production data, external side effects, product judgment, customer impact, merge authority.

Таково место среды исполнения в жизненном цикле изменения: не сделать модель всемогущей, а сделать её действия ограниченными, наблюдаемыми, восстанавливаемыми и пригодными для review. Тогда агент может быстрее проходить те части работы, которые безопасно механизировать, а проект сохраняет отдельные имена для решений, которые нельзя передать sandbox, hook или workflow runtime.
