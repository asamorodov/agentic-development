# X. От рабочих узлов к обслуживаемому потоку: Gas Town, Beads и среда для многих агентских действий

## Когда параллелизм перестаёт быть прогрессом

В одиночной агентской сессии управляемость часто кажется естественной. Есть человек, есть окно разговора, есть текущая задача, есть ответ модели, есть следующий шаг. Даже когда модель ошибается, человек примерно понимает, где находится работа: в этом чате, в этом репозитории, в этом диффе, в этом списке замечаний. Поэтому ранние практики агентской разработки обычно усиливают одну сессию: дают модели больше контекста, лучше описывают задачу, открывают инструменты, ограничивают права, сохраняют след действий.

Этот режим ломается, когда рабочих потоков становится несколько. Один агент правит backend, другой пишет тесты, третий обновляет документацию, четвёртый разбирает review comments, пятый делает маленький рефакторинг в соседнем пакете. Каждый может быть локально полезен. В каждом окне есть движение. Где-то изменился код, где-то появился тест, где-то агент нашёл важное ограничение, где-то pull request почти готов. Но проект как целое становится хуже видимым. Человек видит не работу, а шум: много активных сессий, статусов, промежуточных отчётов, проверок, ожиданий и полузакрытых задач.

Это не дефект конкретного промпта. Это другой класс проблемы. Пока работа одна, достаточно держать состояние отдельной задачи: что нужно сделать, что уже сделано, что блокирует продолжение, какие проверки нужны. Когда работ много, нужно обслуживать сам поток: где какие задачи лежат, кто их взял, что зависло, что ждёт gate, что ушло в merge, что не вернуло результат в общее состояние, что требует решения человека, а что нельзя запускать прямо сейчас, потому что система уже перегружена.

Поэтому масштабирование агентской разработки начинается не с увеличения числа агентов. Наивное «запустим больше сессий» быстро создаёт больше мест, где работа может потеряться. Масштабирование начинается с рабочей среды, которая делает множество агентских действий обитаемыми: у работы появляется адрес, состояние, владелец, очередь, маршрут, площадка, история, условия продвижения, сервисные роли и структурированный путь возврата к человеку.

Gas Town и Beads важны здесь как один из первых видимых прототипов такой среды. Gas Town описывает себя как multi-agent orchestration / workspace manager для Claude Code, GitHub Copilot, Codex, Gemini и других агентских поверхностей; в README отдельно названы persistent work tracking, context persisted in git-backed hooks, mailboxes/handoffs и хранение work state в Beads ledger ([Gas Town README](https://github.com/gastownhall/gastown)). Но читать Gas Town полезнее не как продуктовую витрину и не как набор эксцентричных ролей вроде Mayor, Polecat или Deacon. Его лучше читать как попытку назвать новый слой работы: что должно существовать вокруг агентов, если они перестают быть одной управляемой сессией и превращаются в множество параллельных потоков.

## Почему долговечного состояния отдельной работы уже недостаточно

Предыдущий шаг в этой логике — persistent work graph. Работа не должна жить только в промпте, в памяти модели или в убедительном отчёте агента. Ей нужен внешний объект: задача, зависимости, статус, история, владелец, условия остановки, проверочные материалы, handoff, возможность возобновления после разрыва сессии. Без этого агентская разработка остаётся слишком хрупкой: модель может забыть, контекст может сжаться, человек может открыть новую сессию, а работа потеряет форму.

Beads даёт сильный пример такого нижнего слоя. В текущей документации Beads описан не как простой JSON-список задач, а как Dolt-backed система, где Dolt является sole storage backend и source of truth; рабочее состояние хранится в version-controlled SQL, поддерживает восстановление, синхронизацию и server mode для multi-writer сценариев ([Beads Architecture](https://gastownhall.github.io/beads/architecture)). Это важно: рабочий объект становится не заметкой для человека, а частью версионированного состояния проекта.

На этом уровне уже появляются задачи, зависимости, gates, готовность к следующему шагу, явное назначение и связь с агентской сессией. `bd gate create` может заблокировать issue до human, timer, GitHub run или GitHub PR condition; заблокированная работа не должна появляться в `bd ready` ([Beads gate](https://gastownhall.github.io/beads/cli-reference/gate)). `bd pin` и `bd hook` помогают закрепить работу и связать её с исполнением; multi-agent documentation Beads описывает sequential handoff и fan-out/fan-in, где большая работа делится на части, а затем снова собирается через зависимости ([Beads multi-agent coordination](https://gastownhall.github.io/beads/multi-agent/coordination)). `bd prime` выдаёт AI-optimized context для новой сессии и прямо рассчитан на hooks в Claude Code, Gemini и Codex, чтобы агент не начинал работу после context compaction как с чистого листа ([bd prime](https://gastownhall.github.io/beads/cli-reference/prime)).

Этого уже много. Если проект раньше жил только в переписке, Beads/PWG радикально меняют ситуацию: работа становится долговечной, видимой, возобновляемой и пригодной для передачи между людьми и агентами. Но эта глава начинается там, где такого слоя становится мало.

Представим изменение payment webhook в продукте. Нужно изменить backend handler, добавить миграцию, обновить frontend-экран истории платежей, поправить API documentation для интеграторов, добавить regression checks и затем провести final review. На уровне Beads/PWG это можно оформить как несколько связанных work items: `B-101` для backend contract, `B-102` для database migration, `B-103` для frontend rendering, `B-104` для API docs, `B-105` для regression checks, `B-106` для final integration review. У части задач есть dependencies: frontend ждёт финальную форму backend status model, final review ждёт все ветки. У части есть gates: tests ждут CI run, docs ждут human approval, потому что публичный текст для интеграторов нельзя менять механически.

Такой граф уже лучше набора чатов. Но он всё ещё не отвечает на вопрос, кто обслуживает движение. Кто заметит, что backend-agent взял `B-101`, но перестал продвигать работу? Кто увидит, что docs-agent нашёл важное замечание о replayed webhook payloads, но оставил его только в локальном отчёте и не вернул в `B-105`? Кто удержит `B-105` от преждевременного ready, пока CI gate не закрыт? Кто обработает `MERGE_FAILED`, если backend branch конфликтует с migration branch? Кто решит, стоит ли запускать ещё пять агентов или система уже перегружена? Кто поднимет человеку архитектурное решение, которое агент не должен принимать сам?

Persistent work graph хранит работу. Обслуживаемая среда должна удерживать поток многих работ.

## Рабочее состояние и обслуживание потока

Здесь полезно развести два уровня.

Первый уровень — **рабочее состояние**. Это состояние отдельной работы: что нужно сделать, какие зависимости есть, кто назначен, какой статус, какие gates, какие комментарии, где branch или PR, какие проверки связаны с задачей. Beads/PWG в основном работает на этом уровне. Он делает работу внешней и долговечной.

Второй уровень — **обслуживание потока**. Это работа со множеством задач: выдача в рабочие площадки, очереди, capacity, связи между rig, наблюдение за lifecycle, обнаружение orphaned work, возврат результатов из локальных сессий в общее состояние, merge path, recovery, escalation и поверхность управления для человека.

Без первого уровня второй превращается в хаос процессов. Нечего маршрутизировать, если работа не имеет устойчивой формы. Но без второго первый превращается в красивую базу задач, вокруг которой человек всё равно вручную бегает с фонариком: какой агент жив, что он сделал, где это записано, почему PR не слился, какой вывод потерялся, какую задачу можно запускать дальше, а какую нельзя.

Поэтому слово «оркестрация» здесь одновременно полезно и опасно. Оно указывает на проблему, но слишком быстро сглаживает механику. В агентской разработке речь должна идти не о туманной координации, а о конкретных функциях: routing, pinning, hook, gates, ready queue, rig, convoy, lifecycle patrol, merge recovery, scheduler, backpressure, escalation, return-to-state. Именно эти функции и образуют слой, который появляется поверх persistent work graph.

## Beads как рабочая память, которую может читать и менять агент

Beads в этой главе лучше понимать как нижний durable слой такой среды. Он не просто хранит задачи для человека, а делает рабочее состояние пригодным для агентского чтения и действия.

Во-первых, Beads даёт долговечные рабочие объекты. Issue/bead может иметь dependencies, labels, comments, status, gates, связь с другими репозиториями и route. В multi-agent routing docs Beads описаны routes, pattern matching по title, labels и path prefix, auto-routing, cross-repo dependencies и hydration ([Beads multi-agent routing](https://gastownhall.github.io/beads/multi-agent/routing)). Это уже не «список задач», а рабочий слой, который может направлять задачу туда, где она должна исполняться.

Во-вторых, Beads даёт явное назначение. `bd pin` и `bd hook` помогают различить «кто-то должен этим заняться» и «эта работа сейчас привязана к исполнению». Для человека это может казаться мелочью, но для многоагентной среды это принципиально. Если задача висит на hook, можно ожидать, что исполнитель действительно ведёт её дальше. Если он этого не делает, появляется не неопределённая тревога, а нарушение рабочего контракта.

В-третьих, Beads даёт gates. Gate — это способ сказать, что работа не должна двигаться дальше, пока не выполнено внешнее условие. Это может быть human approval, timer, GitHub run или GitHub PR ([Beads gate](https://gastownhall.github.io/beads/cli-reference/gate)). В одиночном процессе человек может помнить: «этот пункт вроде готов, но надо дождаться CI». В многоагентном процессе такая память быстро ломается. Gate нужен, чтобы работа не выглядела готовой для следующего шага, пока условие не закрыто.

В-четвёртых, Beads связывает agent session с текущим состоянием. `bd prime` рассчитан на то, чтобы дать агенту компактный, ориентированный на работу контекст. Codex integration docs показывают конкретную current-practice форму: SessionStart injects full `bd prime`; PreCompact checks memories-only; PostCompact marks need for refresh; UserPromptSubmit injects full `bd prime`; отдельно указано, что PreCompact alone is not enough because of Codex stdout behavior ([Beads Codex integration](https://gastownhall.github.io/beads/integrations/codex)). Это важная деталь: контекст не просто «как-то хранится». Он возвращается в новую или сжатую сессию через жизненный цикл инструмента.

Наконец, Beads даёт форму повторяемым процессам. В workflows docs formulas/TOML и molecules описывают превращение процесса в persistent instance: steps map to issues, dependencies управляют `bd ready`, hooks и pinning связывают шаги с исполнителями ([Beads Workflows](https://gastownhall.github.io/beads/workflows); [Beads Molecules](https://gastownhall.github.io/beads/workflows/molecules)). Это важный мост к предыдущей главе о process profiles. Процесс перестаёт быть только текстовой процедурой; он может стать рабочим графом, который живёт в состоянии проекта.

Но Beads сам по себе ещё не город. Он делает рабочие объекты достаточно плотными, чтобы с ними могла работать среда. Дальше нужен слой, который обслуживает множество таких объектов.

## Gas Town как город вокруг рабочих объектов

Gas Town добавляет к Beads/PWG не ещё одно поле задачи, а организационную среду вокруг многих работ. В architecture docs прямо различаются town-level и rig-level beads: town-level слой держит Mayor mail/messages, convoy coordination, strategic issues/decisions, town-level agent beads и role-definition beads; rig-level слой держит bugs/features/tasks, merge requests/code reviews, project molecules и rig-level agent beads ([Gas Town Architecture](https://github.com/gastownhall/gastown/blob/main/docs/design/architecture.md)). Это почти готовая схема различения между локальной работой проекта и городским обслуживанием потока.

`Rig` можно понимать как рабочую площадку вокруг конкретного репозитория или проекта. В сквозном примере backend, frontend, docs и tests могут быть разными rig или разными рабочими площадками внутри larger rig. Важно не буквальное соответствие, а принцип: работа живёт не в абстрактном пространстве, а в месте, где есть репозиторий, ветка, проверки, исполнители и локальное состояние.

`Convoy` нужен там, где работа проходит через несколько таких площадок. В публичной документации Gas Town convoys описаны как cross-rig tracking, auto-notification и historical record ([Gas Town docs](https://docs.gastownhall.ai/)). Это полезное отличие от обычной зависимости между задачами. Dependency говорит, что одна работа логически ждёт другую; convoy помогает вести движение через несколько rig так, чтобы город видел связанный маршрут, а не отдельные локальные задачи.

`Mayor` — не просто «главный агент». Это поверхность управления. Mayor видит работу, dispatches её, принимает problem feed, получает escalations и соединяет человека с городом. Ролевой шаблон Mayor описывает `gt sling <bead-id> <rig>` как команду work dispatch: spawn polecat, hook work, start session ([Mayor role template](https://github.com/gastownhall/gastown/blob/main/internal/templates/roles/mayor.md.tmpl)). Эту команду не обязательно разбирать как CLI-справочник, но она хорошо показывает сдвиг: поручение не остаётся приватным сообщением в чате; оно становится операцией над work item, rig и executor.

Вторая важная поверхность Mayor — не запуск, а чтение проблем. B3 уже фиксировал `gt feed --problems` как характерный образ: агенты группируются по состояниям вроде GUPP Violation, Stalled, Zombie, Working и Idle. Эта деталь нужна не как ещё одна команда, а как защита человеческого внимания. Человек не должен читать все терминалы, чтобы понять, где город горит. Но сама сводка ещё недостаточна: из неё должны следовать действия — re-sling, defer, close gate, escalate, recover, merge, mark fix-needed.

`gt prime` и `bd prime` дают ещё одну грань интерфейса. `bd prime` подаёт агенту Beads work context, а `gt prime` подаёт роль и городскую рамку. Это не «память в голове модели», а повторная загрузка рабочего положения из внешнего состояния. Continuation в такой среде не равна просьбе «вспомни, что мы делали». Она строится через durable state и role-specific context.

`Polecat` и `Crew` обозначают разные типы исполнителей. Polecat — расходуемый исполнитель дискретной работы; Crew — более долговечная или контекстная форма. Здесь важна фраза из авторского объяснения Steve Yegge: agent is not session; agent role и текущая сессия не одно и то же, потому что сессия может умереть, а работа и роль должны сохраняться ([Welcome to Gas Town](https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04)). Продолжимость возникает не из магической памяти модели, а из внешних ролей, hooks, beads, mail, history и рабочих площадок.

`gt mail` нужно упомянуть не как главный механизм главы, а как пример канала, который переживает процессные сбои и оставляет след. Если агент просто написал сообщение в терминале, оно легко теряется вместе с сессией. Если сообщение становится частью mail/handoff/state, его может прочитать сервисная роль, Mayor или следующий исполнитель.

`Witness`, `Refinery`, `Deacon` и `Dogs` показывают, что в многопоточной агентской среде появляются сервисные роли. Они не обязательно создают основную фичу. Они смотрят, возвращают, чинят, сливают, эскалируют, проверяют здоровье среды. В публичной документации Gas Town infrastructure roles включают Mayor, Deacon, Witness и Refinery ([Gas Town docs](https://docs.gastownhall.ai/)). Это не декоративная терминология. Это ответ на тот факт, что параллельность сама себя не обслуживает.

Особенно важен документ о polecat lifecycle patrol. Там появляются операционные события: `RECOVERED_BEAD`, `GUPP_VIOLATION`, `ORPHANED_WORK`, сообщения Witness → Refinery вроде `MERGE_READY`, а также Refinery → Witness вроде `MERGED` и `MERGE_FAILED` ([Gas Town polecat lifecycle patrol](https://github.com/gastownhall/gastown/blob/main/docs/design/polecat-lifecycle-patrol.md)). Эти названия ценны не сами по себе, а потому что показывают форму зрелого состояния. Работа не просто «вроде зависла». Она становится событием, которое может вызвать recovery, re-dispatch, merge handling или escalation.

Gas Town тем самым делает видимым второй этаж. Beads держит работу; Gas Town пытается обслуживать жизнь этой работы в городе.

## Сквозной пример: изменение payment webhook

Вернёмся к примеру с payment webhook. Команда хочет изменить обработку платежных событий. Работа распадается на несколько связанных частей:

- `B-101`: backend webhook contract;
- `B-102`: database migration;
- `B-103`: frontend status rendering;
- `B-104`: API docs update;
- `B-105`: regression checks;
- `B-106`: final integration review.

У `B-103` есть dependency на `B-101`, потому что frontend должен знать финальную модель статусов. У `B-106` есть dependencies на все рабочие ветки. У `B-105` есть gate на CI run. У `B-104` есть human gate: публичный текст для интеграторов должен подтвердить человек.

На первом шаге всё выглядит хорошо. Backend rig получает `B-101` и `B-102`. Docs rig получает `B-104`. Test rig получает `B-105`. Frontend rig пока ждёт backend dependency. Mayor или maintainer dispatches work, часть задач pinned или hooked на конкретных исполнителей. В сессиях появляются отчёты. Где-то агент уже изменил код, где-то собрал список тестовых payloads, где-то начал править docs.

На этом месте многие разговоры о многоагентности заканчиваются слишком рано: «мы распараллелили работу». Но реальная проблема начинается дальше.

### Зависший claim

Backend polecat взял `B-101`, открыл рабочую площадку, изменил часть handler code и оставил промежуточный отчёт. Потом сессия оборвалась, ушла в неправильную ветку или перестала продвигать работу. В обычной системе человек видит разрозненные признаки: где-то был diff, где-то есть ветка, где-то осталось сообщение, но непонятно, жив ли исполнитель и надо ли ждать.

В обслуживаемой среде это должно стать состоянием. Если работа находится на hook, а исполнитель её не ведёт, нарушается рабочий контракт. Gas Town glossary формулирует GUPP как правило: если на hook есть работа, её нужно выполнять ([Gas Town Glossary](https://github.com/gastownhall/gastown/blob/main/docs/glossary.md)). Поэтому зависание может стать `GUPP_VIOLATION`, stalled state или `ORPHANED_WORK`, а не чувством человека, что «кажется, агент пропал».

Затем сервисная роль должна превратить событие в действие: вернуть bead в очередь, re-sling work, запросить status, сохранить частичный результат, поднять проблему Deacon или Mayor. Смысл не в том, что каждый проект обязан буквально иметь Witness. Смысл в том, что кто-то или что-то должно выполнять эту функцию. Иначе человек снова становится ручным сторожем всех открытых сессий.

### Полезный вывод не вернулся в состояние

Docs-agent, работая над `B-104`, обнаруживает важную деталь: интеграторов нужно предупредить о replayed webhook payloads, иначе они могут ошибочно принять повторную доставку старого события за новую транзакцию. Это хороший вывод. Возможно, без него изменение будет опасным, даже если код формально пройдет тесты.

Но агент оставляет вывод только в локальном отчёте. Он не обновляет `B-104`, не добавляет linked issue для `B-105`, не создаёт dependency, не уведомляет backend. В обычной агентской работе это один из самых частых тихих провалов: модель сделала полезную мыслительную работу, но эта работа не стала частью проекта.

Обслуживаемая среда должна вернуть такой вывод в durable state. Это может сделать сам агент, сервисная роль, ревьюер или Mayor. Важно, чтобы результат стал comment, dependency, new work item или gate, а не остался в тексте, который следующий исполнитель не увидит. В примере появляется новая связь: regression checks должны покрыть replayed payloads; docs human gate теперь проверяет именно публичное предупреждение; backend work может получить уточнение к contract behavior.

Здесь видно, почему эта глава не равна главе о задачах. Задачи уже были. Потерялось не наличие задачи, а перенос знания из локальной сессии в общий рабочий контур.

### Gate удерживает преждевременную готовность

Test-agent добавил regression checks и сообщает: всё зелёное. Но у `B-105` есть gate на CI run. У `B-104` есть human gate. Если среда плохо устроена, maintainer видит несколько уверенных отчётов и считает проект почти готовым. Потом выясняется, что тесты запускались локально на старом наборе payloads, CI ещё не прошёл, а публичный текст docs никто не подтвердил.

Gate нужен не для бюрократии. Он нужен, чтобы работа не попадала в `ready` раньше времени. Beads gate docs прямо указывают, что blocked issue не появляется в `bd ready` до разрешения gate ([Beads gate](https://gastownhall.github.io/beads/cli-reference/gate)). Это простая, но важная форма сопротивления самообману: «агент сказал готово» не равно «следующий шаг может безопасно брать эту работу как завершённую».

Важно провести границу. Gate не доказывает, что тесты хорошие. Он только не даёт потоку продвинуться до выполнения внешнего условия. Вопрос, достаточно ли regression checks покрывают replayed payloads, относится уже к следующей главе о проверочном материале.

### Merge failed как управляемое состояние

Refinery пытается слить backend branch по `B-101`, но получает `MERGE_FAILED`: параллельная migration branch `B-102` изменила соседний слой. В обычном режиме это снова превращается в шум: merge conflict, пожалуйста разберитесь. Человеку нужно самому вспомнить, какой агент что делал, где worktree, какие изменения полезны, что уже проверено, почему конфликт возник.

В обслуживаемой среде merge failure возвращается в поток. `MERGE_FAILED` становится статусом, comment, fix-needed work или сигналом Witness/Deacon. Предыдущий результат не исчезает и не подменяется новой попыткой с нуля. Если конфликт можно решить автоматически, work возвращается к исполнителю. Если нельзя, появляется escalation.

Это один из ключевых признаков среды: она не просто запускает исполнителей, а удерживает последствия их работы. Ошибка merge — тоже часть работы, а не исключение из неё.

### Backpressure: зрелая среда умеет сказать «не сейчас»

Когда у проекта несколько зависших веток, легко запустить ещё агентов: один разберёт конфликт, другой обновит тесты, третий перепишет docs, четвёртый проверит frontend, пятый сделает summary. Но если город уже перегружен, это увеличит шум. Параллелизм без capacity ухудшает управляемость.

Gas Town scheduler docs дают полезную фактуру: deferred dispatch, `scheduler.max_polecats`, batch size, spawn delay, convoy integration, capacity/backpressure и safety properties вроде dispatch serialization и atomic scheduling ([Gas Town Scheduler](https://github.com/gastownhall/gastown/blob/main/docs/design/scheduler.md)). Для этой главы не важно подробно объяснять scheduler. Важно другое: зрелое масштабирование включает право среды отложить работу. Не всё, что можно запустить, надо запускать сейчас.

В примере это означает: конфликт backend/migration получает приоритет, frontend остаётся deferred до стабилизации contract, test update ждёт решения по replayed payloads, а Mayor видит очередь с приоритетами, а не двадцать активных вкладок.

### Escalation как честный предел автоматики

Наконец, появляется решение, которое агент не должен принимать сам. Backend contract может сохранить backward-compatible semantics или ввести breaking behavior с migration notice. Оба пути возможны, и выбор зависит от продукта, интеграторов, риска и обещаний API. Автоматический исполнитель может собрать аргументы, но не должен сам решить, какое обещание компания даёт пользователям.

Gas Town escalation docs описывают escalations как случаи, где automated resolution is not possible; они severity-routed, tracked as beads, имеют stale detection и re-escalation. Поток проходит от Agent к Deacon, затем к Mayor и при необходимости к Overseer; chain tracked via bead comments ([Gas Town Escalation Protocol](https://github.com/gastownhall/gastown/blob/main/docs/design/escalation.md)). Это хорошая форма человеческого входа: человек получает не сырой сигнал «я не уверен», а структурированную проблему, связанную с work items, попытками восстановления, вариантами и блокировками.

Здесь важно не романтизировать автоматику. Сильная среда не та, где человек никогда не нужен. Сильная среда та, где человеку не приходится быть диспетчером всего, но где его суждение вызывается в правильных местах и с достаточным контекстом.

## Видимость без действия ещё не обслуживает поток

У обслуживаемой среды есть два разных режима: читать состояние и менять состояние. Их нельзя смешивать.

Чтение даёт человеку и агентам обзор: problem feed, список ready work, открытый bead, dependencies, gates, PR checks, trace, session log, merge failure, current role context через `gt prime` или work context через `bd prime`. Это защищает от слепоты. Но если среда только показывает панель состояния, человек всё равно остаётся диспетчером: он должен вручную решить, кого будить, что перезапускать, что закрывать, что считать ready, что эскалировать.

Действие меняет поток: создать work item, добавить dependency, открыть или закрыть gate, `pin`/`hook` work, `sling` задачу в rig, defer dispatch, re-sling orphaned work, записать `MERGE_FAILED`, создать fix-needed work, acknowledge escalation, re-escalate stale item, закрыть работу. В агентской среде эти операции должны быть привязаны к durable state. Иначе действие снова превращается в свободное вмешательство в чат: агент что-то сделал, но проект не знает, что изменилось.

Поэтому правильная формула не «нужна панель состояния» и не «нужен автономный агент». Нужна связка: видимость состояния плюс допустимое действие над этим состоянием. Видимость без действия — наблюдение хаоса; действие без состояния — хаотичная автоматика. Обслуживание потока начинается там, где они соединены.

## Что именно даёт обслуживаемая среда

После прохождения такого цикла проект получает не просто набор ответов агентов. Он получает рабочую картину.

В примере с payment webhook это означает, что `B-101` не просто «где-то делался backend-agent’ом», а имеет состояние: hooked, stalled, recovered, merge-ready или merge-failed. `B-104` не просто содержит черновик документации, а возвращает вывод о replayed payloads в общий граф. `B-105` не становится ready, пока не прошёл CI gate и пока тесты не учли новый риск. `B-103` не идёт в merge до стабилизации backend contract. `B-106` видит не обрывки отчётов, а путь связанных работ: что было сделано, что блокировалось, где была неудача merge, где потребовалось человеческое решение.

Такой проект знает:

- какие work items созданы;
- какие зависимости закрыты;
- что находится на hook;
- что зависло;
- что осиротело;
- где merge failed;
- какие gates ещё блокируют ready;
- где нужен human decision;
- какие полезные выводы вернулись из локальных сессий в Beads/PWG;
- какие ветки можно продолжать;
- что не надо запускать сейчас из-за capacity.

Это и есть предмет главы. В агентской разработке появляется новая инфраструктурная потребность: обслуживать движение рабочих объектов через множество исполнителей и площадок. Если такой среды нет, даже хороший persistent work graph превращается в базу, которую человек вручную сопровождает. Если такая среда есть, человек видит не все подробности всех агентов, а рабочую картину проекта: где поток движется, где стоит, где сломался, где требует решения.

Можно представить этот слой как соединение трёх этажей.

Первый этаж — durable work state: Beads/PWG, issues, dependencies, gates, status, comments, `bd prime`, pin/hook. Второй этаж — рабочая география: rigs, worktrees, branches, PRs, checks, convoys. Третий этаж — обслуживание потока: Mayor, Witness, Refinery, Deacon, Dogs, scheduler, escalation, problem feed. Только вместе они превращают множество агентских действий в поток, с которым проект может работать.

## Не только Gas Town: те же функции в других историях

Gas Town даёт самый собранный язык для этой главы, но потребность в обслуживании потока видна не только там.

У Jökull Sólberg маленькая версия той же проблемы появляется вокруг PR. После `push` работа не заканчивается: нужно дождаться CI, разобрать Greptile comments, запустить `codex review --base main`, решить, что исправить, что отклонить, что эскалировать, повторить проверки и дойти до состояния ready to merge. В “Babysitting PRs With Claude Code” он описывает `/babysit-pr` как процедуру сопровождения PR, а в “How I Use Claude Code” — более широкий режим нескольких рабочих потоков, GitHub issues, worktrees, context management и specialized agents ([Babysitting PRs With Claude Code](https://www.solberg.is/babysit-pr); [How I Use Claude Code](https://www.solberg.is/how-i-use-claude-code)). Это не Gas Town, но это тот же сдвиг: человек не должен быть живым таймером между CI, review comments и повторными исправлениями.

У Stripe Minions похожая логика видна на корпоративном уровне. Снаружи запуск может выглядеть как Slack message и emoji reaction; внутри есть route signal, isolated devbox, branch, tools, анализ кода, tests, commit, PR и human review. В ChatPRD-разборе Stripe Minions эта сцена показана как переход от Slack-сообщения к PR через эмодзи-реакцию и подготовленную dev environment, а связанная workflow page раскладывает steps: Slack idea, emoji trigger, isolated cloud environment, agent loop, PR review ([How Stripe’s AI Minions Ship 1,300 PRs Weekly from a Slack Emoji](https://www.chatprd.ai/how-i-ai/stripes-ai-minions-ship-1300-prs-weekly-from-a-slack-emoji); [workflow page](https://www.chatprd.ai/how-i-ai/workflows/how-to-automate-code-generation-from-a-slack-message-into-a-pull-request)). Для главы X отсюда важен не масштаб PR, а платформа вокруг агента: чем автономнее запуск, тем больше обычной инженерной инфраструктуры должно его удерживать.

Shopify Roast показывает соседнюю форму: workflow as code для AI steps. В статье Shopify Engineering Roast представлен как structured AI workflow framework; открытый README показывает Ruby DSL с `cmd`, `agent`, `chat`, `ruby`, `map`, `repeat`, named outputs and providers; tutorial examples показывают chaining cogs, session resumption, collections and iterative workflows ([Introducing Roast](https://shopify.engineering/introducing-roast); [Shopify/roast README](https://github.com/Shopify/roast/blob/main/README.md)). Roast не заменяет city-level service, но помогает увидеть другой важный принцип: агентская процедура должна быть исполняемым объектом, а не цепочкой устных пожеланий модели.

У Mae Capozzi похожая потребность выражена через worktrees, traces, timeouts, CI, observability and platform constraints. В “How I Use Claude Code to Reduce Toil as a Platform Engineer” она описывает использование Claude Code для рутинной платформенной работы, CI/test PRs, dependency reviews, instrumentation before deploy and cleanup/deletion work ([Mae Capozzi](https://maecapozzi.com/blog/ai-powered-toil-reduction-platform-engineering)). Когда агентских PR и веток становится много, мало получить финальный ответ. Нужно видеть жизненный цикл, время ожидания, зависимые проверки, путь выполнения и место, где работа застряла.

Эти истории не нужно превращать в четыре дополнительных кейса внутри главы. Они подтверждают переносимость проблемы. Gas Town/Beads дают наиболее яркую форму, но за ними стоит более общий сдвиг: агентская разработка переходит от одиночной сессии к обслуживаемой рабочей среде.

## Чего такая среда не даёт

Важно закрыть главу не рекламой Gas Town и не обещанием, что городская среда решит все проблемы. Даже если Beads/PWG удерживает work state, Gas Town-like слой обслуживает поток, scheduler не даёт перегрузить систему, escalation возвращает решения человеку, а merge failures не теряются, остаётся следующий вопрос: можно ли доверять результату?

Сами текущие источники не позволяют писать о Gas Town/Beads как о зрелом стандарте. Beads docs прямо фиксируют ограничения: large teams, real-time collaboration и cross-repo use требуют осторожности; multi-clone races and sync/recovery concerns остаются инженерной реальностью ([Beads Architecture](https://gastownhall.github.io/beads/architecture)). Авторская статья Steve Yegge описывает Gas Town как frontier/hands-on/expensive режим, а не как спокойную готовую платформу для любой команды ([Welcome to Gas Town](https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04)). Поэтому ценность Gas Town/Beads для этой главы не в том, что «все будут использовать именно это», а в том, что они называют и собирают правильный класс механизмов.

`B-105` мог пройти CI gate, но это ещё не доказывает, что тесты действительно покрывают replayed webhook payloads. `B-104` мог пройти human gate, но это ещё не значит, что документация не содержит двусмысленности. `B-101` мог быть merged, но это ещё не доказывает, что backward compatibility сохранена. `B-106` может собрать итоговый review, но итоговый review должен опираться на проверочный материал, а не только на статусы потока.

Это граница с главой XI. Глава X показывает, как работа доходит до review/merge path в управляемом состоянии: не потеряв зависимости, gates, failures, partial results, escalations и human decisions. Но сама организация потока не доказывает достаточность результата. Следующий вопрос — какие проверки, артефакты, логи, диффы, тесты, review decisions и другие материалы делают результат заслуживающим доверия и пригодным для передачи дальше.

В этом месте полезно вернуться к началу. Агентская разработка усложняется не потому, что модели становятся «слишком автономными» сами по себе. Она усложняется потому, что работа перестаёт быть одной линией. Как только появляется много рабочих потоков, проекту нужна инфраструктура, которая удерживает их вместе. Не каждый проект обязан буквально построить Gas Town. Но каждый проект, который всерьёз использует много агентских действий, столкнётся с тем же набором функций: durable work state, routing, рабочие площадки, lifecycle observation, recovery, queues, backpressure, merge path, escalation и человеческая поверхность управления.

Без этого параллелизм остаётся шумом. С этим он начинает становиться потоком.
