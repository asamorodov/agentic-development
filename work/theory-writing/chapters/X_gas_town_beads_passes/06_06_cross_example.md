# 06 — Сквозной пример для главы

## Задача примера

Пример нужен не как иллюстрация Gas Town сам по себе, а как сквозная ситуация, через которую можно провести все различения главы: durable work state, несколько рабочих площадок, назначение работы, зависание, нарушение рабочего контракта, возврат результата, сервисные роли, backpressure, эскалация и граница с проверкой результата.

Лучше использовать один пример на протяжении главы, а не несколько мелких. Он должен быть достаточно предметным, но не настолько доменно специфическим, чтобы читатель ушёл в детали конкретного продукта.

## Исходная ситуация

Команда ведёт продукт, где нужно изменить обработку платежных событий. Изменение выглядит цельным, но на практике распадается на несколько связанных работ:

1. В backend нужно изменить контракт webhook handler и привести старые статусы к новой модели.
2. В frontend нужно обновить экран истории платежей, чтобы новые статусы не выглядели как ошибки.
3. В базе нужна миграция для новой колонки `settlement_state` и обратного заполнения старых записей.
4. В документации API нужно обновить раздел для интеграторов.
5. В тестовом контуре нужно добавить regression checks для старых и новых webhook payloads.

Человек формулирует цель не как «пусть один агент всё сделает», а как набор work items в durable state. На уровне Beads/PWG появляются связанные issues, зависимости и gates:

- `B-101`: backend webhook contract;
- `B-102`: database migration;
- `B-103`: frontend status rendering;
- `B-104`: API docs update;
- `B-105`: regression checks;
- `B-106`: final integration review.

У `B-103` есть dependency на `B-101`, потому что frontend должен знать финальные статусы. У `B-106` есть dependencies на все рабочие ветки. У `B-105` есть gate на CI run или GitHub check. У `B-104` есть human gate: maintainer должен подтвердить, что публичная формулировка API не ломает обещание интеграторам.

На этом уровне уже есть persistent work graph: работа стала объектами, их можно увидеть, продолжить, передать, закрыть, разблокировать. Но глава X начинается там, где этого уже мало.

## Первый запуск: кажется, что параллелизм работает

Mayor или maintainer распределяет работы по нескольким площадкам:

- backend rig получает `B-101` и `B-102`;
- frontend rig получает `B-103`, но пока видит dependency;
- docs rig получает `B-104`;
- test rig получает `B-105`;
- final review остаётся ожидающим `B-106`.

Часть работ можно `pin` или `hook` на конкретных исполнителей. Для backend-ветки запускается polecat, который берёт `B-101`; для docs — другой агент; для тестов — третий. Снаружи всё выглядит хорошо: агенты заняты, worktrees созданы, статусы меняются, в чатах появляются отчёты.

Именно здесь возникает соблазн назвать задачу решённой: «мы распараллелили работу». Но через некоторое время человек видит не прогресс, а шум.

## Сбой 1: claim завис и перестал быть понятным

Backend polecat взял `B-101`, открыл рабочую площадку, изменил часть кода и оставил промежуточный отчёт. Потом сессия прервалась или ушла в петлю. В обычном чате это выглядело бы так: где-то есть вкладка, где-то есть частичный diff, где-то был ответ модели, но никто точно не знает, надо ли ждать, перезапускать, разбирать вручную или считать work item свободным.

В Gas Town-like среде это должно стать видимым состоянием, а не догадкой человека. Witness или patrol замечает, что работа на hook не движется, polecat не ведёт её по ожидаемому lifecycle, либо нарушается GUPP: если work is on hook, она должна выполняться. Возникает событие уровня `GUPP_VIOLATION` или близкое к нему. Если work item потерял владельца, появляется ситуация `ORPHANED_WORK`.

Смысл не в названии события. Смысл в том, что зависание перестало быть субъективным ощущением maintainer’а и стало объектом среды. Его можно записать в Beads, показать Mayor/Deacon, вернуть work item в очередь, переслать другому исполнителю или поднять escalation.

## Сбой 2: агент сделал полезный вывод, но не вернул его в состояние

Docs-agent, работая над `B-104`, обнаруживает, что публичная документация не должна просто перечислить новые статусы. Нужно добавить предупреждение: старые webhook payloads могут приходить повторно, и интегратор не должен считать их новой транзакцией. Это хороший вывод, возможно даже главный для безопасного релиза.

Но агент оставляет его только в локальном отчёте: «I noticed we should warn about replayed payloads». Он не обновляет связанный work item, не создаёт dependency для tests, не добавляет note в `B-105`, не открывает question для backend. В обычной агентской работе такой вывод легко теряется: человек мог не дочитать отчёт, другой агент его не увидит, тестовая ветка продолжит проверять только happy path.

В обслуживаемой среде результат должен быть возвращён в durable state. Это может произойти разными способами:

- агент сам добавляет comment/note в `B-104` и создаёт linked issue для replayed payload tests;
- сервисная роль, просматривающая отчёты, вытаскивает этот вывод и добавляет его в Beads;
- Mayor или Deacon получает сигнал: полезное знание осталось вне графа;
- test rig получает новый dependency или уточнение к `B-105`.

Здесь видно отличие главы X от простой идеи «хранить задачи». Задача уже была. Потерялось не существование задачи, а перенос знания из локальной сессии в общий контур проекта.

## Сбой 3: работа формально почти готова, но gate ещё не разрешён

Test-agent по `B-105` добавляет regression checks и сообщает, что всё зелёное. Но в durable graph у `B-105` есть gate на конкретный CI run, а у `B-104` — human gate на публичную формулировку. Если среда плохо устроена, maintainer видит «тесты готовы» и «доки готовы» и преждевременно считает проект близким к завершению.

Beads-like gate нужен, чтобы work item не попадал в `ready` раньше времени. Это не доказательство качества результата в смысле главы XI, но это дисциплина потока: пока внешнее условие не выполнено, работа не должна выглядеть завершённой для следующих этапов.

В примере это означает:

- `B-105` не разблокирует `B-106`, пока CI run не прошёл;
- `B-104` не разблокирует финальный review, пока человек не подтвердил текст для интеграторов;
- frontend `B-103` не должен мержиться до финального backend contract или explicit compatible stub.

В этой точке X граничит с XI. Глава X может сказать: gate удерживает поток от преждевременного продвижения. Но вопрос, достаточно ли тесты покрывают replayed payloads, относится уже к проверочному материалу следующей главы.

## Сбой 4: merge failed, но результат не должен исчезнуть

Refinery пытается слить backend ветку по `B-101` и получает `MERGE_FAILED`: параллельная миграция `B-102` поменяла соседний слой. В плохой среде это превращается в ещё один шумный чат: «merge conflict, please resolve». Maintainer должен сам вспомнить, какой agent что делал, где worktree, какие изменения полезны, что уже проверено.

В обслуживаемой среде merge failure возвращается в поток:

- `B-101` получает structured comment или status;
- связанный worktree/rig остаётся доступен;
- Refinery сообщает Witness или Deacon;
- новая работа по разрешению конфликта может быть поставлена в очередь;
- предыдущий полезный результат не исчезает и не подменяется новой попыткой «с нуля»;
- если конфликт неразрешим автоматически, возникает escalation.

Здесь важна не сама магия merge. Важна способность среды не терять частичный результат и не заставлять человека вручную реконструировать всю историю из вкладок, логов и сообщений.

## Сбой 5: backpressure — нельзя просто запустить ещё пять агентов

Maintainer замечает, что backend и docs требуют дополнительной проверки, frontend ждёт контракт, tests надо расширить под replayed payloads. Возникает соблазн запустить ещё несколько агентов: один на конфликт, один на docs, один на tests, один на frontend, один на review checklist.

Но если город уже загружен, это может только ухудшить ситуацию. Scheduler/backpressure нужен, чтобы среда могла сказать: часть работы будет deferred, часть пойдёт в очередь, часть останется привязанной к convoy, новая сессия не стартует, пока нет capacity. Это дисциплина зрелого параллелизма: масштабирование не равно бесконечному запуску новых сессий.

В примере это может выглядеть так:

- конфликт `B-101/B-102` получает приоритет выше frontend polish;
- `B-103` остаётся deferred до стабилизации backend contract;
- `B-105` получает уточнение по replayed payloads, но не запускает второй test-agent, пока первый не вернул состояние;
- Mayor видит не список хаотичных просьб, а очередь с приоритетами и зависимостями.

## Сбой 6: автоматике нужен предел и structured escalation

Допустим, после нескольких попыток система видит, что backend contract допускает два несовместимых решения: сохранить старую семантику webhook status ради интеграторов или ввести новый breaking behavior с migration notice. Agent может предложить варианты, но не должен сам принимать продуктово-архитектурное решение.

Здесь escalation полезен как форма признания предела автоматики. Вопрос поднимается не фразой «я не уверен», потерянной в чате, а escalation bead с severity, источником, связанными work items, описанием уже испробованных вариантов и маршрутом Deacon → Mayor → человек.

Человеку нужно принять решение, но его вход уже изменился. Он не babysitter каждой сессии. Он получает структурированную точку вмешательства: какие work items затронуты, что блокируется, какие варианты есть, какие gates не могут закрыться без решения.

## Возврат результата в общее состояние

После решения человека backend contract фиксируется. Тогда среда должна провести обратное движение:

1. Обновить `B-101` с выбранным решением.
2. Разблокировать или пересоздать часть `B-103`, потому что frontend теперь знает финальные статусы.
3. Добавить в `B-105` regression checks для replayed payloads.
4. Обновить `B-104` и пройти human gate.
5. Повторить merge через Refinery.
6. Оставить в `B-106` не только «всё сделано», а путь: какие work items закрыты, какие gates прошли, где были failures, как они были resolved.

Это всё ещё не финальное доказательство качества. Но проект снова стал видимым как целое. Человек может смотреть не на набор чатов, а на состояние работы.

## Как провести пример через главу

### Вступление

Показать исходную ситуацию: пять связанных работ вокруг платежных событий. На первый взгляд они идеально подходят для параллельного агентского выполнения.

### Переход к проблеме

Показать, что параллелизм быстро создаёт не только скорость, но и новые виды потери управления: зависший claim, локальный вывод вне состояния, premature ready, failed merge, перегрузка, неразрешимое решение.

### Введение Beads/PWG

Показать, что durable graph уже решает первый уровень: задачи, зависимости, gates, comments, routing, `bd prime`, pin/hook. Но он сам по себе ещё не обслуживает весь город.

### Введение Gas Town

Показать роли как ответы на конкретные сбои:

- Mayor видит и распределяет работу;
- rigs дают рабочие площадки;
- polecats/crew исполняют;
- Witness наблюдает жизненный цикл;
- Refinery пытается вернуть результат через merge;
- Deacon/Dogs обслуживают здоровье среды;
- Scheduler удерживает capacity;
- Escalation возвращает нерешаемое человеку.

### Сопоставление с историями

Коротко провести параллели:

- Jökull Sólberg показывает маленькую форму babysitting PR: работа требует наблюдения и возврата в merge-ready state.
- Stripe Minions показывает enterprise-level routing/platform/checks/devboxes: много работ требует платформенного слоя.
- Shopify Roast показывает executable workflow, где процесс не просто написан, а исполняется с состояниями.
- Mae Capozzi показывает работу через ветки/worktrees, traces, timeout и контролируемую передачу между шагами.

Эти истории не надо превращать в отдельные кейсы. Они нужны как подтверждение: потребность в обслуживании потока возникает не только в Gas Town.

### Финальный мост к XI

Закрыть пример так: после всех восстановлений `B-106` может быть готов к review, но глава X ещё не отвечает, достаточно ли изменения проверены. Она отвечает на вопрос, как работа дошла до review в управляемом состоянии, не потеряв важные выводы, зависимости, failures и решения. Следующая глава должна разобрать, какие материалы делают результат заслуживающим доверия.

## Мини-версия примера для вставки в текст

Если в основной главе понадобится короткий вариант, его можно сжать так:

Команда распараллеливает изменение платежных webhook: backend contract, migration, frontend rendering, API docs, regression tests. Каждая часть становится work item в durable graph; часть работ можно запускать параллельно, часть ждёт dependencies и gates. Через некоторое время виден типичный сбой масштаба: backend claim завис, docs-agent нашёл важный вывод о replayed payloads, но не вернул его в состояние, tests выглядят готовыми до прохождения CI gate, merge backend ветки падает из-за миграции, а новые агенты только увеличивают шум. Beads удерживает work items, зависимости, gates, pin/hook и контекст; Gas Town-like среда добавляет Mayor, rigs, Witness, Refinery, Deacon, scheduler и escalation. В результате проект видит не хаотичный набор сессий, а обслуживаемый поток: что зависло, что осиротело, что вернулось в очередь, что не прошло merge, что требует решения человека и какие work items снова готовы к продолжению.
