# P02 — карта входного корпуса для главы VII

## Главная линия корпуса

Входной корпус главы VII уже достаточно богат; задача не в том, чтобы пересказать его весь, а в том, чтобы выбрать из него один устойчивый ход. Глава должна строиться вокруг перехода от линейной передачи контекста к графу продолжения работы. Поэтому материал нужно читать не как каталог методов, а как несколько пересекающихся слоёв:

1. **теоретическая граница PWG** — что такое долговечное состояние работы и чем оно не является;
2. **практический якорь Beads** — какие свойства уже материализованы в реальной системе;
3. **соседние механизмы** — issue trackers, process profiles, runtime, durable execution, Gas Town, CRDT/STORM-подобная координация;
4. **story anchors** — где в живых историях виден тот же сбой: PR ждёт CI/review, агент теряет контекст, platform wrapper должен показать trace, harness должен вернуть проверяемое состояние;
5. **визуальный слой** — один сильный локальный asset по Beads/PWG, возможно одна дополнительная синтетическая схема, если черновик покажет необходимость.

## Материалы, которые должны питать главу напрямую

### A4 — граница рабочего состояния

`A4_persistent_work_graph_boundary.md` даёт главе главный отрицательный контур: отчёт «сделано много» не равен состоянию работы. Из него нужно перенести не текст целиком, а несколько опорных различений:

- сессия, лог чата, summary и handoff не вычисляют готовность;
- обычный issue tracker видит задачи и отношения, но не обязательно знает состояние источников, compact prime, основания закрытия и восстановление после сжатия контекста;
- PWG нужен как ответ на вопрос продолжения: что следующий исполнитель может делать сейчас, что заблокировано и кто имеет право закрыть узел;
- состояние источника тоже должно быть состоянием работы: `found`, `opened`, `read`, `used`, `rejected`, `reopen_required` и похожие статусы не должны исчезать в рабочей заметке.

A4 также содержит центральный визуальный кандидат `beads-task-graph-memory.svg`. Его нужно рассматривать как сильный готовый asset, а не как схему, которую надо пересказать словами.

### B2 — глубокий механизм PWG

`B2_pwg_contribution.md` должен стать главным донором внутренней механики: work item, dependencies, readiness, owner/claim, gate, evidence, handoff/prime, recovery и cleanup. Его риск — перегрузить главу словарём графа и сделать текст похожим на implementation sketch. Из B2 нужно взять механизм, но переписать его через обычную русскую техническую прозу и сквозной пример.

Особенно важны:

- готовность вычисляется из графа, а не из самооценки агента;
- `claim` или `pin` защищают параллельную работу от молчаливого дублирования;
- `gate` — не просьба в prompt, а долговечное ожидание, которое блокирует переход;
- `prime` нужен не как «краткое содержание всего», а как компактный ввод в актуальное состояние узла;
- cleanup закрывает не только выполнение, но и само рабочее состояние.

### C2 — граница с процессными профилями

`C2_pwg_to_process_profiles.md` нужно использовать как мост к VIII, а не как самостоятельный слой главы. Его функция — не дать главе VII захватить GSD/BMAD/Gas Town. PWG показывает, где находится работа и какие узлы готовы, заблокированы или ждут человека. Процессный подход говорит, каким способом эту работу вести: какая фаза, роль, проверка, документ или recovery move сейчас уместны.

В главе VII это должно появиться ближе к финалу: `restoration packet` как проверка PWG уже подводит к следующему вопросу — не просто «что известно о работе?», а «каким режимом её теперь продолжать?».

### C3 — граница с evidence и принятием

`C3_pwg_to_evidence.md` нужен как источник осторожности вокруг `done`, `gate` и оснований закрытия. Глава VII не должна становиться главой об evidence, но она обязана показать: узел нельзя закрыть только потому, что агент сообщил об успехе. Для закрытия нужен материал, достаточный для конкретного перехода: тест, CI, review, source audit, trace, человеческое решение или другой проверяемый результат.

Важно не перегрузить терминологию. `Evidence` не стоит автоматически переводить одним словом. В публичном тексте лучше выбирать контекстные формулы: `основание для закрытия`, `материал для принятия`, `результат проверки`, `проверяемое подтверждение`.

### C4 — граница с runtime и durable execution

`C4_execution_runtime_to_pwg.md` даёт главе одну из главных защит от смешения слоёв. Runtime, workflow engine, devbox, worktree, sandbox, checkpoint, thread, trace и durable execution могут показать, где остановился запуск и какие действия он успел совершить. Но они не отвечают сами по себе, какая работа существует, кто ей владеет, какой blocker ещё открыт, какое gate-условие нужно закрыть и какое основание достаточно для принятия.

Из C4 нужно взять язык различения:

- состояние запуска ≠ состояние работы;
- trace ≠ право продолжать;
- checkpoint ≠ закрытый work item;
- worktree изолирует запись, но не решает смысловое владение узлом;
- durable runtime может восстановить процесс, но не заменяет restoration packet для следующей сессии или человека.

## Атлас как concept-first baseline

`work/atlas/articles/persistent_work_graph.md` — главный baseline главы. Его нельзя пересказывать подряд, потому что глава должна стать частью общей теории, а не дублировать статью Атласа. Но из статьи нужно сохранить её ясный контракт:

- PWG — устойчивое состояние работы вне сессии;
- Beads — практический якорь, а не предмет главы;
- Gas Town, process profiles, durable execution, CRDT/STORM и issue trackers — соседние слои;
- минимальный узел существует только тогда, когда поля меняют следующий допустимый шаг;
- restoration/prime и cleanup — не вспомогательные украшения, а часть жизненного цикла узла.

`persistent_work_graph_source_usage.md` и `persistent_work_graph_theory_links.md` нужны для проверки provenance и связи с общей теорией. Их не надо превращать в видимый слой главы, но они должны предотвратить две ошибки: вставку ссылок на внутренние досье вместо первичных источников и повторение уже отвергнутых или ограниченных источников.

## Досье PWG как quarry, а не структура главы

`PERSISTENT_WORK_GRAPH_MECHANISM_DOSSIER.md` — самый фактически плотный вход. Его нужно использовать для восстановления деталей, но не для композиции главы. В нём есть несколько полезных групп материала.

### Beads как практический якорь

Главные первичные источники:

- Beads documentation / architecture / core concepts;
- `bd ready`, `bd blocked`, `bd gate`, `bd prime`;
- Claude Code и Codex integrations;
- multi-agent coordination, pin/claim, routing, recovery, troubleshooting;
- Dolt-backed state и release/recovery дисциплина.

Для главы важны не все команды, а свойства: версионированное состояние, вычисляемая готовность, долговечные ожидания, компактное восстановление, координация нескольких агентов и операционная цена persistent state.

### Обычные issue-графы как нижняя граница

GitHub issue dependencies, GitHub sub-issues и Linear issue relations нужны как внешний baseline. Они показывают, что blocked/blocking, hierarchy, progress и relations уже существуют в обычных системах. Это защищает главу от ложной новизны. Но их нужно использовать как контраст: PWG наследует эту форму, но добавляет агентно-важные состояния — source state, prime, gates, основания закрытия, восстановление после compaction и правила передачи.

### Taskmaster как лёгкая альтернатива

Taskmaster полезен как напоминание, что POC PWG не обязан начинаться с Dolt/SQL. Файловый `tasks.json`, dependencies, `testStrategy`, `tm next`, clusters, tags и loop показывают более лёгкую точку в пространстве решений. В главе это можно использовать кратко: PWG — не конкретное хранилище, а набор поведенческих свойств. Но Taskmaster не должен стать вторым обзором инструмента.

### Durable execution как соседний слой

LangGraph, Temporal, DBOS, Restate и Pydantic AI durable execution нужны только для границы. Они помогают сказать: можно иметь checkpoint/resume без графа работы; можно иметь граф работы без durable runtime; в сильной системе эти слои соприкасаются, но отвечают на разные вопросы.

### Негативная фактура

Досье содержит особенно ценный материал против гладкого тезиса «persistent state всё решит»: Beads release-gates, admin cleanup/compact failures, sandboxed environment issues, heartbeat bloat, HN-обсуждение о merge conflicts/accountability, Gas Town как развивающаяся система с repair/telemetry/pressure mechanics. Это нужно не перегружать, но глава должна хотя бы один раз показать цену устойчивого графа: он делает работу восстановимой, но сам становится инфраструктурой, которую нужно чинить, чистить, мигрировать и защищать от устаревания.

## Gas Town как соседняя граница

`gas_town.md` и `GAS_TOWN_METHOD_DOSSIER.md` не должны питать основную механику главы VII. Их роль — показать верхний организационный слой: Town/Rig, роли, очереди, сервисные агенты, backpressure, recovery, наблюдаемость, mail, рабочие площадки. Для главы VII это важно только как граница: PWG — нижняя опора продолжимости work items; Gas Town — организация множества агентов и потоков поверх этой опоры.

Риск дублирования высокий: если взять из Gas Town слишком много ролей и терминов, глава VII потеряет предмет и начнёт писать будущую главу X. В VII достаточно одного-двух контрастов: Beads/PWG может существовать как память одного агента или небольшого набора узлов; Gas Town возникает, когда вокруг графа появляется городская операционная среда.

## Истории как точечные якоря

Истории не должны пересказываться в главе. Их функция — дать узнаваемые сцены, где абстрактная проблема PWG становится практической.

### Jökull Sólberg

Главный якорь для главы VII. Его `/babysit-pr` превращает PR в сопровождаемый объект: CI, Greptile, Codex review, повторные исправления, Fix/Dismiss/Escalate и критерий готовности к слиянию. Для PWG важна не сама slash command, а форма работы: PR живёт через ожидания, проверки и решения; человек не должен быть живым таймером между внешними сигналами; агент не должен превращать любой сигнал в приказ.

В главе Jökull хорошо подходит к сквозному примеру billing/API: PR или API-изменение имеет несколько сигналов разного статуса и не может быть закрыто простой фразой `done`.

### Mark Erikson

Mark полезен для линии «смысл вышел за пределы локального контекста». Его история показывает, что внешнее состояние, документация, изменения экосистемы, replay/runtime-каналы и практическая проверка могут быть важнее того, что агент держит в текущей сессии. Для VII это вторичный якорь: он помогает показать, почему compact prime и source state важнее общего summary.

### HumanLayer

HumanLayer нужен как соседний якорь по context budget, harness expectations, gates и разделению research/plan/implement. Для VII полезно не пересказывать harness, а взять принцип: когда контекст дорогой и действие может иметь последствия, рабочее состояние должно быть намеренно собрано, ограничено и проверяемо.

### Mae Capozzi

Mae полезна для platform-wrapper взгляда: traces, `InstructionsLoaded`, `TRACEPARENT`, Honeycomb, team-level observability, Linear tickets, PR, testing and human review. Для VII это не evidence-глава и не observability-глава; но Mae помогает показать, что «работа видима» не равно «работа закрыта». Trace показывает фазу и место отказа, но PWG должен связать этот след с узлом, gate, владельцем и основанием принятия.

## Риски дублирования

### Дублирование с Атласом

Если глава пойдёт по структуре статьи `persistent_work_graph.md`, она станет повтором Атласа. Нужно взять из Атласа контракт и понятия, но построить главу вокруг жизненного перехода: почему после нескольких сессий и проверок summary перестаёт быть рабочим состоянием.

### Дублирование с главой VI

VI уже объясняет проектный контекст как интерфейс агента: rules, skills, MCP, subagents, hooks and route selection. VII не должна снова объяснять, как агент получает инструкции или выбирает инструментальный маршрут. Она должна показать, что выбранный маршрут должен оставить состояние работы.

### Дублирование с главой VIII

VIII будет о способе продолжения работы через процессные подходы. VII должна остановиться на том, что граф показывает состояние узла. Нельзя заранее раскрывать GSD/BMAD как полноценные методологии.

### Дублирование с главой IX

IX будет о runtime, permissions, sandbox, worktree, hooks and harness. В VII runtime нужен только как контраст: среда исполнения производит следы и ограничения, но не заменяет граф работы.

### Дублирование с главой X

Gas Town соблазнительно тянет главу к многоагентной организации. Это нужно удержать: глава VII — не о городе агентов, а о том, как отдельная работа остаётся продолжимой.

### Дублирование с XI–XII

Evidence and authority должны появиться только через gate/done. Полная рамка принятия, права закрыть работу и качества свидетельств принадлежит более поздним главам.

## Где нужен внешний добор

Внешний добор нужен точечно, не как новый исследовательский слой.

1. **Beads current docs и CLI pages** — проверить, не устарели ли детали `bd ready`, `bd blocked`, `bd gate`, `bd prime`, integrations, recovery, troubleshooting and sandbox mode.
2. **GitHub issue dependencies / sub-issues** — использовать как current baseline обычных issue-графов.
3. **Linear issue relations** — использовать как второй baseline для blocked/blocking/related/duplicate.
4. **Taskmaster docs** — при необходимости уточнить лёгкую файловую модель task graph и не спутать её с Beads.
5. **Durable execution sources** — брать только если в черновике остаётся риск смешения PWG и runtime.
6. **Beads/Gas Town release notes or issues** — можно использовать для одной честной негативной сцены о цене persistent state, если глава станет слишком гладкой.

Не нужен широкий поиск по `persistent work graph` ради похожих терминов, если найденные источники не добавляют к конкретным границам главы. Не нужно искать десятки workflow/task tools: это размоет главу.

## Визуальные входы

Основной visual input:

- `content/assets/theory-images/beads-task-graph-memory.svg` — local image asset, вероятный центральный visual anchor.

Возможные дополнительные figure ideas, только если черновик потребует:

- linear summary → restoration packet → graph-backed continuation;
- anatomy of gate: blocked transition, resolver, required material after resolution, fallback/timeout/manual override;
- PWG vs runtime boundary: work node / execution run / evidence package / acceptance decision.

Но визуальный слой не должен размножаться ради полноты. Для VII одна центральная фигура может быть сильнее трёх вспомогательных схем.

## Итоговое решение по корпусу

Глава VII должна опираться на A4+B2 как основной внутренний синтез, использовать C2/C3/C4 как boundary guards, брать статью Атласа PWG как concept baseline, досье PWG как источник фактических деталей и внешних ссылок, а истории — как точечные практические сцены. Gas Town, process profiles, runtime и evidence нужны не как конкурирующие предметы, а как границы, через которые читатель понимает собственное место PWG в жизненном цикле изменения.
