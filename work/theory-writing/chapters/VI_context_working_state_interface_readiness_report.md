# Chapter VI — readiness report

Статус: готово как итоговый текст пакета после P30.

## Что получилось

Глава VI отвечает на свою плановую задачу: объясняет «контекст» не как объём токенов и не как историю чата, а как проектный интерфейс агента. В центре удержаны три практических вопроса:

1. что в проекте является устойчивым правилом;
2. где находится текущее состояние работы;
3. каким маршрутом агент должен действовать в данной фазе.

Текст не стал каталогом инструментов. `AGENTS.md`, `CLAUDE.md`, Kiro Steering/Specs/Powers/Hooks/Subagents, Codex Agent Skills, Claude Skills/Hooks/Subagents/MCP, BMAD, GSD, Spec Kit, Matt Pocock skills, Ronacher, Stripe Minions и Mark Erikson используются как опоры для этих различий. После ручной правки раздел о skills раскрывает их как повторяемые процедуры проекта, а не как один пункт в списке возможностей агента.

## Границы

Граница с главой V удержана: спецификационные методы не пересказываются заново, а показываются как носители правил и состояния.

Граница с главой VII удержана: Persistent Work Graph появляется только как следующий ответ на предел файлового состояния, без раскрытия полной модели.

Граница с главой IX удержана: hooks, MCP, permissions и execution environment названы только там, где они нужны для понимания проектного интерфейса. Sandbox, approvals, threat model, durable execution и runtime safety не раскрываются.

## Источники

Основные технические утверждения снабжены ссылками рядом с местом введения механизма. Дополнительный внешний поиск перед завершением не нужен: новых неподтверждённых внешних механизмов в финальных проходах не добавлялось.

## Визуальный материал

В текст вставлена одна синтетическая схема `fig-vi-project-interface-layers`. Она подходит для текущей версии. Перед публикацией можно заменить ASCII-схему на SVG, но содержательно менять её не нужно.

## Готовность

Текст готов для включения в набор глав как no-stage result. Возможная следующая работа — не содержательное добирание, а обычная редакторская сборка с соседними главами: проверить единый стиль заголовков, взаимные переходы V→VI→VII и общий словарь терминов.


## Ручная правка раздела о skills

После замечаний о недостаточном раскрытии skills раздел `Skills: повторяемые процедуры как часть проекта` расширен. В нём объясняется, зачем skill нужен, как он устроен без привязки к конкретной раскладке Claude/Codex, как развивается жизненный цикл skill и почему библиотеки skills становятся важной частью агентской разработки.


## Дополнительная правка skills после внешнего поиска

Раздел о skills после повторного поиска источников расширен ещё раз. Теперь он не только структурно выделяет skill как повторяемую процедуру проекта, но и даёт больше фактуры: общая внутренняя форма skill без привязки к конкретной файловой раскладке, типовые сценарии, примеры из Matt Pocock и Codex, библиотечный слой, публичные каталоги, жизненный цикл, риски выбора, устаревания, конфликтующих процедур и внешних skills.

Граница сохранена: глава не превращена в справочник по Claude/Codex skills. Технические пути, installation flow и platform-specific детали не перенесены в основной текст.


## Дополнительная правка MCP после внешнего поиска

Раздел `MCP: управляемый доступ к внешнему миру` расширен после отдельного source pass. Теперь MCP раскрывается не как общий инструментальный доступ, а как задача проектирования узкого контура доступа под конкретный класс работы: GitHub для репозиториев и pull requests, Figma для дизайна, Playwright/Chrome DevTools для браузера и отладки, Stripe для платежной интеграции, Notion для workspace, Sentry для диагностики, Context7 и reference servers для документации, файлов, Git, Fetch и памяти.

Граница сохранена: глава не стала справочником по MCP-серверам и не ушла в transport/OAuth/JSON-RPC. Security-часть оставлена на уровне, нужном для проектного интерфейса: лишние tools нельзя просто показывать агенту и компенсировать prompts; доступ должен быть минимальным, связанным с задачей и понятным для человека.


## Дополнительная правка subagents после внешнего поиска

Раздел `Subagents: разные исполнители для разных частей задачи` расширен после отдельного поиска источников и проверки внутренних историй. Теперь subagents раскрываются не как «личности» или общий многоагентный энтузиазм, а как часть проектного интерфейса: способ вынести отдельную работу в отдельный контекст, дать исполнителю узкую роль, ограничить инструменты, собрать результат обратно и зафиксировать, что именно было проверено.

В текст добавлены различия между одиночным subagent, несколькими независимыми проверками, supervisor/router-подходами и agent teams. Также добавлены риски: расход токенов, дублирование работы, потеря общего контекста, конфликт локальных предположений и опасность параллельных правок кода. Внутренние истории Steinberger, Willison, Jökull, Vincent и Mark Erikson использованы как практические проверки против слишком абстрактного рассказа о subagents.
