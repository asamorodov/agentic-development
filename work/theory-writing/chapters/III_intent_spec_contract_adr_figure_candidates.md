# III. Figure candidates

## Текущий вывод

После ручной ADR-правки фигура не обязательна для готовности главы, но стала более осмысленной как будущая публикационная вставка. Если визуальный слой будет добавляться, лучший кандидат — не схема «поля ADR», а схема связи между полной записью решения, жизненным циклом ADR и рабочей проекцией для агента.

## Главный кандидат

```text
ADR как запись архитектурного решения

полная запись:
Context / Decision / Status / Consequences / Confirmation
        ↓
жизненный цикл:
proposed → accepted → superseded / rejected
        ↓
рабочая проекция для агента:
область действия → короткое правило → ссылка на ADR → проверка или ревью
```

Эта фигура нужна только если основной текст прямо на неё опирается. Она должна помогать читателю увидеть, что ADR в главе работает не как дополнительный документ, а как связка трёх вещей:

1. память решения;
2. статус и жизнь решения;
3. краткое применение решения в агентской работе.

## Альтернативный вариант

Если схема окажется перегруженной, её лучше разделить на две:

1. **Статус и замена ADR** — `proposed → accepted → superseded / rejected`.
2. **Рабочая проекция ADR для агента** — область действия, правило, ссылка, проверка или ревью.

## Решение для текущей версии

В основной текст фигура не вставлена. Текст уже даёт сквозной пример с запретом прямой зависимости между сервисами, и этот пример сейчас важнее схемы. Фигура остаётся кандидатом для публикационного слоя или последующего визуального прохода.
