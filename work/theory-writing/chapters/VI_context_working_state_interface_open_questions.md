# Chapter VI — открытые вопросы

## 1. Как назвать центральную модель главы

Рабочая формула «три слоя проектного интерфейса» остаётся полезной, но в финальной главе её нужно вводить как практическое различение, а не как новую жёсткую taxonomy. Наиболее естественная формула: правила, рабочее состояние и маршруты действия.

## 2. Насколько глубоко раскрывать `skills`

После P06 ясно: skills можно раскрывать не через список Matt Pocock-команд, а через общую функцию. Skill — это процедурная память и вызываемый маршрут действия. В главе достаточно показать, почему повторяемую процедуру лучше вынести из `CLAUDE.md` / `AGENTS.md` в отдельную способность: её можно вызвать, описать, ограничить, снабдить supporting files и не грузить полностью в каждый обычный контекст.

## 3. Где остановить hooks и MCP

Hooks и MCP остаются на границе с IX. В VI они нужны только как элементы интерфейса проекта:

- hooks связывают правило с событием исполнения;
- MCP расширяет инструментальную и доверенную поверхность;
- Powers/динамическая загрузка показывают, почему «больше tools» не равно «лучше interface».

Права, sandbox, approvals, threat model и runtime security оставить IX.

## 4. Как не повторить V

Spec Kit, Kiro, BMAD и GSD не нужно заново сравнивать как specification profiles. В VI они используются поперёк:

- какие правила проект предъявляет агенту;
- где лежит текущее состояние работы;
- какими маршрутами агент может действовать;
- что возвращается в проект после шага.

Если абзац начинает подробно объяснять саму методику, его нужно сжать или перенести.

## 5. Как не раскрыть VII раньше времени

PWG должен появиться как следующий ответ на ограниченность обычных файловых interfaces. В VI достаточно показать проблему: файлы правил, статуса и задач улучшают работу агента, но плохо выражают зависимости, блокировки, проверочные материалы, состояние источников и восстановление после частичного исполнения. Полную модель PWG не раскрывать.

## 6. Как вставлять внешние источники

Ссылки нужны рядом с механизмом, не в финальном списке. Рекомендуемые пары:

- rules: Codex `AGENTS.md`, Claude memory, Kiro steering;
- working state: Kiro Specs, BMAD project-context / sprint-status, GSD Core, Spec Kit;
- action routes: Claude skills, Kiro Powers, Claude/Kiro subagents;
- boundary with execution: Kiro hooks, Claude hooks, MCP tools spec.

## 7. Нужны ли ещё источники перед черновиком

Для черновика — нет. Дополнительный поиск понадобится только если финальный текст захочет использовать точные детали Mark Erikson/OpenCode, Mae Capozzi/InstructionsLoaded или отдельные security claims по MCP. Сейчас их лучше держать как внутренние story-anchors или оставить для IX.

## P24 — доработка слабых мест

После P24 часть открытых вопросов фактически закрыта в тексте:

- центральная модель главы введена как три диагностических вопроса: устойчивое правило, текущее рабочее состояние, маршрут действия;
- усилено требование к маршрутам действия: skill/MCP/subagent должны иметь условия входа, выхода, проверки и записи результата;
- добавлено требование обслуживания проектного интерфейса: правила, состояние, skills и hooks должны обновляться после изменения процесса, иначе устаревший документ становится активным ложным входом для агента.

Остающиеся вопросы для финальных проверок: не перегружена ли глава примерами и достаточно ли мягко удержан мост к PWG без раскрытия VII.

## P30 — закрытие открытых вопросов

К финальной проверке основные открытые вопросы закрыты:

- центральная модель названа не как новая taxonomy, а как три практических вопроса: правило, состояние, маршрут действия;
- `skills` раскрыты достаточно глубоко и не сведены к списку команд;
- hooks и MCP остановлены на границе VI, без ухода в security/runtime;
- Kiro, Spec Kit, BMAD и GSD не повторяют главу V;
- PWG введён только как необходимость следующей главы;
- внешние ссылки стоят рядом с механизмами, а не собраны в конце.

Открытым остаётся только редакторский вопрос публикационной сборки: заменить ли ASCII-схему на SVG. Для текста главы это не блокер.
