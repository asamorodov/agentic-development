# X. Когда агентов становится много: Gas Town, Beads и координация параллельной работы

## Когда параллельная работа начинает мешать пониманию

В одиночной агентской сессии человек обычно ещё понимает, что происходит. Есть задача, есть чат или окно инструмента, есть репозиторий, есть текущий дифф, есть следующий вопрос к модели. Даже если агент ошибается, место работы более или менее ясно: вот текущий разговор, вот файлы, вот список замечаний, вот команда, которую он запустил. Поэтому ранние приёмы агентской разработки в основном усиливают одну сессию: дают модели больше контекста, точнее описывают задачу, открывают инструменты, ограничивают права и сохраняют след действий.

Но эта картина быстро перестаёт работать, когда таких сессий становится несколько. Один агент правит серверную часть, другой пишет тесты, третий обновляет документацию, четвёртый разбирает замечания ревью, пятый делает небольшой рефакторинг в соседнем пакете. Каждый из них может делать что-то полезное. В каждом окне есть движение: где-то изменился код, где-то появился тест, где-то найдено важное ограничение, где-то PR почти готов. Но проект в целом становится менее понятным. Человек видит не ясную работу, а множество частичных состояний: активные сессии, статусы, промежуточные отчёты, проверки, ожидания, недослитые ветки и задачи, которые как будто закрыты, но всё ещё требуют внимания.

Это не ошибка отдельного промпта. Это другая организационная проблема. Пока работа одна, достаточно удерживать состояние этой работы: что надо сделать, что уже сделано, что мешает продолжать, какие проверки нужны. Когда параллельно идёт несколько связанных задач, приходится понимать больше: где лежит каждая задача, кто её взял, что зависло, что ждёт gate, что уже дошло до слияния, какой вывод остался только в локальной сессии, где нужно решение человека, а что сейчас не надо запускать, потому что и без того открыто слишком много веток.

Поэтому масштабирование агентской разработки начинается не с лозунга «запустим больше агентов». Без дополнительной организации это быстро создаёт больше мест, где работа может потеряться. Масштабирование начинается с рабочей среды, в которой параллельные действия можно видеть, связывать между собой и доводить до результата: у задач появляется адрес, статус, владелец, очередь, рабочая площадка, история, условия продвижения, сервисные роли и понятный путь возврата к человеку.

Gas Town и Beads важны здесь как ранний видимый прототип такой среды. Gas Town описывает себя как multi-agent orchestration / workspace manager для Claude Code, GitHub Copilot, Codex, Gemini и других агентских поверхностей; в README отдельно названы persistent work tracking, context persisted in git-backed hooks, mailboxes/handoffs и хранение work state в Beads ledger ([Gas Town README](https://github.com/gastownhall/gastown)). Но для этой главы важны не сами названия и не городская метафора. Важен принцип: работа многих агентов должна существовать не как набор приватных сессий, а как внешняя, проверяемая и управляемая картина проекта.

## Почему одного графа задач уже недостаточно

Предыдущий слой этой логики — persistent work graph. Работа не должна жить только в промпте, в памяти модели или в убедительном отчёте агента. Ей нужен внешний объект: задача, зависимости, статус, история, владелец, условия остановки, проверочные материалы, handoff и возможность продолжить после разрыва сессии. Без этого агентская разработка остаётся слишком хрупкой: модель забывает, контекст сжимается, человек открывает новую сессию, а работа теряет форму.

Beads даёт сильный пример такого нижнего слоя. В текущей документации Beads описан не как простой JSON-список задач, а как Dolt-backed система, где Dolt является sole storage backend и source of truth; рабочее состояние хранится в version-controlled SQL, поддерживает восстановление, синхронизацию и server mode для multi-writer сценариев ([Beads Architecture](https://gastownhall.github.io/beads/architecture)). Это важный сдвиг: задача становится не заметкой для человека, а частью версионированного состояния проекта.

На этом уровне появляются задачи, зависимости, gates, готовность к следующему шагу, явное назначение и связь с агентской сессией. `bd gate create` может заблокировать issue до human, timer, GitHub run или GitHub PR condition; заблокированная работа не должна появляться в `bd ready` ([Beads gate](https://gastownhall.github.io/beads/cli-reference/gate)). `bd pin` и `bd hook` помогают закрепить работу и связать её с исполнением; multi-agent документация Beads описывает sequential handoff и fan-out/fan-in, где большая работа делится на части, а затем снова собирается через зависимости ([Beads multi-agent coordination](https://gastownhall.github.io/beads/multi-agent/coordination)). `bd prime` выдаёт AI-optimized context для новой сессии и рассчитан на hooks в Claude Code, Gemini и Codex, чтобы агент после сжатия контекста не начинал работу с пустого места ([bd prime](https://gastownhall.github.io/beads/cli-reference/prime)).

Этого уже много. Если проект раньше жил только в переписке, Beads/PWG резко улучшает положение: работа становится долговечной, видимой, возобновляемой и пригодной для передачи между людьми и агентами. Но эта глава начинается там, где одного такого слоя уже мало.

Возьмём изменение payment webhook в продукте. Нужно поправить обработчик на серверной стороне, добавить миграцию, обновить экран истории платежей, изменить документацию для интеграторов, добавить регрессионные проверки и затем провести итоговое ревью. На уровне Beads/PWG это можно оформить как несколько связанных задач: `B-101` для контракта webhook, `B-102` для миграции базы, `B-103` для отображения статусов в интерфейсе, `B-104` для документации API, `B-105` для регрессионных проверок, `B-106` для итоговой интеграционной проверки. Это гораздо лучше, чем один общий тикет. Но если эти задачи одновременно берут разные агенты, появляются вопросы, на которые сам граф задач не отвечает.

Кто заметит, что агент взял `B-101`, но перестал продвигаться? Кто увидит, что агент документации нашёл важное замечание про повторную доставку webhook payloads, но оставил его только в локальном отчёте и не связал с `B-105`? Кто не даст `B-105` стать `ready`, пока CI gate ещё не закрыт? Кто обработает `MERGE_FAILED`, если ветка серверной части конфликтует с веткой миграции? Кто решит, стоит ли запускать ещё пять агентов, если уже есть зависшие ветки и незакрытые проверки? Кто поднимет человеку архитектурное решение, которое агент не должен принимать сам?

Persistent work graph сохраняет форму работы. Следующий слой нужен для другого: чтобы несколько таких работ не разошлись по разным сессиям, веткам и отчётам без общей координации.

## Два уровня: состояние работы и координация многих задач

Здесь полезно развести два уровня.

Первый уровень — **состояние отдельной работы**. Что нужно сделать, какие есть зависимости, кто назначен, какой статус, какие gates, какие комментарии, где ветка или PR, какие проверки относятся к задаче. Beads/PWG в основном работает на этом уровне. Он делает работу внешней и долговечной.

Второй уровень — **координация многих работ**. Это уже не описание отдельной задачи, а организация множества задач: какие из них можно отдавать агентам, какие должны ждать, какая работа закреплена за конкретной сессией, где исполнитель исчез, где результат надо вернуть в общий контекст, какой merge path сейчас возможен, где нужна recovery, а где требуется решение человека.

Без первого уровня второй превращается в хаос процессов: нечего маршрутизировать, если сама работа не имеет устойчивой формы. Но без второго первый превращается в красивую базу задач, вокруг которой человек всё равно вручную бегает с фонариком: какой агент жив, что он сделал, где это записано, почему PR не слился, какой вывод потерялся, какую задачу можно запускать дальше, а какую нельзя.

Поэтому слово «оркестрация» здесь одновременно полезно и опасно. Оно указывает на проблему, но слишком быстро прячет механику. В агентской разработке речь должна идти не о туманной координации, а о конкретных функциях: маршрутизация, закрепление задачи за исполнителем, hooks, gates, очередь готовых задач, rig, convoy, наблюдение за жизненным циклом работы, восстановление после неудачного merge, scheduler, backpressure, escalation и возврат результата в общее состояние. Эти функции и образуют слой, который появляется поверх persistent work graph.

Следующая схема работает как карта этой главы: каждый слой появляется не из любви к терминологии, а потому что предыдущий способ управления перестаёт справляться с новой нагрузкой. Дальше эти механизмы будут раскрыты через Beads, Gas Town и сквозной пример.

## Beads как рабочая память проекта

В этой главе Beads лучше понимать как нижний долговечный слой. Он не просто хранит задачи для человека, а делает рабочее состояние пригодным для агентского чтения и последующих действий.

Во-первых, Beads даёт долговечные рабочие объекты. Issue/bead может иметь dependencies, labels, comments, status, gates, связь с другими репозиториями и route. В multi-agent routing docs Beads описаны routes, pattern matching по title, labels и path prefix, auto-routing, cross-repo dependencies и hydration ([Beads multi-agent routing](https://gastownhall.github.io/beads/multi-agent/routing)). Это уже не «список задач», а слой, который помогает отправить работу туда, где она действительно должна выполняться.

Во-вторых, Beads даёт явное назначение. `bd pin` и `bd hook` помогают различить «этим когда-нибудь надо заняться» и «эта работа сейчас привязана к исполнению». Для человека это может показаться мелочью, но для среды с несколькими агентами это принципиально. Если задача находится на hook, значит от исполнителя ожидается продолжение работы. Если он этого не делает, появляется не смутная тревога, а конкретное нарушение рабочего порядка.

В-третьих, Beads даёт gates. Gate здесь означает простое правило: задача не должна двигаться дальше, пока не выполнено внешнее условие. В документации это может быть human approval, timer, GitHub run или GitHub PR ([Beads gate](https://gastownhall.github.io/beads/cli-reference/gate)). В одиночной работе человек может помнить: «этот пункт вроде готов, но надо дождаться CI». Когда одновременно работают несколько агентов, такая память быстро становится ненадёжной. Gate нужен, чтобы задача не выглядела готовой для следующего шага, пока условие не закрыто.

В-четвёртых, Beads связывает агентскую сессию с текущим состоянием проекта. `bd prime` рассчитан на то, чтобы дать агенту компактный рабочий контекст. документация Codex integration показывает конкретную рабочую форму: SessionStart вставляет полный `bd prime`; PreCompact проверяет memories-only; PostCompact помечает необходимость refresh; UserPromptSubmit снова вставляет полный `bd prime`; отдельно указано, что одного PreCompact недостаточно из-за того, как Codex работает со stdout ([Beads Codex integration](https://gastownhall.github.io/beads/integrations/codex)). Это важная деталь: контекст не просто где-то хранится. Он возвращается в новую или сжатую сессию через жизненный цикл инструмента.

Наконец, Beads даёт форму повторяемым процессам. В документации о workflows formulas/TOML и molecules описывают, как процесс превращается в persistent instance: шаги становятся issues, а зависимости управляют `bd ready`, hooks и pinning связывают шаги с исполнителями ([Beads Workflows](https://gastownhall.github.io/beads/workflows); [Beads Molecules](https://gastownhall.github.io/beads/workflows/molecules)). Это мост к предыдущей главе о том, как продолжать работу под контролем. Процедура перестаёт быть только текстовой инструкцией; она может стать рабочим графом, который живёт в состоянии проекта.

Но Beads отвечает прежде всего за форму работы. Чтобы несколько агентов действительно могли работать параллельно, поверх этого слоя нужен порядок: кто что берёт, куда работа отправляется, кто следит за зависаниями, как обрабатываются неудачные слияния, где человек видит проблемы и как решение возвращается в общий контекст.

## Gas Town как слой координации вокруг рабочих площадок

Gas Town добавляет к Beads/PWG не ещё одно поле задачи, а рабочую организацию вокруг многих задач и репозиториев. В документации по архитектуре прямо различаются town-level и rig-level beads: town-level слой держит Mayor mail/messages, convoy coordination, strategic issues/decisions, town-level agent beads и role-definition beads; rig-level слой держит bugs/features/tasks, merge requests/code reviews, project molecules и rig-level agent beads ([Gas Town Architecture](https://github.com/gastownhall/gastown/blob/main/docs/design/architecture.md)). Это почти готовое различение между общей координацией и локальной проектной работой.

Роли Gas Town лучше читать не как список персонажей, а как функции вокруг жизненного цикла работы. Одну задачу надо принять от человека и превратить в рабочий объект. Другую — отправить в подходящую площадку. Третью — закрепить за исполнителем. Четвёртую — заметить, если исполнитель исчез или нарушил правило. Пятую — провести через merge или вернуть как failed/fix-needed. Шестую — поднять человеку, если автоматическое восстановление исчерпано. Mayor, Rig, Convoy, Polecat, Witness, Refinery, Deacon и Scheduler важны именно как ответы на разные места этого жизненного цикла.

`Rig` можно понимать как рабочую площадку вокруг конкретного репозитория или проекта. В сквозном примере серверная часть, интерфейс, документация и проверки могут быть разными rig или разными участками внутри одного большого rig. Важно не буквальное соответствие, а принцип: работа находится не в абстрактном пространстве, а в месте, где есть репозиторий, ветка, проверки, исполнители и локальное состояние.

`Convoy` нужен там, где работа проходит через несколько таких площадок. В публичной документации Gas Town convoys описаны как cross-rig tracking, auto-notification и historical record ([Gas Town docs](https://docs.gastownhall.ai/)). Это отличается от обычной зависимости между задачами. Dependency говорит, что одна задача логически ждёт другую. Convoy помогает провести связанную работу через несколько rig так, чтобы общая среда видела маршрут, а не набор разрозненных локальных задач.

`Mayor` — не просто «главный агент». Это поверхность управления. Mayor видит работу, распределяет её, принимает problem feed, получает escalations и связывает человека с рабочей средой. Ролевой шаблон Mayor описывает `gt sling <bead-id> <rig>` как команду work dispatch: spawn polecat, hook work, start session ([Mayor role template](https://github.com/gastownhall/gastown/blob/main/internal/templates/roles/mayor.md.tmpl)). Эту команду не обязательно разбирать как CLI-справочник, но она хорошо показывает сдвиг: поручение не остаётся приватным сообщением в чате; оно становится операцией над задачей, rig и исполнителем.

Вторая важная поверхность Mayor — не запуск, а чтение проблем. README Gas Town описывает `gt feed` как терминальную панель, которая объединяет beads activity, agent events и merge queue updates; `gt feed --problems` открывает problems view, где агенты группируются по состояниям вроде GUPP Violation, Stalled, Zombie, Working и Idle ([Gas Town README](https://github.com/gastownhall/gastown)). Эта деталь нужна не как ещё одна команда, а как защита человеческого внимания. Человек не должен читать все терминалы, чтобы понять, где проблема. Но одна сводка тоже не решает задачу: из неё должны следовать действия — re-sling, defer, close gate, escalate, recover, merge, mark fix-needed.

`gt prime` и `bd prime` показывают ещё одну грань интерфейса. `bd prime` подаёт агенту Beads work context, а `gt prime` подаёт роль и городскую рамку. Это не «память в голове модели», а повторная загрузка рабочего положения из внешнего состояния. Продолжение работы в такой среде не сводится к просьбе «вспомни, что мы делали». Оно строится через durable state и role-specific context.

`Polecat` и `Crew` обозначают разные типы исполнителей. Polecat — расходуемый исполнитель дискретной работы; Crew — более долговечная или контекстная форма. Здесь важна фраза из авторского объяснения Steve Yegge: агент — это не сессия; роль агента и текущая сессия не одно и то же, потому что сессия может умереть, а работа и роль должны сохраняться ([Welcome to Gas Town](https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04)). Продолжимость возникает не из магической памяти модели, а из внешних ролей, hooks, beads, mail, history и рабочих площадок.

`gt mail` стоит упомянуть как канал, который переживает разрыв сессии и оставляет след. Если агент просто написал сообщение в терминале, оно легко теряется. Если сообщение стало частью mail/handoff/state, его может прочитать сервисная роль, Mayor или следующий исполнитель.

`Witness`, `Refinery`, `Deacon` и `Dogs` показывают, что в такой среде появляются сервисные роли. Они не обязательно пишут основную фичу. Они смотрят за состоянием, возвращают зависшую работу, помогают со слиянием, поднимают проблему человеку, проверяют здоровье среды. В публичной документации Gas Town infrastructure roles включают Mayor, Deacon, Witness и Refinery ([Gas Town docs](https://docs.gastownhall.ai/)). Это не декоративная терминология. Это ответ на простую вещь: параллельная работа не сопровождает сама себя.

Особенно важен документ о polecat lifecycle patrol. Там появляются операционные события: `RECOVERED_BEAD`, `GUPP_VIOLATION`, `ORPHANED_WORK`, сообщения Witness → Refinery вроде `MERGE_READY`, а также Refinery → Witness вроде `MERGED` и `MERGE_FAILED` ([Gas Town polecat lifecycle patrol](https://github.com/gastownhall/gastown/blob/main/docs/design/polecat-lifecycle-patrol.md)). Эти названия ценны не сами по себе, а потому что показывают зрелую форму рабочего события. Работа не просто «кажется зависшей». Она получает состояние, после которого возможны recovery, повторная отправка исполнителю, обработка merge или escalation.

Gas Town тем самым делает видимым следующий этаж. Beads хранит рабочие объекты. Gas Town пытается организовать жизнь этих объектов, когда их становится много и они движутся через разные площадки.

## Payment webhook: где параллельность начинает создавать проблемы

Вернёмся к примеру с payment webhook. Изменение разбито на несколько задач:

- `B-101`: контракт webhook на серверной стороне;
- `B-102`: миграция базы;
- `B-103`: отображение статусов в интерфейсе;
- `B-104`: обновление документации API;
- `B-105`: регрессионные проверки;
- `B-106`: итоговая интеграционная проверка.

У `B-103` есть dependency на `B-101`, потому что интерфейсу нужна финальная модель статусов. У `B-106` есть dependencies на все рабочие ветки. У `B-105` есть gate на CI run. У `B-104` есть human gate: публичный текст для интеграторов должен подтвердить человек.

Сначала всё выглядит хорошо. Rig серверной части получает `B-101` и `B-102`. Rig документации получает `B-104`. Rig проверок получает `B-105`. Rig интерфейса пока ждёт зависимость от серверной части. Mayor или maintainer распределяет работу, часть задач pinned или hooked на конкретных исполнителей. В сессиях появляются отчёты. Где-то агент уже изменил код, где-то собрал список тестовых payloads, где-то начал править документацию.

На этом месте многие разговоры о многоагентности заканчиваются слишком рано: «мы распараллелили работу». Но реальные трудности начинаются дальше.

### Зависшая работа

Polecat серверной части взял `B-101`, открыл рабочую площадку, изменил часть кода обработчика и оставил промежуточный отчёт. Потом сессия оборвалась, ушла в неправильную ветку или просто перестала продвигать задачу. В обычной системе человек видит разрозненные признаки: где-то был diff, где-то есть ветка, где-то осталось сообщение, но непонятно, жив ли исполнитель и надо ли ждать.

В организованной среде это должно стать явным состоянием. Если работа находится на hook, а исполнитель её не ведёт, нарушается рабочее правило. Gas Town glossary формулирует GUPP как правило: если на hook есть работа, её нужно выполнять ([Gas Town Glossary](https://github.com/gastownhall/gastown/blob/main/docs/glossary.md)). Поэтому зависание может стать `GUPP_VIOLATION`, stalled state или `ORPHANED_WORK`, а не неопределённым ощущением человека, что «кажется, агент пропал».

Затем сервисная роль должна превратить событие в действие: вернуть bead в очередь, re-sling work, запросить status, сохранить частичный результат, поднять проблему Deacon или Mayor. Смысл не в том, что каждый проект обязан буквально иметь Witness. Смысл в том, что кто-то или что-то должно выполнять эту функцию. Иначе человек снова становится ручным сторожем всех открытых сессий.

### Полезный вывод остался в локальной сессии

Агент, работая над `B-104`, обнаруживает важную деталь: интеграторов нужно предупредить о replayed webhook payloads, иначе они могут ошибочно принять повторную доставку старого события за новую транзакцию. Это хороший вывод. Возможно, без него изменение будет опасным, даже если код формально пройдёт тесты.

Но агент оставляет этот вывод только в локальном отчёте. Он не обновляет `B-104`, не добавляет связанную задачу для `B-105`, не создаёт dependency и не уведомляет исполнителя серверной части. В обычной агентской работе это один из самых частых тихих провалов: модель сделала полезную мыслительную работу, но результат этой работы не стал частью проекта.

Среда должна вернуть такой вывод в долговечное состояние проекта. Это может сделать сам агент, сервисная роль, ревьюер или Mayor. Важно, чтобы результат стал комментарием, зависимостью, новым рабочим элементом или gate, а не остался в тексте, который следующий исполнитель не увидит. В примере появляется новая связь: регрессионные проверки должны покрыть replayed payloads; human gate для документации теперь проверяет именно публичное предупреждение; серверная задача может получить уточнение к contract behavior.

Здесь видно, почему эта глава не равна главе о задачах. Задачи уже были. Потерялось не наличие задачи, а перенос знания из локальной сессии в общее рабочее состояние.

### Gate не даёт объявить работу готовой раньше времени

Test-agent добавил регрессионные проверки и сообщает: всё зелёное. Но у `B-105` есть gate на CI run. У `B-104` есть human gate. Если среда плохо устроена, maintainer видит несколько уверенных отчётов и считает проект почти готовым. Потом выясняется, что тесты запускались локально на старом наборе payloads, CI ещё не прошёл, а публичный текст документации никто не подтвердил.

Gate нужен не для бюрократии. Он нужен, чтобы задача не попадала в `ready` раньше времени. Beads gate docs прямо указывают, что blocked issue не появляется в `bd ready` до разрешения gate ([Beads gate](https://gastownhall.github.io/beads/cli-reference/gate)). Это простая, но важная защита от самообмана: «агент сказал готово» не значит, что следующему исполнителю уже можно считать эту работу завершённой.

Важно провести границу. Gate не доказывает, что тесты хорошие. Он только не даёт задаче пройти дальше до выполнения внешнего условия. Вопрос, достаточно ли регрессионные проверки покрывают replayed payloads, относится уже к следующей главе о проверочном материале.

### Неудачный merge должен вернуться в работу

Refinery пытается слить ветку `B-101`, но получает `MERGE_FAILED`: параллельная ветка миграции `B-102` изменила соседний слой. В обычном режиме это снова превращается в шум: merge conflict, пожалуйста разберитесь. Человеку нужно самому вспомнить, какой агент что делал, где worktree, какие изменения полезны, что уже проверено и почему конфликт возник.

В организованной среде неудачное слияние должно вернуться в рабочее состояние. `MERGE_FAILED` становится статусом, комментарием, отдельной задачей на исправление или сигналом Witness/Deacon. Предыдущий результат не исчезает и не подменяется новой попыткой с нуля. Если конфликт можно решить автоматически, работа возвращается к исполнителю. Если нельзя, появляется escalation.

Это один из ключевых признаков такой среды: она не просто запускает исполнителей, а удерживает последствия их работы. Ошибка merge — тоже часть работы, а не исключение из неё.

### Когда не надо запускать ещё одного агента

Когда у проекта несколько зависших веток, легко запустить ещё агентов: один разберёт конфликт, другой обновит тесты, третий перепишет документацию, четвёртый проверит интерфейс, пятый сделает summary. Но если рабочая среда уже перегружена, это увеличит шум. Параллелизм без учёта capacity ухудшает управляемость.

Документация Gas Town scheduler даёт полезную фактуру: deferred dispatch, `scheduler.max_polecats`, batch size, spawn delay, convoy integration, capacity/backpressure и safety properties вроде dispatch serialization и atomic scheduling ([Gas Town Scheduler](https://github.com/gastownhall/gastown/blob/main/docs/design/scheduler.md)). Для этой главы не важно подробно объяснять scheduler. Важно другое: зрелое масштабирование включает право среды отложить работу. Не всё, что можно запустить, надо запускать сейчас.

В примере это означает: конфликт серверной части и миграции получает приоритет, интерфейс ждёт стабилизации контракта, обновление тестов ждёт решения по replayed payloads, а Mayor видит очередь с приоритетами, а не двадцать активных вкладок.

### Где нужно решение человека

Наконец появляется решение, которое агент не должен принимать сам. Контракт webhook может сохранить backward-compatible semantics или ввести breaking behavior с migration notice. Оба пути возможны, и выбор зависит от продукта, интеграторов, риска и обещаний API. Автоматический исполнитель может собрать аргументы, но не должен сам решить, какое обещание компания даёт пользователям.

Документация Gas Town escalation описывает escalations как случаи, где автоматическое разрешение невозможно: они учитывают severity, stale detection и re-escalation, а сами случаи фиксируются как beads. Сигнал идёт от Agent к Deacon, затем к Mayor и при необходимости к Overseer; вся цепочка записывается в bead comments ([Gas Town Escalation Protocol](https://github.com/gastownhall/gastown/blob/main/docs/design/escalation.md)). Это хорошая форма человеческого входа: человек получает не сырой сигнал «я не уверен», а структурированную проблему, связанную с рабочими элементами, попытками восстановления, вариантами и блокировками.

Здесь важно не романтизировать автоматику. Сильная среда не та, где человек никогда не нужен. Сильная среда та, где человеку не приходится быть диспетчером всего, но где его суждение вызывается в правильных местах и с достаточным контекстом.

## Недостаточно видеть состояние; среда должна уметь его менять

У такой среды есть два разных режима: читать состояние и менять состояние. Их нельзя смешивать.

Чтение даёт человеку и агентам обзор: сводку проблем (problem feed), список ready work, открытый bead, dependencies, gates, PR checks, trace, session log, merge failure, current role context через `gt prime` или work context через `bd prime`. Это защищает от слепоты. Но если среда только показывает панель состояния, человек всё равно остаётся диспетчером: он должен вручную решить, кого будить, что перезапускать, что закрывать, что считать ready, что поднимать наверх.

Действие меняет рабочую картину: создать рабочий элемент, добавить dependency, открыть или закрыть gate, `pin`/`hook` work, `sling` задачу в rig, отложить выдачу задачи, заново отправить orphaned work исполнителю, записать `MERGE_FAILED`, создать задачу на исправление, подтвердить escalation, повторно поднять stale item, закрыть работу. В агентской среде эти операции должны быть привязаны к durable state. Иначе действие снова превращается в свободное вмешательство в чат: агент что-то сделал, но проект не знает, что изменилось.

Поэтому правильная формула не «нужна панель состояния» и не «нужен автономный агент». Нужна связка: видимость состояния плюс допустимые действия над ним. Видимость без действия — наблюдение за хаосом; действие без состояния — хаотичная автоматика. Координационный слой появляется там, где эти две стороны соединены.

## Что получает проект

После такого цикла проект получает не просто набор ответов агентов. Он получает рабочую картину.

Для изменения payment webhook проект знает:

- какие рабочие элементы созданы;
- какие зависимости закрыты;
- какая задача сейчас находится на hook;
- какая работа зависла;
- какая работа осталась без исполнителя;
- где не удалось слияние;
- какие gates ещё блокируют `ready`;
- где нужно решение человека;
- какие полезные выводы вернулись из локальных сессий в Beads/PWG;
- какие ветки можно продолжать;
- что сейчас лучше не запускать из-за capacity.

Это и есть предмет главы. В агентской разработке появляется новая инфраструктурная потребность: вести множество связанных работ через разных исполнителей и рабочие площадки. Если такой среды нет, даже хороший persistent work graph превращается в базу, которую человек вручную сопровождает. Если такая среда есть, человек видит не все подробности всех агентов, а рабочую картину проекта: что движется, что стоит, где возникла проблема, где требуется решение.

Можно представить этот слой как соединение трёх уровней.

Первый уровень — долговечное состояние работы (durable work state): Beads/PWG, issues, dependencies, gates, status, comments, `bd prime`, pin/hook. Второй уровень — рабочая география: rigs, worktrees, branches, PRs, checks, convoys. Третий уровень — координационные и сервисные роли: Mayor, Witness, Refinery, Deacon, Dogs, scheduler, escalation, problem feed. Только вместе они превращают множество агентских действий в работу, с которой проект может иметь дело.

## Не только Gas Town: те же функции в других историях

Gas Town даёт самый собранный язык для этой главы, но сама потребность видна не только там. Следующие истории не являются вторыми центрами главы. Они нужны только как проверка: похожие функции возникают при сопровождении PR, в корпоративной платформе разработки, в исполняемом workflow и в платформенной наблюдаемости.

У Jökull Sólberg маленькая версия той же проблемы появляется вокруг PR. После `push` работа не заканчивается: нужно дождаться CI, разобрать Greptile comments, запустить `codex review --base main`, решить, что исправить, что отклонить, что поднять человеку, повторить проверки и довести PR до состояния, когда его можно сливать. В “Babysitting PRs With Claude Code” он описывает `/babysit-pr` как процедуру сопровождения PR, а в “How I Use Claude Code” — более широкий режим нескольких рабочих потоков, GitHub issues, worktrees, context management и specialized agents ([Babysitting PRs With Claude Code](https://www.solberg.is/babysit-pr); [How I Use Claude Code](https://www.solberg.is/how-i-use-claude-code)). Это не Gas Town, но это тот же сдвиг: человек не должен быть живым таймером между CI, замечаниями ревью и повторными исправлениями.

У Stripe Minions похожая логика видна на корпоративном уровне. Снаружи запуск может выглядеть как Slack-сообщение и emoji reaction; внутри есть route signal, isolated devbox, branch, tools, анализ кода, tests, commit, PR и human review. В ChatPRD-разборе Stripe Minions эта сцена показана как переход от Slack-сообщения к PR через эмодзи-реакцию и подготовленную dev environment, а связанная workflow page раскладывает steps: Slack idea, emoji trigger, isolated cloud environment, agent loop, PR review ([How Stripe’s AI Minions Ship 1,300 PRs Weekly from a Slack Emoji](https://www.chatprd.ai/how-i-ai/stripes-ai-minions-ship-1300-prs-weekly-from-a-slack-emoji); [workflow page](https://www.chatprd.ai/how-i-ai/workflows/how-to-automate-code-generation-from-a-slack-message-into-a-pull-request)). Для главы X отсюда важен не масштаб PR, а платформа вокруг агента: чем автономнее запуск, тем больше обычной инженерной инфраструктуры должно его удерживать.

Shopify Roast показывает соседнюю форму: workflow as code для AI steps. В статье Shopify Engineering Roast представлен как framework для структурированных AI-workflows; открытый README показывает Ruby DSL с `cmd`, `agent`, `chat`, `ruby`, `map`, `repeat`, named outputs and providers; tutorial examples показывают chaining cogs, session resumption, collections and iterative workflows ([Introducing Roast](https://shopify.engineering/introducing-roast); [Shopify/roast README](https://github.com/Shopify/roast/blob/main/README.md); [Roast tutorials](https://github.com/Shopify/roast/tree/main/docs/tutorials)). Для этой главы важно не сходство синтаксиса, а сам сдвиг: агентская работа становится исполняемым процессом с шагами, выходами, провайдерами и возможностью продолжать сессию.

У Mae Capozzi похожая потребность выражена через worktrees, traces, timeouts, CI, observability и платформенные ограничения. В “How I Use Claude Code to Reduce Toil as a Platform Engineer” она описывает использование Claude Code для рутинной платформенной работы, CI/test PRs, dependency reviews, инструментирование перед deploy и cleanup/deletion work ([Mae Capozzi](https://maecapozzi.com/blog/ai-powered-toil-reduction-platform-engineering)). Когда агентских PR и веток становится много, мало получить хороший отдельный diff; нужна среда, которая показывает, что уже проверено, что висит, что можно закрыть, а где требуется человеческий выбор.

Эти истории не нужно превращать в четыре дополнительных кейса внутри главы. Они подтверждают переносимость проблемы. Gas Town/Beads дают наиболее яркую форму, но за ними стоит более общий сдвиг: агентская разработка переходит от одиночной сессии к рабочей среде, где параллельные задачи нужно связывать, проверять, возвращать в общее состояние и иногда останавливать.

## Чего такая среда не доказывает

Важно закрыть главу не рекламой Gas Town и не обещанием, что городская метафора решит все проблемы. Даже если Beads/PWG удерживает work state, слой типа Gas Town координирует задачи, scheduler не даёт перегрузить систему, escalation возвращает решения человеку, а merge failures не теряются, остаётся следующий вопрос: можно ли доверять результату?

Сами текущие источники не позволяют писать о Gas Town/Beads как о зрелом стандарте. Beads docs прямо фиксируют ограничения: large teams, real-time collaboration и cross-repo use требуют осторожности; multi-clone races and sync/recovery concerns остаются инженерной реальностью ([Beads Architecture](https://gastownhall.github.io/beads/architecture)). Авторская статья Steve Yegge описывает Gas Town как frontier/hands-on/expensive режим, а не как спокойную готовую платформу для любой команды ([Welcome to Gas Town](https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04)). Это не ослабляет главу, а делает её честнее: важна не зрелость конкретного инструмента, а слой проблем, который он показывает.

`B-105` мог пройти CI gate, но это ещё не доказывает, что тесты действительно покрывают replayed webhook payloads. `B-104` мог пройти human gate, но это ещё не значит, что документация не содержит двусмысленности. `B-101` мог быть merged, но это ещё не доказывает, что backward compatibility сохранена. `B-106` может собрать итоговый review, но итоговый review должен опираться на проверочный материал, а не только на статусы задач.

Это граница с главой XI. Глава X показывает, как работа доходит до review/merge path в управляемом состоянии: не потеряв зависимости, gates, неудачные попытки, частичные результаты, escalations и human decisions. Но координация многих задач ещё не доказывает достаточность результата. Следующий вопрос — какие проверки, артефакты, логи, диффы, тесты, review decisions и другие материалы делают результат заслуживающим доверия и пригодным для передачи дальше.

В этом месте полезно вернуться к началу. Агентская разработка усложняется не потому, что модели сами по себе становятся «слишком автономными». Она усложняется потому, что работа перестаёт идти одной линией. Как только появляется много параллельных задач, проекту нужна инфраструктура, которая связывает их между собой и показывает человеку только те места, где действительно нужно внимание. Не каждый проект обязан буквально построить Gas Town. Но каждый проект, который всерьёз использует много агентских действий, столкнётся с тем же набором функций: durable work state, routing, рабочие площадки, lifecycle observation, recovery, escalation, service roles и human-readable problem feed.

Без этого параллелизм остаётся шумом. С этим он начинает становиться управляемой работой.
