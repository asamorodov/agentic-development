# Использование Атласа для главы V

## Spec Kit

Статья `spec_kit_method.md` — основной донор для подхода Spec Kit. В главе нужно взять не каталог команд, а функцию цепочки: намерение фичи проходит через `spec.md`, уточнения, чек-лист требований, `plan.md`, `tasks.md`, анализ согласованности и реализацию. Главная поддерживаемая ось — перевод намерения в работу через видимые состояния.

Важные элементы для главы:

- `Spec -> Plan -> Tasks -> Implement` как базовая цепочка;
- `clarify` и `checklist` как защита от слишком раннего плана;
- `constitution` и Constitution Check как ограничитель генерации;
- `analyze` как read-only проверка согласованности перед реализацией;
- риск: цепочка выглядит управляемой, но не заменяет человеческое решение и долговечное состояние работы.

## Kiro Specs

Статья `kiro_specs.md` — основной донор для Kiro. В главе нужно использовать Kiro как пример продуктовой spec surface: Feature Specs, Bugfix Specs, Quick Plan, Analyze Requirements, `requirements.md` / `design.md` / `tasks.md`, исполнение задач под наблюдением и связь с hooks/MCP/CLI как соседними слоями.

Главная поддерживаемая ось — спецификация как состояние внутри среды, а не только набор файлов в репозитории. Kiro показывает, что IDE/Web/CLI-поверхность может удерживать требования, дизайн, задачи и статус исполнения рядом с кодом. Но глава не должна превращаться в экскурсию по Kiro: hooks, MCP, Powers, Subagents и Web Preview нужны только как границы с главой VI/IX.

## TDAD

Статья `tdad_comparative.md` нужна для подхода тестов. В главе важно развести два смысла TDAD:

- тесты как определение агента или его ожидаемого поведения;
- тесты как регрессионный маршрут для кодового агента.

TDAD поддерживает оси проверки и ограничения генерации, но не должен съедать будущую главу об evidence. В главе V тест важен прежде всего как форма спецификации: он делает часть требования исполнимой и проверяемой до или во время реализации. Ограничение: тесты не покрывают весь смысл фичи, не решают архитектурное право и не заменяют спецификацию требований.

## Constitutional SDD

Статья `constitutional_sdd.md` — основной донор для подхода constitution как верхнего слоя. Для главы V нужно взять:

- `constitution` как набор принципов и ограничений выше отдельной фичи;
- traceability matrix как связь требований, решений, проверок и контрольных точек;
- security/human checkpoints как места, где агент не должен тихо продолжать работу;
- риск переутверждения: нельзя писать так, будто constitution автоматически доказывает безопасность или compliance.

Constitutional SDD поддерживает оси правил, безопасности, границы генерации и человеческого решения.

## Атласные материалы, которые не нужно переносить

Не переносить длинные списки команд, интерфейсные подробности, вспомогательные изображения и все внешние очереди ассетов. Для главы V нужны только те элементы, которые отвечают на вопрос: какую часть изменения подход делает устойчивой.

## P04 update — что изменилось после проверки внешних первичных источников

Атлас остаётся главным внутренним донором, но текущие формулировки по Spec Kit и Kiro нужно сверять с официальными источниками при первом переносе в основной текст. Для TDAD и CSDD Атлас полезен как объяснительная база, но итоговая глава должна отдельно показать осторожность: TDAD — две разные исследовательско-инструментальные линии; CSDD — proposed methodology / worked example, а не стандарт индустрии.

## P12 — фактическая интеграция Атласа

Из Spec Kit atlas/dossier в основной текст дополнительно перенесена роль `constitution` and Constitution Check как проверки плана против принципов проекта.

Из Kiro atlas/dossier дополнительно перенесена граница: spec state внутри среды полезен только при корректном локальном проектном контексте; иначе аккуратные requirements/design/tasks могут вести не туда.

TDAD and Constitutional SDD atlas materials не расширялись сверх уже встроенного: текущий текст достаточно удерживает две TDAD-линии, тест как исполнимую спецификацию, constitution above feature and caution against overclaim.

## P13 — языковая сшивка Атласа

Фраза про Constitution Check переписана как часть объяснения Spec Kit: план должен сверяться с принципами проекта до дальнейшего проектирования. Kiro-грань переписана через зависимость requirements/design/tasks от корректного проектного контекста.
