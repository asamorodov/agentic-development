# Влияние новых решений Атласа на скелетон Теории

Дата: 2026-06-17.  
Статус: рабочее решение для будущих chapter packages.  
Связанные решения: `ADR-0012`, `ADR-0013`, диагностика результата `agent_run_to_accepted_change`.

## Короткий вывод

Новые решения не требуют ломать принятый скелетон Теории. Главная ось остаётся прежней:

```text
намерение → спецификация → исполнение → проверочный материал → принятие → сопровождение / восстановление / передача состояния
```

Изменение не в верхнем skeleton, а в маршрутизации материала и в правилах покрытия технологий внутри теоретических глав.

Теория должна использовать технологии не как каталог и не как статью Атласа внутри главы, а как grounding layer: конкретные технические формы показывают, где именно жизненный цикл изменения получает носитель, след, проверку, gate, право или route для продолжения.

## Что меняется

### 1. Ex-A3 становится theory-ready fragment для части V

Результат `agent_run_to_accepted_change` не принимается как статья Атласа, но является сильным фрагментом Теории.

Его главный вклад:

```text
agent run ≠ accepted change

след выполнения
→ проверочный материал
→ материал для ревью
→ основание решения
→ принято / отклонено / нужно доработать / заменено / причина неизвестна
→ следующий рабочий маршрут
```

Маршрутизация:

- **Глава XI** берёт из ex-A3 различение между следом выполнения, трассировкой, тестом, CI, benchmark, contract/API check и границей доказательства.
- **Глава XII** берёт из ex-A3 переход от проверочного материала к PR/MR, review, approval, owner decision и статусу принятого / отклонённого изменения.
- **Глава XIII** берёт из ex-A3 хвост принятия: revert, rollback, post-merge monitoring, cleanup, обновление инструкций и процессный урок.

Ex-A3 не должен становиться отдельной новой главой. Он слишком хорошо ложится на границу XI–XII и частично XIII. Его лучше использовать как первичный donor для Part V bridge.

### 2. Git/version-control слой становится сквозным техническим субстратом

Отдельная статья Атласа про Git/version-control не создаёт отдельную главу Теории. В Теории Git должен появляться там, где жизненный цикл изменения получает материальную форму.

Маршрутизация:

- **VI. Репозиторий как интерфейс для агента** — Git repository как место истории проекта, правил, документов и stable context; не сводить главу к Git, но помнить, что repository не только файловая папка.
- **IX. Среда исполнения, протоколы и полномочия** — branch/worktree/sandbox как форма безопасного действия и изоляции рабочей задачи.
- **XI. След выполнения, проверочный материал и границы доказательства** — diff, patch, commit, test output, CI output и trace как разные материалы с разной силой.
- **XII. PR как контур принятия** — PR/MR как social-technical container: diff, discussion, checks, review comments, approvals, CODEOWNERS, merge rules.
- **XIII. После merge** — revert, rollback, bisect, cleanup, удаление/исправление устаревших правил и возвращение урока в процесс.

### 3. В Теории нужен не технический охват, а техническая привязка

Глава Теории не должна пытаться покрыть все технологии своего участка. Это задача Атласа. Но каждая технологически чувствительная глава должна иметь короткий grounding pass:

```text
какие реальные технологии здесь являются носителями аргумента;
какую функцию жизненного цикла они выполняют;
какой слой Атласа раскрывает их технически;
что глава берёт из них для теоретического хода;
что глава сознательно не покрывает, чтобы не стать Атласом.
```

Пример: глава XII может говорить о PR, required reviews, CODEOWNERS, status checks и merge rules, но не должна объяснять все варианты GitHub/GitLab/Azure/Gerrit. Это работа Атласа. Теория использует эти формы для утверждения: accepted change возникает не из успешного прогона агента, а из социально-технического контура принятия.

## Что не меняется

1. Не нужно перестраивать Теорию по техническим слоям. Это был бы Атласный разрез.
2. Не нужно добавлять отдельную главу про Git.
3. Не нужно превращать главы XI–XII в справочник проверки/ревью.
4. Не нужно переносить всю новую карту A1–A8 внутрь Теории.
5. Не нужно снова смешивать Теорию и Handbook через decision matrix в основных главах.

## Потенциальная точечная правка skeleton

При следующем обновлении skeleton можно уточнить формулировки Part V:

```text
XI. След выполнения, проверочный материал и границы доказательства
XII. PR/MR как контур принятия: change candidate, ревью и ответственность
XIII. После merge: сопровождение, очистка состояния и обучение процесса
```

Это не новая структура, а уточнение: XII должна явно включать PR/MR и Git-backed change candidate, а не только абстрактное принятие.

## Новый gate для chapter packages

Для каждой главы Теории добавить короткий `atlas-technical-grounding check`:

```text
1. Какие технические слои Атласа питают эту главу?
2. Какие конкретные технологии/форматы нужно упомянуть, чтобы аргумент не стал пустой методологией?
3. Какие технические детали оставить Атласу?
4. Не подменяет ли глава lifecycle-разрез техническим каталогом?
```

Этот gate защищает сразу от двух ошибок:

- теория без технической опоры становится слишком общей;
- теория с избыточным техническим описанием превращается в Атлас.
