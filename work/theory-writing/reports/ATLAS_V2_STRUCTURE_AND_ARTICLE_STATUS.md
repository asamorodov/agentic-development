# Атлас V2: структура и статус статей

Статус: рабочая архитектура Атласа после жанровой коррекции A3.  
Дата: 2026-06-17.  
Основание: ADR-0012, ADR-0013, обсуждение разрезов Теории / Атласа / Handbook / Fieldbook, диагностика результата A3 и решение выделить Git/version-control в отдельный слой Атласа.

## Коррекция от 2026-06-17

Предыдущая карта A1–A5 была полезной промежуточной структурой, но слишком легко смешивала два разных разреза одной области знания:

- жизненный цикл изменения — правильный главный разрез для Теории;
- технические слои и конкурирующие способы их построения — правильный главный разрез для Атласа.

Результат A3 `От прогона к принятому изменению` показал проблему на практике. Текст получился сильным как теоретический фрагмент о смене статуса материала, но не прошёл функцию статьи Атласа: в нём не хватило технологического покрытия traces, evals, CI/status checks, PR/MR, review tooling, contract/API checks, deployment/rollback surfaces и других механизмов.

Поэтому текущий документ обновляет назначение Атласа V2: новые крупные статьи должны быть не life-cycle essays, а layer maps.

## Публичная граница

Атлас пишется как часть публичного сайта. В статьях не должно быть выводов о личном процессе разработки автора, о Новой или о конкретных будущих архитектурных решениях автора. Такие выводы можно делать отдельно, в рабочих заметках вне публичного текста.

В самих статьях допустимы общие инженерные выводы: какие классы инструментов существуют, какие различения нужны, где проходит граница между похожими формами, какие риски возникают, как меняется жизненный цикл программного изменения и почему один режим работы нельзя механически заменить другим.

## Связь с общей архитектурой корпуса

Атлас использует тот же корпус знаний, что Теория, Handbook и Fieldbook, но другой разрез.

```text
Теория — жизненный цикл изменения.
Атлас — технические слои.
Рабочие сценарии / Handbook — решения практика.
Каталог проблем и решений / Fieldbook — типовые сбои и восстановление.
```

Эта граница зафиксирована в:

```text
work/decisions/ADR-0012-shared-knowledge-genre-cuts.md
work/theory-writing/reports/CORPUS_PROJECTION_CUTS_UPDATE_2026_06_17.md
```

## Базовая форма крупной статьи Атласа

Крупная статья Атласа должна отвечать не только на вопрос «что это значит», а на вопросы «какой это технический слой», «какие способы его построения конкурируют», «какие артефакты они создают» и «как выбирать между ними».

Рабочая форма:

```text
слой
→ проблема слоя
→ классы решений
→ конкретные технологии, протоколы и форматы
→ какие артефакты они создают
→ как они работают технически
→ чем конкурирующие подходы отличаются
→ как выбирать
→ типичные сбои
→ связь с соседними слоями
```

Перед финальной сшивкой article package должен пройти technological payload gate. Если mini-dossiers не собрали реальные технологии, форматы, рабочие поверхности, артефакты, ограничения, источники и критерии выбора, финальная статья Атласа не пишется; пакет должен остановиться на добор материала.

## Уровень 1. Крупные карты технических слоёв

Эти статьи должны стоять первыми в новой навигации Атласа. Они не являются обзором рынка и не должны превращаться в каталог продуктов. Их задача — объяснить технические слои современного агентского процесса, показать конкурирующие способы построения слоя и дать критерии выбора.

Нумерация ниже рабочая. Она может быть уточнена после пересборки target-plans, но слой-ориентированный разрез считается текущим baseline.

### A1. Контекстный интерфейс проекта для агента

Слой: как агент получает рабочее знание проекта.

Внутри должны быть `AGENTS.md`, `CLAUDE.md`, Cursor Rules, GitHub Copilot custom instructions, Codex instructions, Amp instructions, Kiro steering, local task packages, skills, hooks, subagents, project docs, specs и ADR как элементы контекстного интерфейса.

Главный вопрос статьи: где хранить проектное знание, чтобы агент не каждый раз работал из пустого чата, а получал правила, процедуры, ограничения и точки остановки из поддерживаемой среды проекта.

Критерии сравнения: область действия инструкций, наследование, видимость для инструментов, поддерживаемость, риск старения, конфликты правил, noise from over-instruction и восстановление инструкций после неудачного прогона.

### A2. Рабочие поверхности coding agents

Слой: где агент реально работает над изменением.

Внутри должны быть чат, IDE-agent, CLI-agent, cloud coding agent, PR-agent, sandbox/worktree режим, local open-source agent environment, Computer Use / browser-use-подобные формы там, где они нужны для разработки.

Примеры классов: Codex, Claude Code, Cursor, GitHub Copilot coding agent, Aider, OpenHands, SWE-agent-подобные среды.

Главный вопрос статьи: когда работа должна идти в чате, когда в IDE, когда в CLI, когда в отдельной песочнице, когда через PR и когда через облачного агента.

Критерии сравнения: доступ к коду, способность запускать проверки, права на изменение, видимость diff, воспроизводимость, стоимость переключений, удобство review, риск неконтролируемых правок.

### A3. Оркестрация и фреймворки агентского исполнения

Слой: как строится управляемый агентский процесс, если одного чата, IDE или CLI уже мало.

Внутри должны быть LangGraph, OpenAI Agents SDK, Google ADK, AutoGen, CrewAI, LlamaIndex Workflows, самописные workflow runners, multi-agent orchestration, state machines / graph workflows, human-in-the-loop stops и resumable workflows.

Главный вопрос статьи: когда достаточно одного агента, а когда нужен граф, маршрутизация, роли, состояние, повторные попытки, остановки и явная оркестрация.

Критерии сравнения: состояние процесса, ветвление, tool routing, retries, interrupts, human gates, наблюдаемость, возобновление, сложность поддержки.

### A4. Инструменты, протоколы, доступы и полномочия

Слой: как агент получает техническую возможность и право действовать.

Внутри должны быть tool/function calling, MCP, A2A, connectors, sandbox permissions, approvals, secret handling, scoped access, audit logs, prompt injection, tool poisoning, boundaries of data access и organizational policy.

Главный вопрос статьи: чем отличается «агент может вызвать инструмент» от «агенту можно доверить это действие».

Критерии сравнения: субъект действия, область данных, отзыв доступа, хранение секретов, логирование, необходимость human approval, ограничение ущерба.

### A5. Наблюдаемость, traces и evals

Слой: как видеть, воспроизводить и измерять агентскую работу.

Внутри должны быть traces, spans, tool-call logs, replay/debug surfaces, LangSmith-подобные системы, Langfuse/Phoenix-подобный класс, eval harnesses, SWE-bench, regression evals, golden tasks, automated graders и run comparison.

Главный вопрос статьи: как понять, что агентская система реально делает, где она ломается и стала ли она лучше.

Критерии сравнения: что логируется, можно ли воспроизвести прогон, что считается успехом, отделяется ли качество модели от качества toolchain, можно ли сравнивать версии и какие риски остаются невидимыми.

### A6. Git, worktree и PR/MR как субстрат агентского изменения

Слой: как агентский результат получает форму change candidate, которую можно изолировать, сравнить, показать человеку, проверить, обсудить, принять, отклонить, откатить и использовать как provenance.

Внутри должны быть Git, branch, worktree, index, commit, history, diff, patch, merge, squash, rebase, cherry-pick, conflict surface, PR/MR, linked issue, review state, audit trail, revert, rollback, bisect, file restore и multi-agent branches/worktrees.

Главный вопрос статьи: почему для агентской разработки Git/version-control перестаёт быть фоновым механизмом и становится техническим субстратом изменения.

Критерии сравнения: изоляция задачи, возможность параллельной работы агентов, размер изменения, частота checkpoint-ов, чистота истории, surface для review, возможность отката, риск semantic conflicts, совместимость с PR/CI/review контуром.

Важно: эта статья отделена от CI/review/acceptance tooling. Git/PR/MR оформляют материал изменения; CI, status checks, review и merge rules применяют к нему дополнительные gates. См. `work/decisions/ADR-0013-git-version-control-agentic-change-substrate.md` и `work/theory-writing/reports/VERSION_CONTROL_AGENTIC_DEVELOPMENT_COVERAGE_NOTE_2026_06_17.md`.

### A7. CI, status checks, review и acceptance gates

Слой: как уже оформленный change candidate проходит через технические и человеческие gates перед принятием, отклонением или доработкой.

Внутри должны быть CI, test reports, coverage, lint/typecheck/security scans, required status checks, protected branches, rulesets, merge queue, CODEOWNERS, review comments, approvals, requested changes, AI review tools, contract/API compatibility checks, deployment gates, post-merge monitoring и incident/revert feedback.

Главный вопрос статьи: как agent output после оформления в branch/PR/MR получает проверочные сигналы, review surface и решение о дальнейшем статусе.

Критерии сравнения: сила технических gate-ов, прозрачность logs, связь check-ов с конкретным риском, false positives/false negatives review tooling, human review burden, возможность восстановления после ошибочного merge, разделение `право запустить проверку`, `право слить` и `право признать изменение завершённым`.

Текущий результат `agent_run_to_accepted_change` не считается готовой статьёй этого слоя. Он полезен как theory-ready fragment о смене статуса материала, но для A7 требуется новый technical-dossier package с технологическим payload.

### A8. Спецификации, планы и исполняемые процессные артефакты

Слой: как намерение превращается в управляемую работу до кода и вокруг кода.

Внутри должны быть Spec Kit, Kiro specs, ADR, SPDD, BMAD/GSD/TDAD-подобные методологии, issue templates, task packages, acceptance criteria, executable specs и handoff docs.

Главный вопрос статьи: какие формы позволяют агенту не просто писать код, а работать по заданному процессу, с критериями принятия, границами изменения и материалом для продолжения.

Критерии сравнения: насколько артефакт задаёт намерение, контракт, порядок работы, границы изменения, проверку, передачу состояния и возможность исправления процесса.

## Подробная карта для будущих планов

Подробное наполнение новых статей уровня A вынесено в рабочую карту:

```text
work/atlas/plans/ATLAS_V2_LAYER_ARTICLE_MAP.md
```

Именно из неё нужно строить новые target-group plans для A1–A8. Этот status report фиксирует архитектуру и статус, но не должен быть единственным источником для пакета. Если будущий пакет статьи Атласа не использует подробную карту A1–A8, он рискует снова уйти в соседний жанр: теоретическую статью, каталог продуктов или практические Рабочие сценарии.

Каждый план статьи должен явно перенести из подробной карты: обязательные темы, очередь мини-досье, артефакты слоя, критерии выбора и границы.

## Статус прежних A1–A5

Прежние target-plans A1–A3 и старый список A1–A5 считать историческим промежуточным состоянием, пока они не пересобраны под слой-ориентированный разрез.

- A1 ближе остальных к правильному Атласному жанру, но при продолжении всё равно должен пройти technological payload gate.
- A2 в старой форме смешивал рабочие поверхности и оркестрационные frameworks; его лучше разделить на новые A2 и A3 или явно удерживать различие внутри одной статьи, если будет принято не расширять число статей.
- A3 в завершённом результате считается theory-ready fragment, но не принятой статьёй Атласа.
- A4 тематически сохраняется, но должна быть технической статьёй про protocol/access/security layer, а не общей философией полномочия.
- A5 `Генеалогия агентского цикла` полезна как справочный или исторический материал, но не должна вытеснять технические слои Атласа.

Старые executor packages по этим статьям нельзя запускать как актуальные без пересборки и явного жанрового gate-а.

## Уровень 2. Концептуальные механизмы и методологические режимы

Эти статьи остаются самостоятельными. Они уже написаны в формате «одна методология или один механизм — одна статья» и по-прежнему полезны как глубокие узлы Атласа.

### SPDD

Статус: концептуальный механизм / методологический режим.  
Роль: спецификационный жизненный цикл изменения.  
Связи: Теория через жизненный цикл спецификации; A8 через спецификации и process artifacts; A1 через инструкции и рабочее знание проекта.

### Persistent Work Graph

Статус: концептуальный механизм.  
Роль: рабочее состояние, которое можно продолжить.  
Связи: Теория через сохранение и передачу состояния; A3 через durable orchestration; A5 через traces/evals; A6 через change candidate и material after run.

### ADR

Статус: методологический узел.  
Роль: фиксация решений и архитектурная память изменения.  
Связи: Теория через intent/decision lifecycle; A1 через превращение повторяющихся решений в инструкции проекта; A8 через process artifacts.

## Уровень 3. Высоконагруженные частные формы

Эти статьи или разделы не являются универсальными методологиями верхнего уровня, но через них хорошо видны важные проблемы агентской разработки.

### Gas Town / Beads

Статус: частная, но плотная форма.  
Роль: пример того, как много агентских работ требует координации, сервисных ролей, общей рабочей картины и правил возврата результата.  
Связи: Теория через организационно-операционный жизненный цикл; A3 через orchestration; A7 через принятие результатов отдельных work items.

Gas Town не нужно ставить рядом с SPDD или Persistent Work Graph как методологию того же уровня. Его ценность в другом: он показывает операционную сторону параллельной агентской работы лучше многих абстрактных описаний.

### Kiro Specs

Статус: частная форма / вспомогательное досье.  
Роль: продуктовая упаковка агентской разработки через спецификации.  
Связи: Теория через спецификационный режим; A1 через steering; A2 через IDE/work surface; A8 через process artifacts.

### Spec Kit

Статус: частная форма / вспомогательное досье.  
Роль: спецификационный режим и границы изменения.  
Связи: Теория через спецификацию; A8 через executable/process artifacts.

### OpenHands / SWE-agent

Статус: разделы внутри A2 и A5; отдельная статья пока не нужна.  
Роль: открытая рабочая обвязка и интерфейс между агентом и компьютером.  
Связи: A2 через рабочие поверхности; A5 через traces/evals; A6 через превращение результата в change candidate.

OpenHands и SWE-agent полезны не как очередные продукты в каталоге, а как примеры того, как агент получает рабочую среду: файлы, командную строку, тесты, навигацию по репозиторию, журнал действий и возможность воспроизводимого сравнения.

### Рабочие случаи Claude Code / Codex

Статус: не планировать как отдельные статьи сейчас.  
Роль: отдельные рабочие случаи могут появляться в Handbook или в практических разделах, если они понадобятся. В Атласе их лучше не плодить без сильного концептуального основания.

## Уровень 4. Вспомогательные досье и частные методологические формы

Эти статьи не нужно удалять. Они могут использоваться как источник для крупных карт, для теории и для будущего Handbook. Но в новой навигации Атласа они не должны автоматически стоять на одном уровне с layer maps.

- GSD / Open GSD — вспомогательное досье для режима продолжения работы и выбора следующего шага.
- BMAD — вспомогательное досье для организации следующего шага и упаковки работы.
- TDAD — вспомогательное досье для защищающих спецификаций.
- Constitutional SDD — вспомогательное досье для правил, ограничивающих изменение.

## Порядок дальнейшей работы

1. Не продолжать старую A3 как статью Атласа лёгкой правкой. Сначала сохранить её как theory-ready fragment и отдельно пересобрать технический слой.
2. Пересобрать карту Level 1 под слой-ориентированный разрез и решить, остаётся ли число статей равным пяти или расширяется до A1–A8.
3. Для каждой будущей статьи Атласа сначала собрать технические mini-dossiers, затем relationship map, затем выполнить technological payload gate.
4. Только после gate писать финальную статью.
5. Если статья начинает строиться по жизненному циклу изменения, а не по техническому слою, пакет должен остановиться и зафиксировать жанровую подмену.

## Как теория должна использовать Атлас

Атлас объясняет слой как самостоятельный объект. Теория использует этот слой как аргумент внутри жизненного цикла изменения.

Например, статья про рабочие поверхности агентов может подробно описывать CLI, IDE, cloud agent, sandbox/worktree и PR-agent. Теоретическая глава об execution environment не должна повторять всю статью. Она должна взять нужный срез: выбор среды исполнения является выбором прав, видимости, воспроизводимости, переносимости, стоимости review и ответственности.

Статья про Git/PR/CI/review может подробно разобрать ветки, worktrees, PR, status checks, merge queue, review comments и rollback. Теоретическая глава о принятии изменения должна взять из неё другой срез: как рабочий результат получает форму, которую можно проверить, обсудить и принять, но не должна превращаться в справочник GitHub/GitLab workflow.
