# Field-map structural revision proposal — 2026-06-16

Статус: рабочее предложение для обсуждения, не принято как новый активный скелетон.  
Основание: приложенный research-output `practical_agentic_dev_field_map_outputs.zip` и последующий чат пользователя, который ещё не был внесён в `work/discourse.md`.

## 1. Почему этот документ нужен

После coverage-аудита и отдельного исследовательского прохода по карте поля стало понятно, что риск «ещё через два дня найдётся важный слой» не снимается простым перечислением новых источников. Область агентской разработки сейчас собирается сразу из нескольких миров: ранние работы об агентском цикле, продукты кодовых агентов, IDE/terminal/cloud PR-поверхности, фреймворки исполнения, инструкции репозитория, протоколы, наблюдаемость, безопасность и эмпирические исследования PR.

Главная цель труда при этом остаётся пользовательской и практической: не написать историю агентских систем, а разобраться, как выстроить собственный dev-cycle в эпоху агентских инструментов. История вопроса нужна только как методологическая оптика; современные способы разработки, инструменты, режимы работы, ограничения, проверки и интерфейсы интересуют напрямую.

## 2. Исправление прежнего вывода

Исходный research-output осторожно формулировал: «структурную ось труда не менять; достаточно локальных вставок и расширений глав». После обсуждения это решение уточнено.

Актуальная позиция:

```text
Корневую ось менять не нужно, но структуру подачи менять нужно.
```

Корневая ось остаётся прежней:

```text
программное изменение → намерение → спецификация → исполнение → рабочее состояние → проверка → принятие → сопровождение
```

Но если просто расширять существующие главы, новые материалы будут выглядеть как поздние заплаты: «кстати, есть LangGraph», «кстати, есть AGENTS.md», «кстати, есть agent-authored PR studies». Это угрожает связности текста. Поэтому нужен средний структурный пересмотр: сохранить жизненный цикл изменения как главный предмет, но добавить видимую карту современного поля и сгруппировать главы по крупным частям.

## 3. Что именно меняется

### 3.1. Добавляется видимая вступительная карта поля

Перед основной теорией нужен короткий, но структурно заметный блок:

```text
0a. Карта современного поля: от агентского цикла к агентской разработке
```

Его задача — не делать обзор всех frameworks, а объяснить, почему дальше теория идёт не по продуктам и библиотекам, а по жизненному циклу изменения. В этой карте должны появиться:

- ReAct / MRKL / Toolformer / Reflexion / Tree of Thoughts как генеалогия агентского цикла;
- coding-agent surfaces: terminal, IDE, cloud PR, spec-driven IDE, open harness, app-builder;
- repository instructions: `AGENTS.md`, `CLAUDE.md`, Cursor Rules, Kiro steering, skills, hooks, subagents, MCP;
- фреймворки исполнения: LangGraph, LangSmith, OpenAI Agents SDK, Google ADK, AutoGen, CrewAI, LlamaIndex Workflows;
- protocol/security layer: MCP, A2A, identity, authorization, consent, audit, revocation;
- observability/evaluation/provenance;
- эмпирические исследования PR и конфигурационных практик.

### 3.2. Главы группируются в части

Новая структура подачи:

```text
Вступительная часть
  0. Зачем этот труд: мой dev-cycle, а не обзор AI agents
  0a. Карта современного поля: от агентского цикла к агентской разработке

Часть I. Программное изменение как единица работы
  I. Единица анализа: программное изменение под агентами
  II. Агентская сессия и её след
  III. Намерение, спецификация и контракт изменения
  IV. SPDD и жизненный цикл спецификации
  V. Границы изменения и защищающие спецификации

Часть II. Проект как рабочая среда для агента
  VI. Репозиторий как интерфейс для агента
  VII. Persistent Work Graph: рабочее состояние, которое можно продолжить
  VIII. Как продолжать работу под контролем

Часть III. Исполнение, координация и среда
  IX. Среда исполнения, права и границы действия
  X. Когда агентов становится много: координация параллельной работы

Часть IV. Проверка, принятие и обучение процесса
  XI. Проверочный материал: что подтверждено и что осталось неизвестным
  XII. Принятие результата, ответственность и внешний контур
  XIII. После merge: сопровождение, очистка состояния и обучение процесса

Заключение
  Карта выбора режима работы
```

Это не отменяет уже написанные главы, но меняет их рамку: читатель должен видеть движение от единицы работы к среде проекта, затем к исполнению и координации, затем к проверке, принятию и обучению процесса.

### 3.3. Глава VI меняет центр тяжести

Глава VI больше не должна выглядеть как глава «про skills, MCP, subagents и hooks». Её предмет:

```text
Репозиторий как интерфейс для агента.
```

Внутри неё инструменты получают функции:

- `AGENTS.md`, `CLAUDE.md`, Cursor Rules, Kiro steering — постоянные инструкции проекта;
- skills — повторяемые процедуры;
- MCP — внешний интерфейс ресурсов и действий;
- subagents — вынесение части работы отдельному исполнителю;
- hooks — контрольные точки и вмешательство проекта;
- task package — переносимый интерфейс конкретной работы.

### 3.4. Runtime не подменяет рабочее состояние проекта

Для глав VII–IX нужно закрепить различение:

```text
runtime state / execution graph ≠ project working state / Persistent Work Graph
```

LangGraph, ADK, OpenAI Agents SDK и близкие системы могут хранить состояние выполнения, трассировку, handoffs, interrupts, sessions и memory. Но это ещё не говорит, что проект теперь знает, какие решения приняты, какие долги остались, какие файлы стали каноничными, какие проверки дают основание продолжать и что должен прочитать следующий исполнитель.

### 3.5. Проверка и принятие должны опираться на empirical PR reality

Главы XI–XIII ещё не должны писаться как абстрактная философия ответственности. Их нужно строить с учётом исследований agent-authored PR: какие задачи чаще проходят, где агенты ошибаются, почему PR отклоняются, как меняется нагрузка на ревью, что происходит с documentation/CI/build-задачами, stale context, duplicate PR, unwanted features и слабым взаимодействием с ревьюерами.

## 4. Новая очередь статей Атласа

Эта очередь не должна быть каталогом всего поля. Она должна закрывать то, с чем пользователю нужно познакомиться для собственного dev-cycle и для усиления теоретического труда.

### A1. Репозиторий как интерфейс для агента: инструкции, skills, hooks, subagents и MCP

Главная статья. Она должна разобрать `AGENTS.md`, `CLAUDE.md`, Cursor Rules, Kiro steering, GitHub custom instructions, Codex/Amp instructions, skills, hooks, subagents, MCP, scope, conflicts, nested instructions, исправление после неудачного прогона и tool-specific adapters.

Практический результат: понять, как должен выглядеть root `AGENTS.md`, что должно жить в task package, а что — в tool-specific layer.

### A2. Экосистема LangChain: агентский цикл, граф исполнения и наблюдаемость

Статья про LangChain / LangGraph / LangSmith как связку:

```text
agent harness → graph runtime → observability/evaluation/deployment
```

Ключевое различение: LangGraph хранит и исполняет состояние агентского процесса; PWG хранит состояние работы над изменением. Это пересекающиеся, но разные объекты.

### A3. След выполнения — не доказательство: трассировка, provenance, evals и проверочный материал

Статья к главе XI. Нужно развести trace, run log, tool output, eval, benchmark, test, review, static verification, acceptance record и provenance. Главная мысль: след выполнения помогает понять ход работы, но не доказывает корректность и не заменяет принятие.

### A4. AI-authored PRs in the wild: что реально происходит с агентскими pull request

Статья для глав XII–XIII и для практической трезвости. Внутри: task-type success differences, причины отказа, review burden, stale context, duplicate work, сильные стороны documentation/CI-задач и слабые стороны bug-fix/performance-задач, human merge governance.

### A5. MCP и A2A: интерфейс инструментов, связь агентов и границы полномочий

MCP связывает агента с инструментами и ресурсами; A2A — агента с другим агентом. Но протокол не равен праву действовать. Статья должна разложить identity, authorization, delegation, secrets, consent, revocation, audit, prompt injection и tool poisoning.

### A6. Coding-agent surfaces: terminal, IDE, cloud PR, spec-driven IDE, open harness, app-builder

Практическая карта поверхностей работы, не обзор вендоров. Примеры: Claude Code / Codex CLI / Aider / Amp, Cursor / Junie / Copilot IDE, Copilot coding agent / Codex cloud / Jules, Kiro, OpenHands / SWE-agent, Replit Agent.

Практический результат: будущая таблица выбора режима работы в заключении и Handbook.

### A7. ReAct → Toolformer → Reflexion: ранняя агентская петля как методологическая генеалогия

Короткая статья. Она нужна, чтобы не было понятийной дыры между LLM-as-answer-generator и coding agent. Не делать из неё историю всей области.

### A8. OpenAI Agents SDK / Google ADK / AutoGen / CrewAI: фреймворки исполнения как инженерная обвязка агента

Сравнительная статья после A2. Она должна показать agents, tools, handoffs, graph workflows, human-in-the-loop, sessions, memory, tracing, evaluation и deployment. Граница: runtime framework не равен полному dev-cycle.

### A9. Kiro Specs как продуктовая форма spec-driven agentic development

Не новая статья с нуля. Это audit/extension существующей статьи про Kiro. Нужно проверить, достаточно ли там раскрыт Kiro как продуктовая упаковка spec-driven development: requirements, design, tasks, steering, hooks, powers. Если нет — расширить существующую статью.

### A10. Instructions-as-Code в реальной практике: почему инструкции могут помогать и вредить

Вероятно, это расширение A1, а не отдельная статья. Если A1 станет слишком большой, стоит вынести отдельно: файлы инструкций — рабочие артефакты процесса, а не магия. Больше инструкций не всегда лучше; качество, scope и maintenance важнее объёма.

## 5. Рекомендуемый порядок знакомства для практической цели пользователя

1. **A1 — Репозиторий как интерфейс для агента.** Самая прямая связь с текущим package-driven workflow.
2. **A6 — Coding-agent surfaces.** Помогает выбирать, где запускать задачу: чат, терминал, IDE, cloud PR, spec-driven IDE, harness, app-builder.
3. **A3 — След выполнения — не доказательство.** Нужна для главы XI и для практического понимания проверочного материала.
4. **A2 — Экосистема LangChain.** Нужна, чтобы правильно отделить runtime graph от рабочего состояния проекта.
5. **A4 — AI-authored PRs in the wild.** Reality check для cloud PR agents и ответственности за merge.
6. **A5 — MCP/A2A.** Нужна перед серьёзной работой с connector/action layer.
7. **A7 — ранняя генеалогия агентского цикла.** Полезно для введения и понятийной карты, но не первый практический приоритет.
