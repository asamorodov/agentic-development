# Атлас V2 — рабочая карта статей технического слоя

Статус: рабочая карта для планирования пакетов Атласа.  
Дата: 2026-06-17.  
Основание: ADR-0012–ADR-0019 и `ATLAS_V2_SKELETON.md`.

## Назначение

Этот документ нужен для сборки планы целевых групп и исполнительные пакеты. Он не заменяет Скелетон Атласа: Скелетон удерживает композицию всей части, а эта карта говорит, что именно нужно собрать по каждой статье.

Главное правило остаётся простым: статья Атласа строится по техническому слою. Она должна показывать технологии, форматы, протоколы, рабочие поверхности, артефакты, ограничения и критерии выбора. Хорошая концептуальная статья без этого наполнения не считается принятой статьёй Атласа.

## Общая форма статьи

Каждая статья уровня A должна пройти одну и ту же рамку:

```text
слой и его задача
→ классы решений
→ конкретные технологии, протоколы, форматы и рабочие поверхности
→ артефакты, которые они создают или меняют
→ техническая логика работы
→ отличия конкурирующих подходов
→ критерии выбора
→ типовые сбои
→ связи с соседними слоями
```

Перед финальной сшивкой пакет должен пройти проверку технического наполнения. Если собраны только красивые рассуждения, а не карточки источников и фактов, технологическая матрица и артефакты слоя, финальную статью писать рано.

## A1. Контекстный интерфейс проекта для агента

**Задача слоя.** Показать, где в проекте живут явные правила, процедуры и рабочие знания, по которым агент должен действовать. Агент не должен каждый раз начинать из пустого чата: у него должна быть поддерживаемая проектная среда, из которой он узнаёт стиль, ограничения, источники правды, точки остановки и способы восстановления после ошибки.

**Что собрать перед написанием.** AGENTS.md, CLAUDE.md, Cursor Rules, GitHub Copilot custom instructions, Codex/Amp instructions, Kiro steering, skills, hooks, subagents, project docs, specs, ADR, локальные task packages, манифесты источников, acceptance criteria, заметки о ремонте.

**Какие карточки источников и фактов нужны.**

1. Карточки основных классов решений: что это за подход, какие задачи он закрывает, какие ограничения имеет.
2. Карточки конкретных инструментов, протоколов или форматов: что они делают, какие артефакты создают, чем отличаются от соседних решений.
3. Карточки типовых сбоев: что обычно ломается, какие следы остаются, какой слой должен чинить проблему.
4. Карточки выбора: когда подход подходит, когда его лучше не брать, какие условия проекта меняют решение.

**Технологическая матрица.** Для этой статьи нужна матрица: класс решения / конкретная технология / входы / выходные артефакты / где живёт состояние / как проверяется / ограничения / когда выбирать / источники.

**Артефакты слоя.** инструкционные файлы, вложенные правила, steering-документы, skill-файлы, hook-конфигурации, профили subagents, рабочие пакеты, манифесты источников, критерии принятия, заметки о ремонте правил.

**Критерии выбора.** одноразовая задача или повторяемый процесс; один инструмент или несколько агентов; важность наследования правил; что держать в инструкции, а что вынести в документы; где будет фиксироваться урок после сбоя.

**Граница статьи.** A1 говорит о явных проектных правилах. Поиск по кодовой базе относится к A10, память прошлых сессий — к A12, организационная карта сервисов — к A16.

**Артефакты слоя.** workflow graph, node/edge, state object, решение о маршруте, tool call, handoff, checkpoint, interrupt, retry record, agent role, маркер возобновления, trace link.

**Граница статьи.** Не писать историю ReAct и не делать рейтинг фреймворков. Статья сравнивает orchestration patterns и причины, по которым слой становится нужен.

## A7. CI, status checks, review и контуры принятия

**Задача слоя.** Показать, как оформленный change candidate проходит технические и человеческие проверки перед принятием, отклонением или возвратом на доработку.
