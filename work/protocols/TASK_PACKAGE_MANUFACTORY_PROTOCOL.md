# Протокол пакетной мануфактуры

Статус: рабочая спецификация для механической сборки исполнительных пакетов из уже подготовленных планов целевых групп.

Назначение: отделить смысловое проектирование пакетов от их механической сборки. Этот протокол применяется, когда планы целевых групп уже написаны, проверены и приняты, а следующая задача — собрать по ним self-contained Python-gated пакеты и положить их в файловую систему.

## Основной принцип

Пакетная мануфактура не пишет теорию, не выбирает источники заново и не улучшает prompt-очереди. Она выполняет сборочную работу: берёт принятый `*_TARGET_GROUP_PLAN.md`, берёт перечисленные в нём источники и создаёт отдельный исполнительный пакет.

Если нужно улучшить план целевой группы, это делается до мануфактуры. Сборщик не должен чинить смысл плана по ходу сборки.

## Входы

Обычные входы мануфактуры:

- принятые планы целевых групп из `work/theory-writing/target-group-plans/`;
- протокол создания пакетов-заданий;
- протокол очередей writing-prompt-ов;
- шаблон плана целевой группы;
- все внутренние файлы, на которые ссылаются выбранные планы;
- общий read-only source bundle, если пакет мануфактуры self-contained.

Для одного собранного пакета имя архива берётся из имени плана без суффикса `_TARGET_GROUP_PLAN`:

```text
A2_SPECIFICATION_ADR_CONTRACT_TARGET_GROUP_PLAN.md
→ work/theory-writing/packages/A2_SPECIFICATION_ADR_CONTRACT.zip
```

Если пакет собирается из нескольких планов, имя должно описывать объединённую группу, а manifest обязан перечислить входящие планы.

## Механическая схема

Для мануфактуры с несколькими пакетами предпочтительна простая последовательность:

1. материализовать общий read-only source bundle;
2. по одному шагу собрать каждый пакет из одного плана;
3. после каждого пакета выполнить smoke-test первого и второго перехода runner-а;
4. в финале проверить все zip-архивы, записать manifest, verification report и resume note.

Не надо вести отдельный сложный реестр “источник → пакет”, если исходные планы уже содержат точные списки файлов для чтения. Безопаснее материализовать общий source bundle и дать каждому writing-пакету взять из него те файлы, которые указаны в его плане.

## Требования к собранному пакету

Собранный пакет должен быть self-contained, если явно не указано обратное. Он должен содержать `START.md`, generic Python-runner, opaque payload, нужные источники внутри payload, уникальные имена материализованных рабочих листов и финальную запись проверки/упаковки.

В обычный исполнительный режим пакет не должен содержать открытый `TARGET_PLAN_SNAPSHOT.md`, полный список будущих проходов, финальный список артефактов или список критериев готовности. Полный target plan остаётся вход этапа сборки мануфактуры; в архив может попасть только короткий public contract без будущей очереди и финальной карты результата.

Видимый runner не должен содержать списки документов, названия планов, имена досье, `docs × passes`, `map_task`, финальную предметную логику или тексты внутренних prompt-ов.


## Стадийность при сборке

Мануфактура должна поддерживать внешний параметр стадийности: `stage_count` или `max_passes_per_stage`. Этот параметр не меняет принятый target-group plan и не переписывает prompt-очередь; он только нарезает уже принятую очередь на запланированные остановки.

Для тяжёлых writing-пакетов, особенно глав теории, сборщик должен по умолчанию рассмотреть staged mode. Если пользователь задаёт количество стадий, package должен включать stage-stop records, stage-result archives, протокол продолжения и emergency/resume instructions. На границе стадии пакет не должен автоматически материализовать следующий рабочий лист в том же действии.

Если ожидается работа обычной модели или жёсткие лимиты по времени/сообщениям, мануфактура должна предложить отдельные stage packages как более надёжный режим: следующая стадия выдаётся только после проверки предыдущей.

## Защита от подсматривания и правила продолжения после обрыва

Каждый собранный пакет должен явно запрещать исполнителю декодировать будущие записи payload, читать runner source ради будущих шагов, восстанавливать отсутствующие pass outputs по памяти, создавать будущие pass reports пачкой и финализировать результат до финального рабочего листа.

`START.md` и рабочие листы должны объяснять: любой пустой или невнятный ввод пользователя после обрыва означает продолжить последний реальный рабочий лист или один раз запустить runner для следующего листа, если required output уже существует. Такой ввод не означает разрешение прыгнуть к финалу.

Emergency mode должен создавать не только архив, но и диагностический `INTERRUPTION_STATE.md`: текущая запись, текущая стадия, последний рабочий лист, required output текущего листа, статус exists/missing и последние изменённые файлы.

## Проверка собранного пакета

Для каждого собранного пакета обязательны базовые проверки: `unzip -t`, первый запуск runner-а создаёт рабочий лист, видимый Python не раскрывает предметную структуру задания, в архиве нет открытого полного target plan, а `START.md` не раскрывает финальный состав результата.

Для короткого нестадийного пакета допустим быстрый smoke-test первых переходов. Для длинных, стадийных или перестроенных пакетов этого недостаточно. Перед выдачей такого пакета мануфактура должна провести полный сухой прогон runner-цепочки: последовательно запускать runner, создавать пустые заглушки обязательных выходов текущего листа, проверять следующий переход, проходить stage-stop через штатный `continue` и дойти до финальной записи. Сухой прогон проверяет не качество текста, а целостность очереди и зависимостей.

Во время сухого прогона ни одна запись не должна требовать файл, который появится только в будущей записи. Каждый required file должен быть исходным файлом пакета или результатом одного из уже пройденных рабочих листов. Если runner требует будущий файл, прыгает через часть очереди, не останавливается на плановой границе или после `continue` начинает не с той записи, пакет считается failed и должен быть пересобран.

Результаты проверки фиксируются в `PACKAGING_VALIDATION.md` и в итоговом manifest мануфактуры: сколько записей в очереди, где стоят плановые остановки, какова максимальная длина участка между остановами, прошёл ли полный сухой прогон, были ли проблемы с required files, stage-stop/continue или аварийным режимом.

Если проверка не проходит, пакет нельзя выдавать как готовый. Нельзя скрывать это в финальном manifest.

## Аварийная упаковка

Пакет мануфактуры должен поддерживать аварийную упаковку текущего состояния: все уже собранные zip-архивы, текущие рабочие файлы, отчёты, state, последний материализованный рабочий лист, `INTERRUPTED.md` и `RESUME.md`. Это не нормальное завершение, а способ вернуть пользователю всё, что уже есть в файловой системе.

## Что не делает мануфактура

Мануфактура не заменяет target-group planning, source-pass, writing-pass, language-pass или repair-pass. Она не должна улучшать главы, дописывать источники, менять композиционную функцию узлов или переписывать prompt-очереди. Если такие изменения нужны, надо вернуться к планам целевых групп, а не чинить их внутри сборочного пакета.
