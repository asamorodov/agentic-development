# Скелетон пересборки теоретического синтеза — v6 field-map proposal

Статус: предложение для обсуждения, не активный скелетон.  
Дата: 2026-06-16.  
Основание: Skeleton V5 после Атласа, `AGENTIC_AI_COVERAGE_AUDIT_2026_06_16.md`, research-output `practical_agentic_dev_field_map_outputs.zip` и последующее решение из чата.

## Главное решение

Корневая ось труда сохраняется:

```text
агентская разработка меняет жизненный цикл программного изменения
```

Но структура подачи меняется. Нужно не просто добавить в старые главы вставки про ReAct, AGENTS.md, LangGraph, LangSmith, OpenAI Agents SDK, Google ADK, MCP/A2A и agent-authored PR. Тогда текст станет рыхлым и будет выглядеть как теория, к которой поздно пришили современную индустриальную карту.

Новая задача скелетона: сохранить глубокую линию программного изменения и одновременно явно показать, где она стоит внутри современного поля agentic development.

## Вступительная часть

### 0. Зачем этот труд: собственный dev-cycle, а не обзор AI agents

Труд должен сразу поставить практическую цель: понять, как выстроить собственный цикл разработки в эпоху агентских инструментов. Он не является историей агентских систем и не является обзором всех frameworks. История нужна только как методологическая оптика: откуда пришли нынешние формы, какие проблемы повторяются, какие решения начинают становиться стандартом.

Главный вопрос:

```text
Как организовать программное изменение так, чтобы агентское действие было продолжимым, проверяемым, восстанавливаемым и принимаемым?
```

### 0a. Карта современного поля: от агентского цикла к агентской разработке

Этот блок должен быть структурно видимым. Он защищает теорию от замкнутости в собственных опорных кейсах и developer stories.

Он показывает несколько слоёв поля:

1. **Генеалогия агентского цикла.** ReAct, MRKL, Toolformer, Reflexion, Tree of Thoughts показывают переход от модели, которая сразу отвечает, к модели, которая рассуждает, действует через инструмент, получает результат, исправляет следующий ход и иногда сравнивает варианты.
2. **Поверхности coding-agent работы.** Терминальный агент, IDE-agent, cloud issue-to-PR agent, spec-driven IDE, open harness, app-builder. Это разные рабочие режимы, а не просто разные продукты.
3. **Репозиторий как интерфейс.** `AGENTS.md`, `CLAUDE.md`, Cursor Rules, Kiro steering, skills, hooks, subagents и MCP показывают, что проект начинает содержать инструкции, процедуры и доступы для агента.
4. **Исполнение и оркестрация.** LangGraph, OpenAI Agents SDK, Google ADK, AutoGen, CrewAI, LlamaIndex Workflows и близкие системы дают graph execution, sessions, handoffs, memory, human-in-the-loop, tracing и deployment.
5. **Протоколы и права.** MCP и A2A расширяют каналы действия и коммуникации, но не решают автоматически identity, authorization, consent, secrets, audit и revocation.
6. **Наблюдаемость и проверка.** Traces, run logs, evals, benchmarks, state-diff contracts, tests и reviews относятся к разным слоям проверочного материала.
7. **Реальность PR.** Agent-authored PR studies показывают, какие задачи агенты чаще доводят до merge, где проваливаются, как меняется нагрузка на ревью и почему результат остаётся социально-техническим объектом принятия.

После этой карты теория объясняет, почему дальше она идёт не по продуктам, а по жизненному циклу изменения.

## Часть I. Программное изменение как единица работы

### I. Единица анализа: программное изменение под агентами

Глава задаёт главный масштаб анализа. Единица — не prompt, не model call, не tool call, не agent framework и не diff. Единица — изменение, которое проходит через намерение, спецификацию, исполнение, проверочный материал, принятие и сопровождение.

Сохранить главный тезис уже написанной главы I: локальные действия агента получают ценность только тогда, когда складываются в принятое изменение рабочего состояния проекта.

### II. Агентская сессия и её след

Глава объясняет, что сессия даёт материал восстановления, но не равна памяти проекта и не доказывает правильность результата.

Добавить различение слоёв:

- запись диалога;
- журнал выполнения: файлы, команды, правки, проверки;
- техническая трасса runtime: model calls, tool calls, handoffs, spans, guardrail events;
- проверочный материал;
- запись принятия или отказа.

След выполнения помогает понять, что происходило. Он не говорит сам по себе, что результат можно принять.

### III. Намерение, спецификация и контракт изменения

Глава связывает намерение пользователя с проверяемой формой работы. Агенту нельзя давать только желание: нужно определить, что меняется, почему, где границы, какие обещания даёт результат, какие решения уже приняты и какие варианты отклонены.

ADR, specifications, design notes и change contracts важны как носители смысла между человеком, агентом и будущей сессией. Здесь можно добавить короткий мост: повторяющиеся решения или ограничения могут позже становиться repository instructions.

### IV. SPDD и жизненный цикл спецификации

SPDD остаётся главным anchor case для спецификационного жизненного цикла. Глава показывает, что спецификация — не предварительная бюрократия, а рабочая поверхность, через которую намерение становится видимым, проверяемым и синхронизируемым с кодом.

После исследовательского прохода по карте поля стоит точечно показать, что spec-driven agentic development выходит в продукты: Kiro и близкие spec-driven IDE/workflow forms превращают requirements/design/tasks в видимый пользователю workflow агентской разработки. Но глава не должна превращаться в статью о Kiro.

### V. Границы изменения и защищающие спецификации

Глава объясняет, что спецификация должна не только описывать желаемый результат, но и ограничивать отклонения. Чем больше агент может менять, тем важнее заранее заданные инварианты, запреты, stop conditions, allowed files, allowed tools, test gates и human decision points.

Spec Kit, Constitutional SDD, TDAD и близкие формы показывают разные способы сделать границы видимыми.

## Часть II. Проект как рабочая среда для агента

### VI. Репозиторий как интерфейс для агента

Это ключевое изменение Skeleton V6. Глава VI больше не является главой про отдельные mechanisms. Её предмет — проект как agent-facing environment.

Внутренняя логика главы:

1. **Постоянные инструкции проекта.** `AGENTS.md`, `CLAUDE.md`, Cursor Rules, GitHub custom instructions, Kiro steering и близкие формы.
2. **Повторяемые процедуры.** Skills и шаги task package как способ не писать одно и то же заново.
3. **Внешний интерфейс ресурсов и действий.** MCP as a tool/resource boundary.
4. **Делегирование части работы.** Subagents — это изоляция роли и контекста, а не магическое параллельное мышление.
5. **Контрольные точки.** Hooks — точки вмешательства проекта до действия, после действия, при проверке или при завершении.
6. **Исправление инструкций после проблем.** Ошибка агентского прогона должна иногда чинить не только код, но и инструкции, task package, проверочный барьер or allowed-action boundary.

Главная мысль: инструкции репозитория — не украшение промпта. Это рабочий слой процесса, который нужно писать, проверять, чинить, удалять и версионировать.

### VII. Persistent Work Graph: рабочее состояние, которое можно продолжить

Глава сохраняет фокус на durable working state. PWG нужен не потому, что агент не может написать summary, а потому что summary не хранит статус работы как проектный объект.

Добавить защитное различение:

```text
runtime graph / runtime state ≠ project working state
```

LangGraph-style graph может знать, где остановился агентский workflow, какой node вызвал tool и где произошёл interrupt. PWG должен знать другое: какие решения приняты, какие документы актуальны, что готово, что заблокировано, какие проверки есть, какие долги остались и что следующая сессия может считать основанием.

### VIII. Как продолжать работу под контролем

Глава объясняет, что найденное состояние ещё не говорит, какой следующий ход допустим. Иногда нужно уточнить спецификацию, иногда провести review, иногда запустить ограниченную правку, иногда остановиться и вернуть решение человеку.

GSD, BMAD и близкие формы процесса важны как способы выбирать режим продолжения: роль, фаза, обязательные материалы, разрешённые действия, граница изменения, stop conditions и recovery path.

## Часть III. Исполнение, координация и среда

### IX. Среда исполнения, права и границы действия

Глава показывает, что агентская работа становится реальной там, где агент получает среду исполнения: файловую систему, shell, browser/devtools, container/worktree, MCP servers, external APIs, CI, secrets и network access. Но техническая возможность выполнить действие не равна праву его выполнить.

Новые обязательные различения:

- протокол не равен разрешению на действие;
- tool surface не равен data ownership;
- identity и delegated action must be explicit;
- human approval must be tied to action class;
- sandbox и blast radius становятся важнее по мере роста доступа к инструментам;
- prompt injection и tool poisoning are action-surface risks.

LangGraph, OpenAI Agents SDK, Google ADK, AutoGen, CrewAI и близкие системы могут появляться как примеры исполнения и оркестрации, но не как замена теории жизненного цикла разработки.

### X. Когда агентов становится много: координация параллельной работы

Gas Town и Beads остаются сильными опорными кейсами, но глава должна быть явно связана с современными multi-agent и cloud PR-поверхностями: subagents, cloud issue-to-PR agents, AutoGen/CrewAI-style orchestration, OpenHands/SWE-agent-like harnesses и A2A-style agent communication.

Главный тезис: параллельные агенты дают ускорение только тогда, когда параллельные единицы работы отделимы, проверяемы и возвращаются в общую картину. Иначе они умножают review burden, merge conflicts, stale context, duplicate work и acceptance debt.

## Часть IV. Проверка, принятие и обучение процесса

### XI. Проверочный материал: что подтверждено и что осталось неизвестным

Глава не должна быть каталогом tests/review/CI. Её предмет — связь между обещанием изменения, риском, проверочным материалом, границей проверки и остатком неизвестного.

Организующая связка:

```text
обещание изменения → риск → проверочный материал → граница проверки → что осталось неизвестным
```

Слои проверочного материала:

- run log;
- technical trace;
- tests и CI;
- contract tests и API diff;
- static verification;
- evals и benchmarks;
- code review;
- security review;
- rollout metrics и SLO signals;
- acceptance note.

Trace помогает восстановить ход работы. Он не доказывает, что изменение корректно, достаточно и может быть принято.

### XII. Принятие результата, ответственность и внешний контур

Глава начинается там, где проверочный материал уже есть, но ещё не решено, можно ли впустить результат в проект. Agent-authored PR is the boundary object: он содержит diff, описание, tests, discussion, review и merge decision, но не отменяет человеческую или организационную ответственность.

Нужно включить empirical PR reality: документационные, CI и build-задачи могут быть для агентов проще; bug-fix, performance и product-shape tasks несут больший риск; неудача может быть вызвана не только failing tests, но и duplicate work, stale task context, unwanted feature implementation, poor reviewer engagement или weak rationale.

### XIII. После merge: сопровождение, очистка состояния и обучение процесса

Глава показывает, что работа не заканчивается merge. После изменения нужно закрыть или обновить working nodes, ADR/spec, tests, documentation, source registers, task package templates, instructions и acceptance notes.

Новый слой: instruction repair. Если агент ошибся из-за слабых инструкций, неясной границы, missing verification bar или stale project rule, post-merge or post-failure pass должен обновить durable process artifacts. Иначе следующая сессия повторит ту же проблему с другим агентом.

## Заключение. Карта выбора режима работы

Заключение должно возвращать труд к личной цели: как выбирать режим агентской разработки.

Примерные surfaces:

- обычный чат для малых вопросов и reasoning;
- локальный terminal agent for isolated repo work;
- IDE-agent for navigation-heavy multi-file editing;
- cloud PR agent for docs/CI/build/dependency maintenance;
- spec-driven IDE for feature work needing requirements/design/tasks;
- open harness for reproducible experiments;
- app-builder for prototype/demo work;
- package runner / future Noveia-like layer for durable doc-first work.

Итоговая мысль: нужен не один лучший агент, а карта режимов, где для каждой задачи заранее видно радиус действия, состояние работы, проверочный материал, право принять результат и путь восстановления.

## Что не менять

1. Не превращать труд в каталог LangChain / ADK / OpenAI Agents SDK / AutoGen / Kiro / Claude Code / Codex.
2. Не делать отдельную большую главу «История LLM agents».
3. Не заменять SPDD, PWG, GSD/BMAD и Gas Town поверхностной индустриальной картой.
4. Не смешивать runtime state с project working state.
5. Не считать trace доказательством результата.
6. Не считать protocol правом на действие.
7. Не считать большее число агентов бесплатным ускорением без acceptance cost.

## Практическое следствие для текущей ветки

Если Skeleton V6 будет принят, оставшиеся target plans и executor packages должны быть перестроены до запуска. Старые планы для введения, XI, XII, XIII и conclusion не обязательно плохие, но они не знают новой структурной рамки карты поля и группировки по частям. Запускать их без ревизии рискованно.
